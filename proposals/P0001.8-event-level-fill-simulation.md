## 0. 本阶段固定契约（供审查）

### 0.1 事件模型：aggressor trade 是唯一成交证据

`MarketEvent` 词表中 `EventType.TRADE` 早在 P0001.1 就已保留，但一直没有载荷类型。
本阶段为它补齐 **`TradePayload`**（`market/events/payloads.py`）：

| 字段 | 含义 |
| --- | --- |
| `aggregate_trade_id` | 交易所聚合成交 id；**去重键**（重复投递不得重复推进队列 / 重复成交） |
| `price` / `quantity` | 该次聚合成交的价格与数量（> 0） |
| `aggressor` | 主动方方向（`AggressorSide.BUY/SELL`）；**只有与挂单方向相反**的 aggressor 才消耗队列 |

- `AggressorSide` 定义在 market 层：`portfolio.types` 已 import market，反向依赖会成环（CLAUDE.md §14）。
- Event Store codec 同步支持 `TRADE` 的编解码（否则「Replay → 模拟器」无法携带成交证据）。
- **未改** `MarketBook` / Feature Engine / `market-state-v1`：`TradeFeatures` 仍然 unavailable（trade 事件只被模拟器消费）。
- **L2 变化永远不是成交证据**：`Book decrease ≠ Fill evidence`。

### 0.2 队列近似与推进规则

| 项目 | 规则 |
| --- | --- |
| 初始队列 | 订单生效时该价位的**可见** resting quantity（`queue_ahead = visible size`） |
| 推进 | **只有** aggressor trade 才推进 `queue_ahead`（`consume_queue`：先扣队列，剩余才是我们的成交） |
| `UNKNOWN` | 价位不可观察 / 盘口不可信 / gap 之后未重建 → `queue_ahead` 为 `None`，**绝不**当作 0，也**绝不**产生推测性成交 |
| `KNOWN` 的建立条件 | `BookHealth == HEALTHY` **且** 订单价位在当前 L2 中可观察（精确价格匹配） |
| 存活期 | 队列估计一旦建立，只由成交推进；L2 档位减少 / 删除**不改变**它（也不是成交证据） |
| 价位匹配 | 精确相等（价格来自同一套 tick 语义） |

### 0.3 Fill 规则

| aggressor 成交价 vs 订单限价 | 证据 | 成交规则 |
| --- | --- | --- |
| 相等 | `QUEUE_CONSUMED` | 先 `consume_queue`，剩余量成交 |
| 穿过订单限价（买单价 > trade 价 / 卖单价 < trade 价） | `TRADE_THROUGH` | 队列视为清空（ahead = 0），成交量 = `min(剩余订单量, 该笔 aggressor 量)` |
| 未触及订单限价 | — | 忽略（不推进队列、不成交） |

- 成交价一律 `order.limit_price`（§11：不做 price improvement 猜测）。
- 流动性一律 `Liquidity.MAKER`，`FillReceived.is_maker = True`。
- 手续费由**显式注入**的 `FeeSchedule(maker_fee_rate, fee_asset)` 计算（无生产默认值）。
- 多张同侧挂单的重叠解释：`TRADE_THROUGH` 的量对每张符合条件订单**各自**生效（各自受自身剩余量约束）。
  这是刻意的保守近似，已记录为 Known Issue；MakerPolicy 每侧最多一张挂单，因此当前链路无歧义。

### 0.4 时钟、延迟与生效

| 项目 | 规则 |
| --- | --- |
| 模拟时钟 | **只**由市场事件推进（`process_ts`，单调取 max）；`poll()` 只在同一时刻重估到期项 |
| Submit latency | `entry_ts = submitted_at + submit_latency_ms`；`process_ts >= entry_ts` 才参与推断（同刻算已进入） |
| Cancel latency | `cancel_effective_ts = requested_at + cancel_latency_ms`；窗口内仍可成交，生效后禁止新成交，**同刻撤单优先** |
| 撤单确认 | 生效时产生 `OrderCanceled`（时间戳 = 生效时刻）；请求当刻已生效则同步返回（不发生二次投递） |
| Ordinal | `SimulatedVenue.event_ordinal` = 已处理事件数（0 基 = 喂入顺序）；Replay 顺序由 Event Store 的 recorded ordinal 决定 |
| wall clock | 全层不 import `time` / `datetime`（由既有隔离测试固定） |

### 0.5 盘口不可信时的处理（gap / stale / 未同步）

- `BookHealth != HEALTHY` → 每张挂单 `fill_inference = SUSPENDED`，队列估计**作废**（`UNKNOWN`），不产生新成交；
- 恢复 `HEALTHY` 后：若价位可观察 → 用**当前可见量**重建队列（`queue_rebuild_count += 1`，`initial_queue_ahead` 保留供审计）；
  否则保持 `UNKNOWN`。**绝不**无声续用 gap 之前的估计。
- 模拟器不自行发出 resync 请求（那是传输层职责）；恢复快照由回放流提供。

**刻意的近似与限制（如实记录）**

1. **队列模型是近似**：只使用 L2 可见量，不声称恢复真实 queue position；`TRADE_THROUGH` 对多张同侧挂单各自生效（见 §0.3）。
2. **不做 hidden / iceberg / self-trade / liquidation / taker**（提案 NOT Included）。
3. `TradePayload` 是 P0001.8 新增的市场载荷：真实 Binance `aggTrade` 归一化与 `TradeFeatures` 接线**不在本阶段**，
   因此当前 `TradeFeatures` 仍为 unavailable（未修改 `market-state-v1`）。
4. `TRADE_THROUGH` 的成交量按「观察到的 aggressor 量」上限，不推断被穿档位的真实深度。
5. 模拟器不主动发 resync：盘口恢复依赖回放流中的快照（与 P0001.1 的传输层职责划分一致）。

## 2. 原提案文本（原样保留）

目标
把现在“人工调用 broker.fill()”的 PaperBroker，升级出一个基于真实 Replay 市场事件的成交模拟器。
目标不是复刻交易所撮合引擎，而是回答：
给定当时真实 L2 Book + Trade 事件，这个 Maker 挂单是否有合理证据认为成交了？成交多少？什么时候成交？

要求：
deterministic
no-future
conservative
explicit uncertainty

背景
当前 PaperBroker 已验证订单状态机，但成交仍由测试显式驱动。
现在需要：
Recorded MarketEvent
      ↓
Replay
      ↓
Fill Simulator
      ↓
ExecutionEvent
      ↓
OrderTracker
      ↓
Accounting

这是 Backtest 与真实 Live 之间最关键的一层。
架构
ReplaySource
   │
   ├─ L2 snapshot/delta
   └─ trade events
          │
          ▼
     SimulatedVenue
          │
          ├─ book state
          ├─ resting orders
          ├─ queue estimate
          └─ latency model
          │
          ▼
     ExecutionEvent
          │
          ▼
      OrderTracker
          │
          ▼
      Accounting

SimulatedVenue 实现现有 ExecutionAdapter 契约。
不要修改 Strategy、Accounting、Risk、OrderTracker 的核心语义。
设计
1. Replay 顺序就是事实顺序
事件严格按已有：
ordinal

处理。
不按：
timestamp
sequence

重新排序。
同一输入必须得到完全相同成交结果。
2. 不使用未来数据
订单在：
submitted_at

之后，只能看到之后进入模拟器的 MarketEvent。
禁止：
查看未来 K 秒最高/最低价
然后决定是否成交

任何 fill 必须由逐事件因果链产生。
3. Maker Queue Approximation
我们只有 L2，不知道真实订单级 queue position。
因此采用明确的近似模型：
订单进入某价位时：
queue_ahead =
该价位当前可见 resting quantity

自己的订单排在可见队列之后。
例如：
best bid = 100
visible qty = 3 BTC

我们挂：
BUY 1 @ 100

初始：
queue_ahead = 3

4. 什么可以消耗 queue_ahead
这是本阶段最重要的规则：
只有有明确成交证据的 aggressor trade 才推进 queue。
例如我们挂：
BUY @100

只有：
SELL aggressor trade @100

才能减少前方队列。
不要因为：
L2 quantity decreased

就认为我们向前排队。
因为减少可能来自：
cancel
modify
hidden liquidity
feed artifacts

因此：
Book decrease ≠ Fill evidence

这是保守模型。
5. Fill 条件
例如：
queue_ahead = 3
our_qty = 1

之后 aggressor sell：
trade 1.0 @100
→ queue_ahead = 2

trade 2.0 @100
→ queue_ahead = 0

trade 0.4 @100
→ fill 0.4

trade 0.6 @100
→ fill 0.6
→ FILLED

自然支持 partial fill。
6. Trade-through
如果 aggressor trade 价格穿过我们的 limit：
例如：
BUY @100

观察到：
SELL aggressor trade @99.5

在没有数据缺口的前提下，可认为：
100 档位已经被穿过。

这种情况允许视为队列已被清空，并按可解释规则产生 fill。
但必须记录：
fill_reason = TRADE_THROUGH

与：
QUEUE_CONSUMED

分开。
7. Book Gap / Unhealthy
一旦：
BookHealth != HEALTHY

模拟器不得继续推导新的 Maker Fill。
订单保留，但模拟状态进入：
FILL_INFERENCE_SUSPENDED

恢复健康以后：
不要假装知道 gap 期间发生了什么。
已有 queue estimate 作废，必须重新建立或标记：
QUEUE_UNKNOWN

不能无声续算。
8. Observable Price Level
只有订单价位在当前 L2 中可观察时，才能建立 queue estimate。
如果：
报价位超出记录深度

则：
QUEUE_UNKNOWN

不能假设 queue=0。
这类订单可以存在，但不能产生推测性 fill。
9. Submission Latency
定义显式配置：
submit_latency_ms
cancel_latency_ms

无默认生产值。
订单直到：
submit_time + submit_latency

之后才进入模拟盘口。
因此 latency 期间发生的 trade 不属于该订单。
10. Cancel Latency
同样：
cancel requested
      ↓
cancel_latency
      ↓
cancel effective

期间订单仍可成交。
这直接复用 P0001.6 的 cancel-race 语义。
11. Fill Price
Maker fill 第一版使用：
order.limit_price

不是 aggressor trade price。
因为真实 resting limit order 的成交不会比自己 limit 更差。
不要在这里做 price improvement 猜测。
12. Fee
Simulator 生成 Fill 时必须明确：
liquidity = MAKER

Fee 不从历史数据猜。
使用显式注入：
FeeSchedule
maker_fee_rate

无生产默认值。
13. Queue Uncertainty
新增模拟状态：
QueueState

KNOWN
UNKNOWN

不要制造虚假的 queue 精度。
必要 telemetry：
initial_queue_ahead
remaining_queue_ahead
queue_state
fill_reason
market_event_ordinal

以后研究策略时才能知道：
这个成交到底是高可信模拟，还是信息不足。

14. Snapshot / Delta
Snapshot 用于：
建立当前 visible depth

Delta 用于：
维护 MarketBook

但 delta quantity reduction 本身不推进 queue。
再次强调：
L2 update
≠
executed volume

15. Replay 与 Paper 分开
保留：
PaperBroker

作为可控单元/故障测试 adapter。
新增：
SimulatedVenue

不要把 PaperBroker 变成越来越复杂的万能类。
16. 与 MakerPolicy 集成
完整研究链：
Replay MarketEvent
→ MarketState
→ Jev / Recorded Prediction
→ MakerPolicy
→ RiskGate
→ SimulatedVenue
→ Fill
→ Accounting
→ next decision

但第一批 Acceptance 可以使用固定 OrderProposal，不要求 Jev 网络调用。
Replay 中 Jev 应使用：
RECORDED

而不是 live requery。
边界
包含
- Event-level simulated venue
- L2 queue approximation
- aggressor-trade-driven fill
- partial fill
- trade-through
- submit latency
- cancel latency
