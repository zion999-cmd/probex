# P0017.5 — Real-Time Multi-Symbol Paper Trading Closure

**P0017.5：实时多标的行情驱动模拟交易链路收口**
**状态：实现中**（人类当前会话明确批准并指示实施，2026-10-12）

## 0. 任务性质与授权

这是 P0017 产品主线的**产品收口任务**，不是新的模块探索项目。

目标是基于 P0017.1–P0017.4 已交付能力，打通实时多标的行情驱动的模拟交易链路，并通过预先定义的端到端验收。

**授权范围：设计、必要的代码修改、测试、回归、验收报告、Closure Audit 和正式收口。**

不需要每个子步骤单独申请批准。执行过程中应直接完成已授权范围内的工作，不得将正常的实现细节反复升级为新的设计阶段。

已有《系统终态闭环审计》作为本提案的基线，不重复开展全系统审计。仅当实际代码与审计结论存在冲突，或发现影响正确性、安全性、核心验收的实质问题时，才进行针对性核验与修复。

## 1. 产品目标

实现以下完整运行链路：

实时多标的公开行情
→ 多标的市场状态更新
→ 多标的决策
→ 共享组合风险控制
→ 多个 SimulatedVenue 模拟执行
→ 订单、成交、持仓、费用与会计更新
→ 运行状态和可审计结果输出。

产品必须能够通过注入式行情源进行确定性自动化验收，也应具备接入现有真实行情采集器的运行路径。

本提案不以“代码已接线”或“模块测试通过”为完成标准，而以端到端链路实际闭合为完成标准。

## 2. 现有能力的复用要求

实施前直接核对必要的实际接口，然后开始实现。不得另起一轮全系统差距审计。

优先复用：

- P0017.1 的 `MultiSymbolMarketCollector` 及其事件、状态输出。
- P0017.2 的组合 gross-notional 风险控制及其既定 reduce-only 语义。
- P0017.3/P0017.4 的多标的决策、模拟执行、共享会计与确定性测试基础。
- 现有 assembly、CLI、运行状态和报告机制。

应尽可能抽取并复用离线回测与实时运行共同需要的步进逻辑，避免复制两套决策/执行实现。

不得为了追求抽象完整性重写已经验证的组件。只有真实集成所必需的生产代码修改才属于本提案。

## 3. 必须交付的功能

### 3.1 实时多标的运行编排

实现 `LiveMultiSymbolRunner` 或等效组件，将实时采集批次持续交给多标的决策与模拟执行链路。

要求：

- 支持至少两个标的。
- 每个标的保持正确的市场状态和决策上下文隔离。
- 所有标的共享同一个组合风险约束和会计状态。
- 明确批次内事件处理、决策、执行轮询的顺序。
- 不允许使用未来事件或引入不符合因果顺序的数据。
- 不允许把历史回测专用逻辑未经核验直接用于实时路径。

### 3.2 组合风险与执行正确性

- 跨标的组合预算在实时模拟路径中真实生效。
- 同批次竞争预算时结果具有确定性。
- 风险拒绝不得产生未授权的订单、成交或会计副作用。
- 保持 P0017.2 已批准的 reduce-only 语义，不得擅自改变风险规则。
- 订单、成交、费用、持仓、已实现盈亏和权益满足既定会计不变式。

### 3.3 运行生命周期

必须定义并实现：

- 正常启动和持续运行。
- 单个标的采集失败时的隔离、状态标记与恢复行为。
- 背压或事件积压的可观察行为，不允许静默丢弃关键事件。
- 重复、乱序或异常时间戳事件的明确处理策略。
- SIGTERM 等正常停止信号下的有序退出。
- 停止时不虚构市场收盘价、不强制平仓、不将模拟订单伪装成真实成交。
- 对未成交挂单采取明确、可测试的停止策略；如果选择撤销，必须验证撤销状态，不得仅因进程退出就假定撤销成功。
- 运行状态和异常原因可被观察与记录。

若现有架构不能安全支持某项恢复语义，应采用明确的安全失败策略，不得宣称具备未经实现和验证的恢复能力。

### 3.4 产品入口

将新运行路径接入现有产品入口，使用户能够使用现有 CLI/启动机制启动多标的实时模拟交易。

命令与配置遵循现有项目约定，具体名称由实际代码决定，但必须在交付文档中提供可复制的启动命令、必要配置、停止方法及结果查看方式。

真实下单路径必须在结构上与本运行模式隔离。模拟模式不得因配置错误、依赖注入错误或降级行为而自动切换为真实下单。

## 4. 固定验收标准

以下条件全部满足才允许关闭提案。

### A. 端到端功能

1. 使用脚本化的多标的行情批次，驱动至少两个标的。
2. 真实执行决策路径，产生可核验的模拟订单、模拟成交及会计更新；不能仅验证函数调用或 mock 被触发。
3. 证明组合预算跨标的生效，并覆盖同批次预算竞争。
4. 验证风险拒绝无副作用。
5. 验证单标的故障不会不必要地终止其他健康标的的运行。
6. 验证正常停止、未成交订单处理和进程退出。
7. 验证重复运行的确定性，以及事件处理的因果正确性。
8. 验证实时运行路径可以输出可审计的状态和运行结果。

### B. 结构与安全

1. 离线与实时路径共用已明确的核心决策/执行步进逻辑，不得维护两份实质相同的实现。
2. 使用结构性测试或 AST 守卫，确认模拟运行路径不依赖 Testnet 或主网写入执行入口。
3. 确认未知标的、缺失市场状态、无效配置等情况具有明确失败行为。
4. 确认组合风险、订单追踪、成交和会计状态保持一致。

### C. 回归与交付

1. 全量测试通过；所有跳过项均记录原因，不得把 skipped 计为通过。
2. P0017.1–P0017.4 的相关回归全部通过。
3. 在 detached clean checkout 中重复验证，确认不依赖未提交文件或本地偶然状态。
4. 提供完整验收报告，列出命令、结果、关键计数及失败/跳过情况。
5. 完成一次 Closure Audit，并同步更新 roadmap、current_state、handoff、status.json 等适用状态文件。
6. 提交实现、测试和收口证据，确认工作树 clean、提交已 push、`currentProposal = null`。

若某项验收失败，不得宣布收口。

## 5. 缺陷处理规则：禁止无限补充

实施期间按以下规则决策：

- **A 类：** 影响正确性、安全性、核心功能或既定验收的缺陷，必须在本提案内修复。
- **B 类：** 外部环境、凭据或授权造成的限制，必须明确记录未验证边界；不得伪造通过，也不得因此反复重做本地已能完成的自动化验收。
- **C 类：** 不影响既定验收的性能、扩展性或非必要增强，记录为后续事项，不阻塞本提案关闭。

只有以下情况允许扩大当前实现范围：

1. 发现核心链路存在真实且无法通过既定设计规避的正确性问题。
2. 发现明确的安全风险。
3. 发现某项既定验收条件无法满足，且原因在于当前实现。

扩大范围时，先判断能否在现有工作包内以最小变更解决。不得仅因发现潜在优化、未来需求或架构偏好而新增阶段。

**完成既定验收后，必须停止开发并关闭提案。不得以“还可以更完善”为由继续追加设计、审计或补丁轮次。**

## 6. 明确排除范围

本提案不包含：

- Testnet 真实下单、撤单、平仓或其他写操作。
- 清理 P0001.16 遗留的 0.001 BTC 测试网仓位。
- 主网/LIVE 交易。
- 新的策略体系或交易信号研究。
- bar/OHLCV、真实滑点、资金费率、taker、真实队列校准等扩展模型。
- 为支持三个及以上标的而进行的独立增强专项。
- 与本提案验收无关的重构和性能优化。

这些事项不得混入当前实现；其未完成状态也不得阻止 L2 的既定收口。

## 7. 外部真实行情验证的边界

本提案必须通过注入式行情源完成确定性端到端验收，不依赖 Binance 网络可达性。

现有真实行情采集器应能被新运行编排调用，但 Binance HTTP 451 导致的真实行情长跑验证仍应单独标记为 NOT RUN，直到具备可访问的外部环境并取得真实证据。

不得把注入式验收等同于真实行情长跑验收，也不得因为真实网络暂不可用而无限期延迟本地产品闭环的交付。
