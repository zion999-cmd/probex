### 0.2 incomeType 分类（**fail closed 的具体边界**）

| 类别 | 取值 | 处理 |
| --- | --- | --- |
| TRADING | `REALIZED_PNL`、`COMMISSION`、`FUNDING_FEE`、`SPECIAL_FUNDING_FEE`（提案 §3 原样） | 计入账户级 daily trading PnL（**按交易所原符号直接相加**） |
| NON_TRADING | **只有 `TRANSFER`**（人类裁决 2026-09-28） | 记录但**不**计入 trading PnL |
| UNCLASSIFIED | 其余一切（`FEE_RETURN`、`INSURANCE_CLEAR`、`REFERRAL_KICKBACK`、`COMMISSION_REBATE`、`API_REBATE`、`CONTEST_REWARD`、`DELIVERED_SETTLE`、`OPTIONS_*`、`WELCOME_BONUS`、跨保证金划转、未来新增枚举……） | `UNCLASSIFIED_INCOME` ⇒ **baseline BLOCKED**（未知 ≠ 0） |

**为什么"其余都 UNCLASSIFIED"（人类裁决 2026-09-28）**：这里定义的不是"钱包余额变化"，而是
**可用于 RiskGate 的账户级 daily trading net realized**；返佣/清算/交割结算是否计入属于**业务语义**，
实现方不得凭名字猜测（CLAUDE.md §12）⇒ 一律 fail closed，等真实账户出现对应类型后再做 evidence-driven 裁决。
（真实测试网当日窗口只出现 `COMMISSION` / `REALIZED_PNL` / `TRANSFER`，未触发该分支。）

### 0.2.1 去重身份：**审计问题不得污染风险计算**（人类裁决 2026-09-28）

| 行类型 | 业务身份 | 冲突语义 |
| --- | --- | --- |
| TRADING（PnL 贡献） | `(income_type, tran_id)` | 同 key 内容不同 ⇒ `HISTORY_CONFLICT` ⇒ BLOCKED（**保持严格**） |
| NON_TRADING / UNCLASSIFIED | **完整行内容**（审计层，canonical row） | 完全相同 ⇒ 去重计数；不同内容 ⇒ **合法共存**（**不** BLOCKED） |

理由：`TRANSFER` 的 `tranId` 恒为 0（真实数据），且它不参与 `daily_net_realized`；
若因两笔 TRANSFER 共用 `tranId=0` 就让整个 daily PnL 变 UNKNOWN，属于审计身份问题污染风险计算。

### 0.3 真实 payload 事实（2026-09-28 实测，驱动解析修正）

- 键集合：`symbol` / `incomeType` / `income` / `asset` / `time` / `info` / `tradeId` / `tranId`；
- `TRANSFER` 行的 `symbol` / `tradeId` / `info` 是**空字符串**（不是缺字段）⇒ 空串按"无值"处理
  （与 P0001.9.2 的 D-033 同类真实数据修正）；
- `TRANSFER` 的 `tranId = 0`（并无唯一 id）⇒ **同一 UTC 日内出现两笔 TRANSFER 会触发
  `HISTORY_CONFLICT`**（提案 §6 指定的键 `(income_type, tran_id)` 在 tranId=0 上不唯一）。
  这是有意的 fail closed；若真实账户出现该情形，需要人类裁决（见 §1.7）。
- 分页：`page=1&limit=1000` 返回 11 行、`page=2` 返回 0 行 ⇒ `rows < limit` 即读完（本实现依赖该规则）。

### 0.4 水位线与去重

- 外部历史：`income.time <= cutoff_ts`；本地账本：`event_ts > cutoff_ts`
  ⇒ `realized_pnl_today = baseline.daily_net_realized + accounting.net_realized_since(cutoff_ts)`；
  任一段未知 ⇒ `None`（未知 ≠ 0），绝无双计（延续 D-038）。
- 去重键 `(income_type, tran_id)`：内容相同 ⇒ 去重计数；**内容不同 ⇒ `HISTORY_CONFLICT` ⇒ baseline 未知/BLOCKED**。
- 三件事实分离（提案 §8）：`daily_pnl_known` / `drawdown_known`（恒 False）/ `peak_equity_known`（恒 False）。

## 2. 原提案文本（原样保留）

我先把一个关键判断定死：P0001.9.4.1 不应该试图“一步恢复完整历史 drawdown”。
原因是 Binance 的 GET /fapi/v1/income 能比较可靠地恢复当日 REALIZED_PNL / COMMISSION / FUNDING_FEE 等现金流，并支持时间范围与分页；官方当前说明历史仅保留最近 3 个月。币安开发者中心
但它不能告诉我们历史每一时刻的账户 equity，因此不能从这些流水可靠推出 intraday peak_equity。强行算就是重新制造假事实。
所以 .1 只解决可精确恢复的 Daily PnL，同时把 drawdown 的“可恢复条件”定义清楚。

状态：已提议
日期：2026-09-28
依赖：P0001.9.4
目标
从 Binance 权威历史事实恢复当前 UTC 风险日内、startup baseline 之前的账户级已实现风险状态，使：
HISTORICAL_DAILY_PNL_UNKNOWN

能够在证据完整时变成已知值。
同时正式定义：
historical daily PnL
≠
historical peak equity / drawdown

本阶段绝不为了让 LIVE_READY 变绿而伪造 peak 或 drawdown。

Recovery = RECOVERED

HISTORICAL_DAILY_PNL_UNKNOWN
HISTORICAL_DRAWDOWN_UNKNOWN

可以按 startTime/endTime/page/limit 查询 income history，并包含 REALIZED_PNL、FUNDING_FEE、COMMISSION 等类型；当前官方说明历史覆盖最多约 3 个月、单页最大 1000。币安开发者中心
2026-09 Binance 还新增了 SPECIAL_FUNDING_FEE，说明 income type 集合会演进，因此实现不能把未知类型静默当成 0。币安开发者中心
