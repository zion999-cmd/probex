## 0.1 本阶段固定契约

| 项目 | 规则 |
| --- | --- |
| Futures 连续性语义 | **`current.pu == previous.u` 才算连续**；`pu != previous.u` 才是真实丢失 → `STALE → RESYNC` |
| 边界携带 | `BookDeltaPayload.previous_update_id: int \| None`（Futures 提供；无该字段的 venue/stream ⇒ None） |
| 判据优先级 | 有 `previous_update_id` ⇒ 用 venue 规则；无 ⇒ 回退既有窗口规则（`first <= last+1 <= u`，D-003），现货语义不变 |

| 既有 `ALREADY_APPLIED` | 仍在最前（`u <= last_applied` 一律视为重复/过期，与 pu 无关） |

## 2. 原提案文本（原样保留）

目标
确认当前 36 次所谓 gap，到底是：
真实消息丢失

还是：
错误使用 U/u 连续性规则导致的假 gap

只做诊断
让 Pi 在真实流上记录连续约 100–300 条 depthUpdate：
prev.u
current.U
current.u
current.pu

然后分别统计：
A: current.U == prev.u + 1
B: current.pu == prev.u

以及：
current.U <= prev.u + 1 <= current.u

不要修改生产语义。
特别把之前判为 GAP 的样本打印 10 条，例如：
prev.u = ...
curr.U = ...
curr.u = ...
curr.pu = ...
old_rule = GAP
pu_rule = CONTIGUOUS/GAP

判定
如果大量样本表现为：
U != prev.u + 1
但是
pu == prev.u

那么结论就是：
P0001.1 的 Binance Futures adapter 把事件内部/批次 ID 跳跃误判成了消息丢失。

这种情况下不要选 A，也不要弱化成 B。
应该直接修 adapter：
Binance Futures continuity:
current.pu == previous.u

真正：
current.pu != previous.u

才触发：
STALE → RESYNC

这不是“弱化完整性”，而是修正 venue-specific sequence semantics。
不包含
- 不切 depth20
- 不接受有界 gap
- 不修改 MarketBook 通用完整性原则
- 不后台 REST resync
- 不改 Feature schema
- 不做 P0001.9.2
