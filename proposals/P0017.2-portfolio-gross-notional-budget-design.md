## 1. 设计目标

P0017.2 的目标是解决多标的交易中的组合风险约束缺口：

当多个标的分别通过现有单标的风险检查时，其合计敞口仍可能超过账户允许的组合预算。

本设计采用**组合级第二道风险闸 + 现有单标的 RiskGate** 的方案，在尽量保留既有架构和行为的前提下，为所有标的建立统一的总名义敞口约束。

本设计不重构整个风险系统，不改变交易策略，也不改变账户会计与交易所执行的权威职责。

本文严格区分：

* **代码事实：** 来自现有只读耦合分析报告。
* **设计决策：** 本文提出的目标语义。
* **实施前验证：** 必须对实际代码、状态机和调用时序进一步确认的事项。

本文本身不构成实现授权。

## 2. 现状与问题

根据只读耦合分析报告：

1. `RiskLimits` 已有单标的持仓限额，以及账户级日亏损、回撤和杠杆限制，但没有跨标的总持仓或总在途敞口限额。
2. `RiskSnapshot` 包含组合级聚合信息，但自身仍然是带有单一 `symbol` 的风险快照。
3. `AccountingCore` 管理多标的持仓，已经具备组合 gross exposure 计算能力。
4. `RiskGate.evaluate()` 对 symbol 不匹配执行硬拒绝，因此不能直接把现有单标的闸改成跨标的评估器。
5. `OrderTracker` 具有全局在途敞口统计，但 `execution/engine.py` 将该总量传入单标的快照，存在统计作用域不一致的问题。

由此产生的缺口是：

假设组合限额为 10,000 USDT，两个标的分别持有 6,000 USDT 的名义敞口。如果现有检查仅分别约束每个标的，那么两个标的都可能通过，但组合总敞口已达到 12,000 USDT。

现有单标的风险检查不能替代组合级风险检查。

## 3. 目标与非目标

### 3.1 目标

1. 建立跨标的共享的 gross notional 限额。
2. 保留现有 `RiskGate` 及其单标的检查职责。
3. 将当前持仓与仍可能成交的在途订单纳入统一预算。
4. 明确单标的在途限额与组合总限额的作用域。
5. 新限额默认关闭，保持现有配置的兼容性。
6. 在状态一致性得到证明的前提下，采用单决策线程顺序评估，不引入不必要的新锁。
7. 在无法可靠确定敞口时遵循 fail-closed 原则。

### 3.2 非目标

本提案不包括：

* 保证金、初始保证金或维持保证金模型。
* VaR、情景损失或前瞻性 loss-at-risk 模型。
* 重写 `RiskSnapshot` 和 `RiskGate` 为统一的组合快照体系。
* 引入每个标的独立配置的组合预算。
* 修改 MakerPolicy 的策略逻辑。
* 改变交易所订单提交、撤销、幂等或对账语义。
* 改变 `AccountingCore` 的会计权威职责。
* 修改 `status.json`、roadmap、`currentProposal` 或其他生命周期状态。

## 5. 预算单位与数学语义

### 5.1 Gross notional

对标的 \(s\)，定义持仓名义敞口：

$$
N_s=|q_s p_s|
$$

其中：

* \(q_s\)：该标的的当前净持仓数量。
* \(p_s\)：该标的有效标记价格。

组合持仓总名义敞口为：

$$
G_{\mathrm{position}}=\sum_{s\in S}|q_s p_s|
$$

其中 \(S\) 是组合中所有需要纳入计算的标的集合。

该定义与 `AccountingCore.gross_exposure` 的现有语义保持一致。

**Gross notional 不是保证金，也不是最大潜在亏损。** 本系统没有因此获得 IM/MM、VaR 或情景损失计算能力。

缺失、无效或不符合现有有效性要求的标记价格，不得静默转换成零敞口。

### 5.2 为什么不能简单使用净敞口

组合预算采用：

$$
G=\sum_{s\in S}|N_s|
$$

而不是：

$$
N_{\mathrm{net}}=\left|\sum_{s\in S}N_s\right|
$$

原因是多空对冲可能降低净敞口，却不能证明总名义敞口或相关风险已经消失。

### 5.3 在途订单与拟提交订单

组合预算不能只检查当前持仓，还必须纳入：

* 已成交且已反映在会计持仓中的敞口。
* 尚未成交、但仍可能成交的订单剩余量。
* 正在评估的候选订单。

但不能直接把所有订单的原始名义价值机械相加。部分成交、反手订单、reduce-only 订单和订单状态不确定性都可能使简单相加出现重复计数或错误判断。

因此，组合风险闸必须遵循以下安全不变量：

> 如果某个候选订单在系统支持的订单状态和成交语义下，存在可能导致组合 projected gross 超过限额的可行成交结果，则不得批准该订单增加风险。

具体算法必须与现有订单状态机、会计更新时序和交易所实际支持的订单语义一致。

## 6. 在途订单状态与敞口规则

实施前必须逐项映射到 `execution/types.py` 的实际 `OrderStatus` 和合法状态转换，不得仅根据状态名称推断订单是否仍可成交。

| 订单状态或事件                | 组合预算处理                      | 必须满足的约束                      |
| ---------------------- | --------------------------- | ---------------------------- |
| ACTIVE / 已接受且仍有剩余数量    | 计入仍可能成交的剩余敞口                | 不重复计算已成交部分                   |
| 部分成交                   | 已成交部分由会计持仓计入；未成交部分继续作为在途敞口  | 验证 tracker 与 accounting 更新时序 |
| 撤单请求中 / cancel-pending | 继续保留剩余敞口                    | 撤单请求不等于撤单成功                  |
| 权威终态撤单、拒绝或过期           | 只有在状态确认后，才可释放不再可能成交的剩余敞口    | 处理可能迟到的成交事件                  |
| 完全成交                   | 在途剩余敞口归零，由会计持仓反映成交结果        | 不得继续计算整笔原始订单金额               |
| LOST / 未知提交结果 / 对账未收敛  | 保守保留不确定敞口                   | 不得把未知状态当作已撤销或空订单             |
| 撤单后出现迟到成交              | 依照既有成交去重和记账规则更新敞口           | 不重复入账，不提前释放预算                |
| reduce-only            | 仅在交易所语义和本地订单契约足以保证时，才可按减仓处理 | 不允许通过错误的减仓假设掩盖风险             |
| 反手订单                   | 考虑平仓和反向开仓可能性                | 不得假设反向订单只会降低敞口               |

### 6.1 部分成交的计数边界

对一个部分成交订单：

$$
Q_{\mathrm{original}}
=
Q_{\mathrm{filled}}
+
Q_{\mathrm{remaining}}
$$

在一致的状态视图中：

* \(Q_{\mathrm{filled}}\) 对应已经应用到会计持仓的成交量。
* \(Q_{\mathrm{remaining}}\) 对应仍可能成交的剩余量。

这只是订单数量守恒关系，不意味着名义金额在价格变化时也能直接使用同一价格相加。实际名义价值计算必须遵循统一的价格口径。

如果现有事件处理可能出现会计持仓先更新而 tracker 剩余量尚未减少，或者相反，则必须先解决或证明决策视图能够避免重复计算和遗漏。

### 6.2 reduce-only 的特殊处理

不能简单地因为订单带有 `reduce-only` 标记，就将其从组合预算中排除。

设计必须验证：

1. 交易所是否强制执行该约束。
2. 本地订单类型是否完整表达该语义。
3. 数量超过现有持仓时，实际成交行为如何定义。
4. 与其他仍可能成交的订单共同存在时，是否仍能保证不反手、不增加敞口。

若无法证明其只会降低敞口，则采用保守计算；不能凭标签给予无条件放行。

### 6.3 LOST 与不确定订单

未知状态不等于订单不存在。

如果未知订单的剩余数量、价格或可能成交范围无法可靠确定，则对风险增加操作执行 fail-closed。只有在对账或其他权威事件使敞口重新可计算后，才可依据更新后的状态重新评估。

## 7. 目标架构

### 7.1 职责划分

**`AccountingCore`**

* 继续作为账户会计和持仓的权威来源。
* 提供现有多标的持仓与标记价格语义。
* 不新增第二套可独立变更的持仓账本。

**`OrderTracker`**

* 继续负责订单状态、成交去重、撤单中状态及不确定敞口。
* 提供按标的查询的只读敞口视图。
* 不改变订单状态机的权威归属。

**组合预算评估器**

建议新增：

`risk/portfolio_budget.py`

其职责是基于一致的输入视图，纯函数式地评估候选订单加入后是否违反组合 gross-notional 限额。

评估器不得直接提交订单、修改会计持仓或变更 tracker 状态。

**`RiskLimits`**

新增可选字段：

`max_portfolio_gross_notional`

**现有 `RiskGate`**

继续负责单标的风险检查，不移除 symbol mismatch 检查，也不绕过既有硬约束。

### 7.2 评估流程

对于候选订单，目标流程为：

1. 取得会计持仓、有效标记价格和 tracker 订单状态的一致视图。
2. 检查敞口计算所需的数据是否完整、有效。
3. 计算包含候选订单的保守 projected portfolio gross。
4. 若超过已配置的组合限额，使用 `PORTFOLIO_NOTIONAL_LIMIT` 拒绝。
5. 若组合检查通过，构造正确的单标的 `RiskSnapshot`。
6. 使用候选标的对应的在途敞口执行现有 `RiskGate`。
7. 如果单标的风险闸拒绝，保留其既有拒绝原因。
8. 两道闸均通过后，沿用既有执行管理器和 tracker 流程。
9. 保证候选订单的预算占用在下一次决策之前可见，避免多个决策重复消费同一预算。

具体检查顺序必须兼容现有硬检查的优先级。实施时应先审计现有 reason-code 顺序，再通过测试固定最终的拒绝原因优先级。

## 8. 单标的在途敞口作用域修正

只读耦合分析指出，当前 tracker 的全局在途敞口被传入单标的快照，导致统计作用域错位。

本设计明确：

**`max_open_order_exposure` 是单标的在途敞口限额，不是组合总在途限额。**

拟实施的修改包括：

1. 在 `OrderTracker` 中增加只读方法 `exposure_by_symbol()`。
2. 在构造单标的 `RiskSnapshot` 时，只传入对应标的的在途敞口。
3. 如果保留组合总在途敞口统计，应使用明确表达 portfolio scope 的名称。
4. 增加守恒测试：在统计口径和有效数据范围一致时，所有标的的在途敞口之和应等于对应的组合总在途敞口。
5. 对 LOST、未知敞口和无效价格等特殊类别分别定义统计语义，不能通过混合不同口径让守恒测试表面通过。
6. 保持单标的历史行为兼容。

这里的守恒关系必须建立在相同订单集合、价格口径和状态纳入规则之上，而不是强行要求不同口径的指标相等。

## 9. 并发、一致性与 TOCTOU

本设计倾向于单决策线程顺序评估，不增加新锁，但这必须以实际代码证明为前提。

目标的决策序列为：

`读取一致状态 → 组合预算检查 → 单标的风险检查 → 确保候选订单预算占用可见 → 继续既有提交流程`

不能出现两个决策读取同一份旧状态，各自判断剩余预算充足，最终共同超限的情况。

实施前必须确认：

* 所有风险增加决策是否都经过同一串行执行入口。
* 是否存在其他线程、回调或异步入口可以提交订单。
* tracker 和 accounting 的更新是否会造成决策视图短暂不一致。
* 订单提交结果为 UNKNOWN 时，候选订单是否能立即进入保守的在途统计。
* 新订单的预算占用是在提交前、提交后还是其他时点登记。
* 撤单、迟到成交和对账更新是否可能与预算评估交错。

**单线程本身不自动证明没有 TOCTOU。** 只有当决策序列、状态更新边界和订单登记顺序均得到验证时，才可以采用无新锁方案。

如果无法证明该不变量，必须暂停集成并提出同步或预留机制的设计变更，不得直接假定现有执行流程足够安全。

## 10. 配置与兼容性

拟新增配置：

`RiskLimits.max_portfolio_gross_notional`

目标语义：

* `None`：禁用组合级限额，保持现有行为。
* 配置为有效非负金额：启用组合 gross-notional 约束。
* 计价单位：USDT 名义价值。
* 所有标的共享同一个组合限额。
* 不改变现有 `max_position_qty`、`max_position_notional`、`max_open_order_exposure`、日亏损、回撤、杠杆等既有字段的其他语义。

具体类型、数值校验、序列化默认值和零值边界，必须沿用现有 `RiskLimits` 的设计惯例，并通过兼容性测试确认。

不得在未审查持久化配置格式的情况下，静默迁移或重解释既有配置。

建议明确边界规则：

$$
G_{\mathrm{projected}}\leq G_{\mathrm{limit}}
$$

允许通过；只有严格超过限额时才因组合金额超限而拒绝。对于浮点精度、Decimal 及金额比较，应遵循项目现有数值类型与比较规范。

## 11. 拒绝原因与可观测性

新增拒绝原因：

`PORTFOLIO_NOTIONAL_LIMIT`

它必须与现有单标的 `NOTIONAL_LIMIT` 区分。

组合预算拒绝结果至少应能帮助定位：

* 配置的组合限额。
* 计算得到的 projected gross。
* 使用的统计范围和价格口径。
* 拒绝是由于确定的超限，还是由于无法建立安全敞口上界。

如果现有类型系统已有适用于缺失数据或未知状态的专用错误/拒绝原因，不应把所有失败都塞入 `PORTFOLIO_NOTIONAL_LIMIT`。

拒绝原因的优先级和 telemetry 统计方式应通过确定性测试固定。

## 12. Fail-closed 规则

对于风险增加操作，出现下列情况时，不得静默低估组合敞口：

* 必需标记价格缺失、无效或过期。
* 未知订单状态导致剩余敞口无法界定。
* 会计与订单追踪视图不一致。
* 数量、价格或计算结果无效。
* reduce-only 或反手语义无法可靠确认。
* 决策并发破坏了一致视图或预算预留约束。

Fail-closed 应通过项目既有的类型化错误或拒绝机制实现。

它不意味着把未知敞口设为零，也不意味着无条件禁止所有风险降低操作。对于风险降低操作，只能在其安全性可以由实际订单和交易所语义证明时保留现有放行行为。

## 13. 验收标准

### 13.1 组合预算测试

* [ ] 组合限额为 `None` 时，既有单标的行为不变。
* [ ] 多个标的各自满足单标的限额，但组合 projected gross 超限时，组合闸拒绝。
* [ ] projected gross 等于组合限额时，按规定边界规则允许通过。
* [ ] 单标的自身超限时，仍由原有单标的风险闸拒绝。
* [ ] 多空持仓采用 gross 聚合，不以净敞口抵消。
* [ ] 缺失价格和无效输入不会被当成零敞口。
* [ ] 组合拒绝原因与单标的拒绝原因区分。

### 13.2 订单状态与会计测试

* [ ] 部分成交只把已成交部分计入会计持仓一次。
* [ ] 部分成交订单只按剩余量计入在途敞口。
* [ ] 撤单中订单继续占用预算。
* [ ] 权威终态订单不会永久保留不再可能成交的剩余敞口。
* [ ] LOST 或未知订单不会静默释放预算。
* [ ] 迟到成交和重复成交事件不造成重复记账或重复计算。
* [ ] 反手订单覆盖平仓和反向开仓情形。
* [ ] reduce-only 覆盖超量订单及与其他在途订单同时存在的情况。
* [ ] 候选订单只被计入一次。
* [ ] 已接受订单的预算占用在下一次决策前可见。

## 15. 实施风险与待验证事项

### 15.1 Projected gross 算法

必须将“所有允许的成交结果均不超过预算”的语义，转化为适用于当前订单模型的确定性算法。

不能仅凭一个简单求和公式就声称已经正确覆盖反手、reduce-only 和独立成交的多个订单。

### 15.2 未知订单状态

保守保留未知敞口可能暂时降低交易可用性。这是风险安全与交易可用性之间的明确权衡，不应通过把未知当作零来规避。

### 15.3 标记价格一致性

组合聚合需要定义一致的价格视图。不同时间的价格与持仓、订单状态混合计算，可能使预算检查失去意义。

### 15.4 单线程假设

如果系统存在其他能够提交风险增加订单的入口，单决策线程设计就不充分，必须补充预算预留或同步机制。

### 15.5 reduce-only 的交易所保证

本地意图不能替代交易所实际执行语义。必须根据现有 adapter 与订单契约确定可依赖的保证。

### 15.6 在途敞口的统计范围

现有 `total_pending_exposure` 可能与普通在途敞口、未知敞口使用不同口径。实现时必须统一定义或明确分项，不能用含义不一致的指标构造表面守恒关系。
