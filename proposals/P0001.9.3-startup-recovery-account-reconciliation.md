### 0.2 Recovery 状态与 reason code

| 项 | 定义 |
| --- | --- |
| 状态 | `RECOVERED` / `BLOCKED`（`NOT_RECOVERED` 为初始值；stream 断开后回落到它） |
| reason code | `STREAM_NOT_ACTIVE`、`CONTINUITY_NOT_ASSUMED`、`BOUNDARY_MISSING`、`ACCOUNT_SNAPSHOT_FAILED`、`POSITION_SNAPSHOT_FAILED`、`OPEN_ORDERS_READ_FAILED`、`ORDER_HISTORY_READ_FAILED`、`FILLS_READ_FAILED`、`FOREIGN_OPEN_ORDER`、`UNRESOLVED_ORDERS`、**`UNRESOLVED_FILLS`**（P0001.9.3.1 新增）、`RECONCILIATION_NOT_CONVERGED`、`BASELINE_MISMATCH`、`BASELINE_ALREADY_APPLIED`、`ACCOUNT_MODE_UNSUPPORTED`、`SYMBOL_CONTRACT_VIOLATION` |
| 未知即 BLOCKED | 任一条件未知/失败 ⇒ `BLOCKED`（绝不"当作没问题"） |

### 0.3 Probex ownership boundary

- 只认 `clientOrderId` **严格**匹配 `probex-`（前缀 + 至少一个字符）的订单为**自己的**
  （`OWNED_CLIENT_ORDER_ID_PREFIX = CLIENT_ORDER_ID_PREFIX + "-"`；P0001.9.3.1 SC-1：
  `probexevil-1` / `probex2` / `probex` / `probex-` 一律属于 external）。
- 发现任何**非 Probex 外部挂单** ⇒ `BLOCKED: FOREIGN_OPEN_ORDER`；**不忽略、不自动撤、不 adopt**。
- 历史订单/成交同样只归一化 Probex 自己的记录；成交按**三分类**处理（P0001.9.3.1 §0.1）：
  自己的 → reconcile；**已验证外部**（映射存在但前缀不匹配）→ 丢弃并计数 `foreign_fills`；
  **不可归属**（映射不存在）→ `BLOCKED: UNRESOLVED_FILLS`（未知成交不得被忽略）。

### 0.4 Accounting startup baseline（一次性）

- `ExternalAccountBaseline`（wallet/available/position/entry/mark/liquidation/captured_at/source=BINANCE_RECOVERY）。
- `AccountingCore.bootstrap_from_baseline(...)`：
  - **仅当**「本 session 尚未处理任何 Fill」且「尚未 bootstrap 过」时允许一次；否则拒绝（SC-7）。
  - 之后所有变化仍只能由真实 Fill / Funding / Mark 驱动；**禁止第二次覆盖**（`baseline_applied` 记录）。
  - 不产生任何 synthetic Fill（SC-6）。
- **历史 PnL 保持 UNKNOWN**：baseline 之后 `net_realized_since(ts)` 对 `ts < captured_at` 返回 `None`；
  `peak_equity` / `drawdown` / `drawdown_pct` 在 baseline 之后为 `None`（历史峰值未知）；
  `RiskGate` 对这些未知值 **fail closed**（新增 `MISSING_DRAWDOWN`）。

### 0.5 Reconnect 纪律

private stream 断开 ⇒ `continuity_assumed=False`（P0001.9.2 runtime 已有）+ recovery 状态立即回落为
`NOT_RECOVERED`；**即使自动重连成功也不得自动 RECOVERED**，必须重新走
`snapshot → external orders/fills → reconcile → RecoveryGate`（SC-8）。

## 2. 原提案文本（原样保留）

目标
让 Probex 在启动、重启、private stream 断线恢复之后，能够重新确认 Binance 外部真实状态，并决定本地状态是否可以继续使用。
本阶段解决的是：
“我重新启动以后，
现在账户里有什么仓位、挂单、成交，
本地 OrderTracker / Accounting 是否可信？”

最终输出明确的：
RECOVERED
BLOCKED

而不是直接开始真实交易。
背景
现有能力已经有：
PrivateAccountRuntime
→ account snapshot
→ position snapshot
→ user stream
→ snapshot boundary

OrderTracker
→ ACTIVE / LOST / unresolved

reconcile()
→ ExternalOrder / ExternalFill
→ 本地订单状态收敛

但中间还缺真正的 live adapter：
Binance REST facts
        ↓
ExternalOrder / ExternalFill
        ↓
reconcile()

而且重启后 AccountingCore 目前没有合法方式从交易所当前仓位恢复。
禁止用伪造 Fill 去“补”当前仓位。
架构
Binance Private API
      │
      ├── account / position snapshot
      ├── open orders
      ├── order history
      └── user trades
              │
              ▼
       RecoverySnapshot
              │
      ┌───────┴────────┐
      ▼                ▼
 Order Recovery   Account Baseline
      │                │
      ▼                ▼
 OrderTracker     AccountingCore
      │                │
      └───────┬────────┘
              ▼
       RecoveryGate
        │          │
   RECOVERED     BLOCKED

Private stream 必须先建立，再获取恢复快照，继续沿用 P0001.9.2 的 boundary 纪律。
设计
1. 增加只读 Recovery REST facts
扩展现有 PrivateRestClient，仅增加读取能力：
open orders
order history
user trades

第一版：
venue  = Binance USDⓈ-M
symbol = 单一 symbol
mode   = one-way

统一归一化为现有：
ExternalOrder
ExternalFill

不要另造一套订单领域模型。
2. Order Recovery
启动时：
交易所 open orders
+ recent order facts
+ recent fills
        ↓
existing reconcile()
        ↓
OrderTracker

必须覆盖：
本地 ACTIVE，但交易所不存在 → LOST
本地 LOST，交易所仍存在 → RESTORED
交易所有 Probex 订单，本地没有 → ADOPT
成交遗漏 → 补 canonical Fill
资料不足 → unresolved / fail closed

3. Probex ownership boundary
只把：
clientOrderId prefix = probex-

视为 Probex 自己的订单。
如果发现非 Probex 的外部挂单：
FOREIGN_OPEN_ORDER
→ Recovery BLOCKED

不能：
忽略
自动撤掉
自动 adopt

因为同一个账户存在人工/其他机器人订单时，本系统不能假装自己拥有完整状态。
4. Account Baseline
这是本阶段最重要的新契约。
当前 AccountingCore 规定：
Position 只能由 Fill 派生。

但重启时交易所可能已经存在仓位，因此必须增加一个显式 startup baseline，而不是制造历史 Fill。
概念：
ExternalAccountBaseline
- wallet_balance
- available_balance
- position_qty
- entry_price
- mark_price
- liquidation_price
- captured_at
- source = BINANCE_RECOVERY

允许 AccountingCore 在：
尚未处理任何本 session Fill

时 一次性 bootstrap。
之后：
所有变化仍只能由真实 Fill / Funding / Mark 驱动

禁止第二次偷偷覆盖 Accounting 状态。
5. 历史 PnL 不伪造
Startup baseline 只能回答：
“现在是什么状态”

不能证明：
今天启动前赚亏多少
历史 peak equity
完整 funding history

因此这些未知值必须保持 UNKNOWN。
尤其不能因为 restart 就让：
realized_pnl_today = 0
drawdown = 0

看起来像真的。
如果 RiskGate 依赖这些数据：
继续 fail closed

历史 PnL 恢复留给后续独立能力。
6. RecoveryGate
只有全部成立才输出：
RECOVERED

至少要求：
private stream ACTIVE
continuity_assumed = true
snapshot boundary 有效
account / position snapshot 成功
open orders 成功读取
recent fills 成功读取
无 unresolved order
无 foreign open order
OrderTracker reconcile 收敛
Accounting baseline 与外部 position 一致
one-way / USDT-M / symbol 契约成立

任何一项未知：
BLOCKED

并必须有 reason code。
7. Reconnect
private stream 一旦断线：
continuity_assumed = false
Recovery state → NOT_RECOVERED

即使自动重连成功，也不能自动恢复 RECOVERED。
必须重新：
snapshot
→ external orders/fills
→ reconciliation
→ RecoveryGate

边界
包含
- Binance open-order 只读查询
- Binance order-history 只读查询
- Binance user-trades 只读查询
- ExternalOrder / ExternalFill 归一化
- startup recovery orchestration
- OrderTracker reconciliation 接线
- 一次性 Accounting startup baseline
- foreign-order 检测
- recovery reason codes / telemetry
- reconnect 后强制重新 recovery
- testnet read-only acceptance
- 清理 roadmap 当前残留的错误状态行
不包含（关键）
- 不实现真实 submit
- 不实现真实 cancel
- 不自动撤 foreign order
- 不修改杠杆
- 不修改 margin mode
- 不修改 position mode
- 不启动 MakerPolicy live loop
- 不让 Strategy 直接访问 private API
- 不做主网真实资金交易
- 不做完整历史 PnL 重建
- 不做历史 funding 重建
- 不做 durable trading-state database/checkpoint
- 不用 synthetic Fill 伪造已有仓位
- 不引入 CCXT
- 不改 P0001.9.1 public transport
- 不进入 P0001.10
目录结构
建议：
connectors/binance/private/
  recovery.py          # recovery orchestration
  orders.py            # ExternalOrder normalization
  trades.py            # ExternalFill normalization
  rest.py              # 增加只读查询

portfolio/
  accounting.py        # 一次性 startup baseline contract

execution/
  reconciliation.py    # 仅必要契约扩展，不重写现有算法

tests/
  unit/
  integration/
  fault/
  live/

不要创建新的 core/、services/、managers/。
成功标准
1. 空仓、无挂单启动 → RECOVERED。
2. 已有 Probex 挂单重启 → 正确 ADOPT / RESTORE。
3. 已有成交但本地遗漏 → canonical Fill 只补一次。
4. 非 Probex 外部挂单存在 → BLOCKED: FOREIGN_OPEN_ORDER。
5. 有未解决订单资料 → BLOCKED，未知暴露不得按 0。
6. 非空仓重启 → 从真实 position snapshot 建立一次性 baseline，不产生 synthetic Fill。
