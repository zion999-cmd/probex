## 0. 已确认的真实外部契约

> Jev 当前通过 OpenRouter 调用，不使用旧的 Typesafe `/v1/systemone` 直连接口。

| 项目 | 值 |
| --- | --- |
| Provider | OpenRouter |
| Model | `typesafe/jev-router` |
| Endpoint | `POST https://openrouter.ai/api/v1/chat/completions` |
| Auth | `Authorization: Bearer <OPENROUTER_API_KEY>` |
| Content-Type | `application/json` |
| 请求体 | OpenAI-compatible Chat Completions：`{"model": "typesafe/jev-router", "messages": [{"role": "user", "content": "<jev-market-v1 canonical payload>"}]}` |
| 响应 | 提取 `choices[0].message.content` 作为 Jev content |
| 凭证 | 只来自环境变量 `OPENROUTER_API_KEY`；不写入仓库 / 日志 / Record / fixture |
| 依赖 | 只用标准库 `urllib.request`，不新增第三方依赖 |

分层（禁止跨层）：

```text
OpenRouterTransport      本模块：HTTP / Authorization / timeout / OpenRouter envelope / status / transport error
      ↓ choices[0].message.content
JevProvider              P0001.4 既有 adapter（未修改）
      ↓ Jev content
existing strict parser   P0001.4 既有（未修改）
```

旧 `fmz_v3(1).js` 语义（`market_*`：choice / probabilities / confidence；`toxicity_*`：score / probabilities；
`fill_*`：noul / probability / value）仅作为 Jev 领域参考，**不作为 OpenRouter 下的契约**。
真实返回必须由 live test 验证；不一致时报告 `CONTRACT_MISMATCH`，不得静默修值或模糊兼容。

## 1. 实现与验收契约

### 1.1 Included（已实现）

- `prediction/providers/openrouter.py`：`OpenRouterTransport`（真实 HTTP）、`build_chat_completions_body`、
  `extract_message_content`、`map_http_status`、`OpenRouterCall`（telemetry）。
- HTTP timeout、HTTP error mapping、envelope 校验、调用 telemetry（request bytes / status / response bytes /
  latency / error name）。
- API Key 仅从环境变量读取；绝不进入 telemetry、异常文本、`PredictionRecord` 或测试 fixture。
- 离线验证：本机 stub server（`tests/stub_server.py`，只监听 `127.0.0.1`）。
- 真实验证：`tests/live/test_openrouter_live.py`（显式 opt-in + 真实 Key）+ 契约诊断报告器
  （`tests/live/contract_report.py`，输出 envelope / content 结构 / 旧 FMZ 语义 / 五分类求和 / latency）。

### 1.2 NOT Included（未触碰）

- Strategy / 买卖信号 / Order / Position / Accounting / Risk。
- 概率解释、TTL、stale response、backoff policy（属 P0001.4 上层，保持不变）。
- 连接池、重试风暴、多 provider、性能优化。
- 不保存 API Key；不静默 normalize；不修改 P0001.1–P0001.4 的公开契约；不新增第三方依赖。

### 1.3 固定实现细节（供审查）

| 项目 | 取值 |
| --- | --- |
| 4xx（400/401/403/404/405/406/409/410/413/415/422 及其它 4xx） | `PredictionTransportError` → `TRANSPORT_ERROR` |
| 408 / 425 / 429 / 5xx | `PredictionProviderError` → `PROVIDER_ERROR`（由上层 backoff 处理） |
| 非 JSON 体 / envelope 不符（缺 `choices`、缺 `message`、`content` 为空） | `PredictionInvalidResponseError` → `INVALID_RESPONSE` |
| HTTP / socket timeout | `PredictionTimeoutError` → `TIMEOUT` |
| 缺 `OPENROUTER_API_KEY` | `PredictionTransportError`，且**不发起任何请求** |
| 阻塞 HTTP | 在线程中执行（`asyncio.to_thread`），事件循环不被占用 |
| wall-clock | 仅 `prediction/providers/openrouter.py` 允许（`time.monotonic`，只用于 latency telemetry）；有结构性测试保证其它预测层模块不得使用 |
| `PredictionRecord.raw_response` | Jev content（strict parser 的输入），不是 OpenRouter 外层 |
| `PredictionRecord.provider` / `model` | `jev`（`JevProvider.PROVIDER_NAME`）/ `typesafe/jev-router` |

## 2. 原 P0001.4.1 提案文本（原样保留）

# P0001.4.1：Real Jev Transport Validation
状态：已提议
日期：2026-09-28
依赖：P0001.4
目标
把已经完成的 Prediction Runtime 接到真实 Jev API，验证最重要的工程假设：
真实请求
→ 真实响应
→ strict parser
→ PredictionRecord

重点不是做完整网络基础设施，而是证明我们的 Provider 契约与真实世界一致。
背景
P0001.4 已经证明：
MarketState
→ Request
→ Provider abstraction
→ Prediction

内部成立。
现在唯一没验证的是：
Provider abstraction
↔ Real Jev

这个假设必须在继续扩大系统前验证。
架构
PredictionRuntime
       │
       ▼
   JevProvider
       │
       ▼
  JevTransport
       │ HTTPS
       ▼
    Real Jev
       │
       ▼
 ProviderResponse
       │
       ▼
 existing strict parser

禁止修改上层 Runtime 来迁就真实 API。
如果 API 不匹配，应该修改 adapter。
设计
真实 Transport 只负责：
endpoint
authentication
request serialization
HTTP timeout
response body
HTTP status
transport errors

它不负责：
probability interpretation
TTL
stale response
backoff policy
MarketState
Strategy

这些已经属于上层。
必须记录真实调用 telemetry：
request bytes
HTTP status
response bytes
latency_ms
provider/model
parse outcome

但 API Key 绝不进入日志、PredictionRecord 或 Event Store。
验证场景
至少用若干个真实、已经 warm-up 的 MarketState 请求 Jev，验证：
1. 实际请求 payload 是否被 API 接受。
2. 实际响应能否被现有 strict parser 无修改解析。
3. 实际 model/provider 字段如何返回。
4. HTTP 4xx / 5xx 如何表现。
5. timeout 如何表现。
6. 响应 latency 的实际分布数量级。
7. Jev 是否存在 schema 外字段。
8. probabilities 是否确实满足当前互斥和求和契约。
尤其第 8 条不能靠猜。
如果 Jev 返回的实际上不是我们定义的严格五分类分布，就必须现在修订 jev-market-v1，而不是 parser 强行修值。
边界
包含
- 一个真实 Jev HTTP transport
- API key 从环境/运行配置注入
- 网络 timeout
- HTTP error mapping
- 真实调用 smoke/integration test
- response contract 验证
- latency telemetry
- 可选人工执行的 live test
不包含（关键）
- 不进入 Strategy
- 不下单
- 不实现 Accounting
- 不实现 Risk
- 不做性能优化
- 不做连接池框架
- 不做多 provider
- 不做 retry storm
- 不保存 API Key
- 不因为真实响应不符合预期就静默 normalize
- 不改变 P0001.1–P0001.3
成功标准
1. 至少一组真实 warm MarketState 能完成：
   MarketState → Jev → PredictionRecord。
2. 真实 Jev 响应无需业务层特殊分支即可进入现有 Parser；若不能，必须明确报告契约差异。
3. 非 2xx、timeout、非法 body 都能映射为既有 failure type，不产生假 Prediction。
4. API Key 不出现在日志、异常文本、Record 和测试 fixture 中。
5. 实测 latency 被记录，而不是假设。
6. 网络测试与普通 495 条离线测试隔离；无 Key 时普通测试仍全部通过。
