10 次真实调用的 content 形态（**不稳定**）：

| # | latency | content 形态 | 顶层键 |
| --- | --- | --- | --- |
| 1 | 10.5 s | ```` ```json ```` 代码围栏 + JSON | `assessment` `confidence(str)` `future_return_distribution` `buy/sell_adverse_selection_probability` `buy/sell_fill_probability` `reasoning` `caveat` `symbol` `venue` |
| 2 | 11.1 s | 裸 JSON | 同上 + `directional_bias` `limitations` `market_state_hash` `probability_sum` `signals` |
| 3–5 | 5–11 s | （latency 采样，未解析） | — |
| 6 | 4.9 s | **纯自然语言**（逐项点评） | —（无 JSON） |
| 7 | 19.0 s | 围栏但**整体不可 JSON 解析** | — |
| 8 | 6.7 s | 纯自然语言 | —（无 JSON） |
| 9 | 5.8 s | 纯自然语言（bullet 分析） | —（无 JSON） |
| 10 | 9.8 s | ```` ```json ```` 围栏 + JSON | `symbol` `venue` `as_of_event_ordinal` `market_view` `future_return_distribution` `buy_adverse_selection` `sell_adverse_selection` `buy_fill_probability` `sell_fill_probability` |

**语义上一致、结构上不一致**：

- 一致（好消息）：五分类 bucket 恰为 `strong_down/down/flat/up/strong_up`；horizon 恰为 5s/15s/30s/60s；`buy_fill_probability` / `sell_fill_probability` 命名一致；
  样本内五分类求和 = 1.000000；模型确实读到了我们的 canonical payload（回复中引用 OFI / microprice / spread bps / book quality，并回显 `market_state_hash`、`as_of_event_ordinal`、`symbol`、`venue`）。
- 不一致（阻断 SC-1）：
  1. content 不是稳定 JSON：会在「纯自然语言 / 围栏 JSON / 裸 JSON」之间随机漂移 → 现有 strict parser 必然 `PARSE_ERROR`。
  2. 分布键名：`future_return_distribution`（我们为 `future_return`）。
  3. 问题键名不稳定：`buy_adverse_selection` ↔ `buy_adverse_selection_probability`（同一次会话内不同调用给出不同命名）。
  4. `confidence` 是**分类字符串**（如 `"low"`），而我们的 `provider_confidence` 是 `float | None`。
  5. 每次调用附带**不同的额外字段**（`reasoning` / `caveat` / `limitations` / `signals` / `assessment` / `market_view` / `directional_bias` / `probability_sum` …），
     而我们的 strict parser 对未知字段是 `INVALID_RESPONSE`（fail closed）。
  6. 输出含自然语言解释，而 P0001.4 明确把自然语言解释排除在我们的契约之外。
  7. latency 量级从旧 typed 接口的 ~270 ms（见 `activation-room-poc/RESULTS-P3.md`）变为 **5–19 s**。

**按提案要求，此处不静默修值、不模糊兼容、不修改 Prediction Runtime 上层**。三条候选路径，需人类决定：

| 选项 | 内容 | 代价 / 风险 |
| --- | --- | --- |
| A. adapter 结构转换 | 在 OpenRouter adapter 内做：去围栏 → 定位 JSON → 键名映射 → 丢未知字段 | 等于把「模型输出」normalize 成契约，会掩盖真实的模型不稳定性；高层仍假设 Jev 是确定性的 structured 端点 |
| B. 升级 question schema | `jev-market-v1` → v2：改为 `future_return_distribution`、允许 `confidence` 为分类、允许/忽略 `reasoning` 等扩展字段；parser 同步放宽 | 是正式的契约变更（提案 §2 允许），但会让「未知字段 fail closed」的保证退化；且无法解决「有时根本不是 JSON」 |
| C. 在请求里补输出契约 | payload/请求内加入明确的输出格式契约（要求 only JSON、固定键名） | 改动请求内容（仍是 schema 内的事），可能显著提高结构化率，但不保证；需要与真实模型反复验证 |
| D. 复核 Jev 的真实形态 | `typesafe/jev-router` 当前路由到 `stealth/space-bunny-alpha`；若生产 Jev 实际仍是 typed `/v1/systemone`（`activation-room-poc` 中可工作的集成：model `jev-1.13`、`answers.<id>.noul`、~270 ms），则应先澄清「Jev」到底指哪一个端点 | 需要人类确认；本会话未擅自调用被声明为废弃的旧接口 |

**Q4 它是否真的提供结构化 answers 契约**

**是。** 记录到的真实响应形状：

```json
{ "id": "gen-dec-...", "model": "typesafe/jev-1.13-20260917", "provider": "TypeSafe",
  "answers": { "<question_id>": { "type": "noul", "noul": 0.81 }, ... },
  "usage": { "input_tokens": 396, "output_tokens": 75, "cost": 1.6632e-05 } }
```

- `questions` 是 **map**，一次请求可放 N 个 typed 问题（旧实现 4 个角色 1 次请求，`requestsPerEvent = 1`）。
- 原语：**Choice / Score / Noul**；`noul` = P(yes)，无 `confidence`；`choice` / `score` 才带 `confidence`。
- 旧实现记录的标定探针：`P(yes)=0.98/0.99`（真）、`0.01`（假）→ 0.5 是原生判界。
- **与 `jev-market-v1` 的形状差异**：typed Jev 返回的是「每个问题一个 typed 答案」，而不是我们定义的
  「五分类收益分布 + 4 个单概率」。若将来要对齐，五分类应对应 **Choice（5 路）**，其余四个概率对应 **Noul**，
  且 `confidence` 只在 Choice/Score 上存在 —— 这属于未来 schema 决策，本次不实施。

**Q5 与 `typesafe/jev-router`（OpenRouter chat completions）的关系**

同一**平台与凭证体系**（OpenRouter，同一 `sk-or-v1` Key），但**不同 API 表面，且测试时解析到不同上游模型**：

| 维度 | 旧 typed（poc，2026-09-21/22） | 本次 P0001.4.1（2026-09-28） |
| --- | --- | --- |
| 路径 | `POST /api/v1/systemone` | `POST /api/v1/chat/completions` |

`jev-router` 的名称暗示它是路由别名，但当前解析结果与 `jev-1.13` 的 TypeSafe typed 行为完全不同；

↔ Real Jev

       │
       ▼

       │
       ▼
  JevTransport
       │ HTTPS
       ▼
    Real Jev
       │
       ▼
 ProviderResponse
       │
       ▼
 existing strict parser

禁止修改上层 Runtime 来迁就真实 API。
如果 API 不匹配，应该修改 adapter。
设计
真实 Transport 只负责：
endpoint
authentication
request serialization
HTTP timeout
response body
HTTP status
transport errors

它不负责：
probability interpretation
TTL
stale response
backoff policy
MarketState
Strategy

这些已经属于上层。
必须记录真实调用 telemetry：
request bytes
HTTP status
response bytes
latency_ms
provider/model
parse outcome

但 API Key 绝不进入日志、PredictionRecord 或 Event Store。
验证场景
至少用若干个真实、已经 warm-up 的 MarketState 请求 Jev，验证：
1. 实际请求 payload 是否被 API 接受。
2. 实际响应能否被现有 strict parser 无修改解析。
3. 实际 model/provider 字段如何返回。
4. HTTP 4xx / 5xx 如何表现。
5. timeout 如何表现。
6. 响应 latency 的实际分布数量级。
7. Jev 是否存在 schema 外字段。
8. probabilities 是否确实满足当前互斥和求和契约。
尤其第 8 条不能靠猜。
如果 Jev 返回的实际上不是我们定义的严格五分类分布，就必须现在修订 jev-market-v1，而不是 parser 强行修值。
边界
包含
- 一个真实 Jev HTTP transport
- API key 从环境/运行配置注入
- 网络 timeout
- HTTP error mapping
- 真实调用 smoke/integration test
- response contract 验证
- latency telemetry
- 可选人工执行的 live test
不包含（关键）
- 不进入 Strategy
- 不下单
- 不实现 Accounting
- 不实现 Risk
- 不做性能优化
- 不做连接池框架
- 不做多 provider
- 不做 retry storm
- 不保存 API Key
- 不因为真实响应不符合预期就静默 normalize
- 不改变 P0001.1–P0001.3
成功标准
1. 至少一组真实 warm MarketState 能完成：
   MarketState → Jev → PredictionRecord。
2. 真实 Jev 响应无需业务层特殊分支即可进入现有 Parser；若不能，必须明确报告契约差异。
3. 非 2xx、timeout、非法 body 都能映射为既有 failure type，不产生假 Prediction。
4. API Key 不出现在日志、异常文本、Record 和测试 fixture 中。
5. 实测 latency 被记录，而不是假设。
6. 网络测试与普通 495 条离线测试隔离；无 Key 时普通测试仍全部通过。
