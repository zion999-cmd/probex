## 0. 本阶段的固定契约（供审查）

| 项目 | 取值 / 规则 |
| --- | --- |
| `Order` | **不可变快照**（tracker 在每次转换时替换）；字段按提案；`OrderProposal` 不获得任何生命周期字段 |
| `OrderType` | 第一版只有 `LIMIT`（`post_only` 是 LIMIT 的属性）；MARKET/STOP 属后续阶段 |
| `OrderStatus` | 九态固定；终态 = FILLED / CANCELED / FAILED / EXPIRED；**LOST 不是事实终态**，可被 reconciliation 恢复 |
| 视图 | `active` = PENDING_CREATE / OPEN / PARTIALLY_FILLED / PENDING_CANCEL；`recent_terminal` = 四个终态；`lost` = LOST |
| `ExecutionEvent` | 六类：OrderAccepted / OrderRejected / OrderCanceled / OrderExpired / FillReceived / OrderStatusUpdate |
| 记账路径 | `ExecutionEvent → OrderTracker → canonical Fill → AccountingCore`；**ExecutionEngine 不直接改 Accounting** |
| Partial fill | 每一笔成交立即产生 canonical `Fill` 并入账；禁止「等完全成交再记账」 |
| 双层去重 | execution 层按 `(execution_id)` 与 `(trade_id)` 去重；accounting 的 `FillLedger` 保留第二道防线 |
| Cancel race | 只有 `OrderCanceled` 才进 CANCELED；PENDING_CANCEL 期间 Fill 合法（可能 → PARTIALLY_FILLED / FILLED） |
| Late fill | 终态后到达、且**成交时间 ≤ 终态时间**的 fill 必须记账；超出窗口 → 拒绝（fail closed）。终态与成交事实分离：`Order.final_executed_quantity` |
| Cancel-before-replace | `replace` 必须等旧单进入**已确认终态**；否则拒绝（`REPLACE_OLD_NOT_TERMINAL`） |
| `client_order_id` | `probex-{session}-{sequence:06d}`：唯一、可排序、restart-safe（可从日志定位） |
| Reconciliation | 契约覆盖四类情形：本地 active/外部不存在 → LOST；本地 LOST/外部存在 → 恢复；本地未知/外部存在 → adopt；本地 filled 落后 → 补记外部 fill。返回 `ReconciliationReport(actions, converged)` |
| PaperBroker | 由测试**显式驱动**（submit / cancel / fill / late fill / lost / reconcile）；**不做盘口撮合**（属 P0001.8） |
| Post-only | 盘口已知且穿越（buy ≥ best_ask / sell ≤ best_bid）→ `REJECT_POST_ONLY`；盘口未知 → 跳过该检查（文档化） |
| Risk 紧邻 submit | `OrderProposal → 新鲜 RiskSnapshot（含 open_order_exposure）→ RiskGate → ALLOW → submit`；REJECT 时**不创建外部订单**，只产出 `ExecutionRejected` |
| Pending exposure | active 订单未成交部分按**订单自身价格**（最坏情形）计入 `open_order_exposure`（§15） |
| Kill switch 三态 | `NORMAL` / `REDUCE_ONLY`（只放行真正降暴露）/ `HALT_ALL`（禁止 submit，**仍允许 cancel**）；P0001.5 的 `kill_switch: bool` 保持兼容（`True` → HALT_ALL） |
| 适配器接口 | 第一版**同步**；异步/网络适配器（P0001.9）作为新契约决策引入（`context/decisions.md` D-021） |
| Restart / recovery | 只做逻辑恢复：load local recent orders + broker open orders + recent fills → reconcile；**不做数据库持久化** |

## 2.1 实施结果（2026-09-28）

**交付**

- `execution/types.py`：`Order`（不可变快照，含终态成交量 `final_executed_quantity`）、`OrderStatus` 九态 + 转换表、
  `ExternalOrder` / `ExternalFill`（reconciliation 输入）、执行领域错误。
- `execution/events.py`：六类 `ExecutionEvent`（OrderAccepted / OrderRejected / OrderCanceled / OrderExpired /
  FillReceived / OrderStatusUpdate）。
- `execution/tracker.py`：`OrderTracker`（本地状态权威；`(symbol, execution_id)` 与 `(symbol, trade_id)` 双键去重；
  cancel-pending / LOST / late fill / active|recent_terminal|lost 视图 / pending exposure）。
- `execution/adapters/{base,paper}.py`：`ExecutionAdapter` 契约 + `PaperBroker`（可控 accept/reject/defer-cancel/fill/
  duplicate/late/status-update/drop-from-external，含 post-only 基本 venue rule）。
- `execution/reconciliation.py`：`reconcile(...)` → `ReconciliationReport(actions, converged)`，覆盖 §11 的四类情形。
- `execution/manager.py`：`OrderManager`（submit / cancel / replace，cancel-before-replace 强制等终态）。
- `execution/engine.py`：`ExecutionEngine`（新鲜快照 + RiskGate → submit；事件 → tracker → canonical Fill → Accounting；
  `ExecutionRejected` telemetry；HALT_ALL 禁 submit 但放行 cancel）。
- `risk/`：新增 **kill switch 三态**（`KillSwitchMode.NORMAL / REDUCE_ONLY / HALT_ALL`），P0001.5 的 bool 语义保持兼容。
- 测试：`tests/unit/{test_order,test_order_tracker,test_execution_events,test_paper_broker,test_execution_isolation}.py`、
  `tests/integration/{test_paper_execution,test_execution_accounting,test_execution_risk}.py`、
  `tests/fault/{test_cancel_race,test_late_fill,test_duplicate_execution,test_lost_order,test_reconciliation}.py`、
  `tests/replay/test_execution_determinism.py`，以及 `tests/execution_support.py`（可控执行栈）—— 新增 117 条。

**人类对 P0001.5 未决点的裁决（本阶段生效）**

1. 空仓无 mark 不允许新增仓位 → **保留**（fail-closed）。
2. 反手按 INCREASING → **保留**（Policy 可自行拆成「先平后开」，Risk 不猜意图）。
3. Kill switch 拆成 `HALT_ALL` / `REDUCE_ONLY` → **本阶段实现**（HALT_ALL 不禁止 cancel）。

**关键行为自检**

| 场景 | 结果 |
| --- | --- |
| partial fill 0.2 → 0.3 → 0.5 | 每笔立即入账；订单状态 PARTIALLY_FILLED → FILLED；Accounting 累计 1.0 |
| 重复 execution_id / trade_id 投递 | `fill_duplicate`；订单成交量与 Accounting 均不变（两层去重） |
| 已发撤单（PENDING_CANCEL）期间成交 | 成交正常入账，状态回到 PARTIALLY_FILLED；只有确认才 CANCELED |
| 撤单确认后的 late fill | `late_fill_applied`：终态保持 CANCELED，`executed_quantity` 更新并记账 |
| 超出合法性窗口的 fill | `fill_rejected`（fail closed，不入账） |
| replace（旧单未确认终态） | 只发撤单请求，**不创建新单**；确认终态后才下新单 |
| pending exposure | active 未成交部分按订单价格计入；第二单因此被 `OPEN_ORDER_EXPOSURE_LIMIT` 拒绝 |
| HALT_ALL | submit 被拒（`KILL_SWITCH`），cancel 仍可执行 |
| LOST | 非终态；reconciliation 可恢复为外部真实状态；LOST 不计入 pending exposure |
| 重启收敛 | 陈旧本地快照 + 外部 open orders/fills → 补齐成交与状态；第二次 reconcile `converged = True` |

**有意为之的行为（供审查）**

1. `ExecutionEngine` 在 submit 前**总是**取新鲜 `RiskSnapshot`（含 manager 的 pending exposure）；
2. `adapter` 接口为同步（第一版）；异步/网络适配器留待新决策（D-021）；
3. `PaperBroker` 不做盘口撮合（属 P0001.8）；post-only 只在盘口已知时校验，未知则跳过（文档化）；
4. reconciliation 对「本地终态 vs 外部仍报活」只报 `STATUS_CONFLICT`，不擅自回退终态；
5. 数量校正 / adopt 需要外部给出 `avg_fill_price`，否则 fail closed。

## 3. 原 P0001.6 提案文本（原样保留）

P0001.6：Order Lifecycle + Paper Execution
状态：已提议
日期：2026-09-28
依赖：P0001.1–P0001.5
目标
建立完整的本地订单状态机、成交事件处理、取消/替换与 Paper Execution。
这一阶段解决：
我提出一个订单以后，从“准备发送”到“完全结束”，系统如何始终知道它现在是什么状态？

先用 Paper Broker 验证完整订单生命周期。
本阶段仍不连接 Binance 私有下单 API。
背景
现在已有：
MarketState
Prediction
Accounting
Risk

但还缺中间最关键的一层：
OrderProposal
     ↓
???
     ↓
Fill

如果这一层做错，最典型的问题不是“订单没成交”，而是：
重复下单
漏记 partial fill
cancel 后 late fill
撤单未确认就重新挂
重启后不知道交易所还有没有单

Hummingbot 研究中最值得吸收的，正是这些订单生命周期语义。
架构
OrderProposal
      │
      ▼
   RiskGate
      │ ALLOW
      ▼
ExecutionEngine
      │
      ▼
OrderManager
      │
      ├── submit
      ├── cancel
      └── replace
      │
      ▼
ExecutionAdapter
      │
      └── PaperBroker  ← 本阶段
              │
              ▼
       ExecutionEvent
              │
              ▼
        OrderTracker
              │
              ├── Order state
              └── Fill
                     │
                     ▼
              AccountingCore

核心原则：
OrderTracker 是本地订单状态权威；ExecutionAdapter 提供外部事实；二者通过事件收敛。

设计
1. Order 与 OrderProposal 分开
已有：
OrderProposal

只是意图。
真正订单新增：
Order
- client_order_id
- exchange_order_id
- venue
- symbol
- side
- type
- price
- quantity
- filled_quantity
- avg_fill_price
- reduce_only
- post_only
- status
- created_at
- updated_at

OrderProposal 不允许偷偷获得生命周期字段。
2. OrderStatus
第一版固定：
PENDING_CREATE
OPEN
PARTIALLY_FILLED
PENDING_CANCEL
FILLED
CANCELED
FAILED
EXPIRED
LOST

终态：
FILLED
CANCELED
FAILED
EXPIRED

LOST 不是事实终态，而是：
本地无法确认外部状态。

因此 LOST 后仍允许 reconciliation 恢复为真实状态。
3. ExecutionEvent
所有 Adapter 统一输出：
OrderAccepted
OrderRejected
OrderCanceled
OrderExpired
FillReceived
OrderStatusUpdate

ExecutionEngine 不直接修改 Accounting。
只能：
ExecutionEvent
→ OrderTracker
→ canonical Fill
→ AccountingCore

4. Partial Fill 是一级行为
必须支持：
qty = 1.0

fill 0.2
→ PARTIALLY_FILLED

fill 0.3
→ PARTIALLY_FILLED

fill 0.5
→ FILLED

每个 Fill 都立即进入 Accounting。
禁止等订单完全成交以后一次性记账。
5. Fill 去重
Execution 层需要自己的：
trade_id / execution_id

去重。
重复事件：
不能增加 order.filled_quantity
不能再次生成 canonical Fill
不能再次影响 Accounting

Accounting 的 FillLedger 仍保留第二道去重防线。
即：
Execution dedupe
+
Accounting dedupe

两层不是重复，而是防御纵深。
6. Cancel Race
必须明确允许：
submit cancel
        │
        ├── Fill arrives
        │
        └── Cancel confirmed

甚至：
PENDING_CANCEL
→ PARTIALLY_FILLED
→ FILLED

都是合法路径。
不能认为：
发送 Cancel == 已撤单

只有明确 OrderCanceled 才进入 CANCELED。
7. Late Fill
订单进入 CANCELED 后，仍可能收到交易所稍晚到达的已发生 Fill。
因此 tracker 需要接受：
late Fill

如果该 Fill 的交易时间证明发生在订单有效期内：
必须记账

但不能把已经 CANCELED 的订单简单重新变回 OPEN。
需要保存：
terminal status
+
final executed quantity

终态和成交事实是两个维度。
8. Cancel-before-replace
正式规定：
old order
   ↓
request cancel
   ↓
wait confirmed terminal
   ↓
new order

禁止：
cancel sent
+
立即 new order

否则 Maker 系统很容易瞬间拥有双份 exposure。
9. client_order_id
由 Probex 本地产生。
至少需要：
unique
sortable
restart-safe

不要只用：
timestamp

建议语义：
probex-{session}-{sequence}

具体编码交给实现，但必须能够从日志定位订单。
10. Active / Cached / Lost Views
吸收 Hummingbot 思路，但不照搬具体实现。
OrderTracker 提供三个逻辑视图：
active
recent_terminal
lost

目的：
- active：当前可能产生 exposure；
- recent_terminal：等待 late fill / audit；
- lost：需要 reconciliation。
不是要求必须用三个 dict。
11. Reconciliation Contract
本阶段建立接口，但 PaperBroker 实现完整：
reconcile(
  local_orders,
  external_open_orders,
  external_recent_fills
)

目标：
local ↔ broker facts

最终收敛。
至少覆盖：
本地 OPEN，外部不存在
本地 LOST，外部 OPEN
本地未知订单，外部存在
本地 filled_qty 落后

Paper 环境可以完全模拟这些故障。
12. PaperBroker
Paper 不是：
submit → 立即成交

必须是可控的 ExecutionAdapter。
第一版支持：
submit
accept/reject
cancel
partial fill
full fill
late fill
lost order
reconciliation

测试可以显式驱动：
broker.fill(order_id, qty, price)
broker.cancel_ack(...)

不要提前做真实盘口撮合。
P0001.8 才做 Event-level Fill Simulation。
13. Post-only
PaperBroker 必须支持：
post_only

但本阶段只验证基本规则：
如果订单提交瞬间：
buy price >= best ask
sell price <= best bid

则：
REJECT_POST_ONLY

注意：
这只是 Paper 的基本 venue rule 模拟。
以后 Binance 的实际 GTX/LIMIT_MAKER 返回才是最终事实。
14. Execution 与 Risk 的关系
执行顺序必须是：
OrderProposal
→ fresh RiskSnapshot
→ RiskGate
→ ALLOW
→ submit

不能：
提前 risk check
过几秒
再直接 submit

Risk check 必须靠近 submit。
如果：
REJECT

Order 都不应该被创建成外部订单。
可以产生：
ExecutionRejected

用于 telemetry。
15. Pending Exposure
订单一旦 OPEN/PARTIALLY_FILLED：
未成交部分必须进入：
open_order_exposure

供下一次 RiskSnapshot 使用。
否则：
连续挂 10 个单
Position 仍然 0

会绕过 Position Limit。
这是 P0001.6 与 P0001.5 的关键连接点。
16. Kill Switch 语义正式拆分
本阶段定义：
NORMAL
REDUCE_ONLY
HALT_ALL

含义：
NORMAL
→ 正常 RiskGate

REDUCE_ONLY
→ 只允许真正降低当前 exposure 的 proposal

HALT_ALL
→ 禁止新 submit
→ 仍允许 cancel 已存在订单

这里特别注意：
HALT_ALL 不能禁止 Cancel。

否则 Kill Switch 反而会把已有挂单锁在市场上。
P0001.5 原来的 bool kill switch 保持兼容或迁移，但最终 Risk contract 应走这个三态语义。
17. Restart / Recovery
本阶段只做逻辑恢复模型。
进程重新启动时：
load local recent orders
+
query broker open orders
+
query recent fills
+
reconcile

PaperBroker 必须测试这个流程。
不实现正式数据库持久化。
可以用测试 fixture / in-memory snapshot 驱动。
