## 2. Binance private API surface 审计（只读，无凭据）

**证据 1：WS API 面真实存在（无凭据探测，仅用明显无效的 key）**

```text
连接 wss://ws-fapi.binance.com/ws-fapi/v1  → handshake OK
发送 {"id":1,"method":"userDataStream.start","params":{"apiKey":"INVALID-KEY-FOR-CONTRACT-AUDIT"}}
收到 {"id":1,"status":401,"error":{"code":-2014,"msg":"API-key format invalid."},
      "rateLimits":[{"rateLimitType":"REQUEST_WEIGHT","interval":"MINUTE","intervalNum":1,"limit":2400,"count":6}]}
```

⇒ endpoint 与 `userDataStream.*` 方法名确认存在（无效 key 被拒 ⇒ 未接触任何账户数据）。

**证据 2：private tier URL 形态 —— 与 ccxt 一致（独立佐证）**

```text
ccxt.pro.binanceusdm().get_private_ws_url('future', key) → wss://fstream.binance.com/private/ws?listenKey=<key>
ccxt.pro.binanceusdm().get_ws_url('future','public')     → wss://fstream.binance.com/public/ws
ccxt.pro.binanceusdm().get_ws_url('future','market')     → wss://fstream.binance.com/market/ws
```

⇒ 当前 Probex 的 `/private/ws?listenKey=` 与成熟库一致；**没有** `events=` 参数。

**证据 3：`events=` 不是连接准入条件（但不等于投递证明）**

无效 listenKey 下三种 URL 的握手都成功且都**不投递**任何消息（无 close、无错误帧）：

| URL | handshake | 收到的消息 |
| --- | --- | --- |
| `/private/ws?listenKey=<invalid>` | OK | 无 |
| `/private/ws?listenKey=<invalid>&events=ORDER_TRADE_UPDATE` | OK | 无 |
| 旧入口 `/ws/<invalid>`（2026-04-23 之后应退役） | OK | 无 |

⇒ 无法用无效 key 区分「路径正确但未授权」与「路径已退役」（Binance 边缘对三者都接受连接）。
**明确结论：private tier 是否真正投递必须用有效 listenKey 验证**（属 P0001.9.2 的真实凭据 smoke）；本轮不猜、不改 URL。

**证据 4：两个 surface 的关系**

- REST listenKey 流：`POST/PUT/DELETE /fapi/v1/listenKey` + `/private/ws?listenKey=`（本阶段实现，ccxt 默认路径）；
- WS API 流：`wss://ws-fapi.binance.com/ws-fapi/v1` + `userDataStream.start/ping/stop`（ccxt 亦实现
  `userDataStream.subscribe.signature` / `userDataStream.subscribe.listenToken`）。
- 两者是**同一账户体系的两种私有数据入口**；本阶段保留 REST listenKey 路径（已被代码与 ccxt 双重印证），
  是否切换到 WS API 流（免 listenKey 续期）留作候选，不在本阶段改。

**raw payload 保留（提案重点项）**

  **`order['info']` 与 `trade['info']` 逐字段等于原始 payload** ✓（`order_info_is_raw_payload: true`、

- ⇒ Probex 需要的 `x`（execution type）、`l`/`z`/`L`/`ap`、`n`/`N`、`R`、`m`、`E`/`T` 都能从 `info` 取到；

**归一化缺口 / 需真实响应验证**

| 项 | 结果 |
| --- | --- |

**§6 continuity 结论（有代码证据）**

- ccxt 对 **orderbook** 有序号处理（`ccxt/pro/binance.py` 中 `U <= nonce <= u` **或 `pu == nonce`**
  —— 这也独立佐证了 P0001.9.1.1 的 `pu` 判据修正 ✓）；但对 **user data / order 事件没有任何序号或连续性跟踪**。
- `watch_orders` 在断线后重连并重订阅（listenKey 续期由库内部完成），**不提供“事件是否连续”的证据**。
- ⇒ **CCXT 自动 reconnect ≠ Probex 状态连续**；无论选哪种 transport，`continuity_assumed`
  与 P0001.9.3 reconciliation **都不能省**（SC-8 明确结论）。
