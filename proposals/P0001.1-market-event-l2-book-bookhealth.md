## 1. P0001.1 实现契约

### 1.1 目标

把「市场发生了什么」做正确的最小闭合单元：统一 `MarketEvent` 边界 + 可信 L2 盘口 + 盘口可信度状态机（BookHealth）。

### 1.2 Included

- 统一 `MarketEvent`（`venue` / `symbol` / `event_type` / `exchange_ts` / `receive_ts` / `process_ts` / `sequence` / `payload`）
- `BookSnapshot` / `BookDelta` 两类事件载荷
- Binance USDⓈ-M 深度报文归一化（REST 深度快照 + WS `depthUpdate` 增量），含不可信边界校验
- `OrderBook`：快照应用、增量应用、档位增 / 删 / 改、best bid / best ask、top-N depth
- sequence gap 检测
- `BookHealth` 四态状态机：`AWAITING_SNAPSHOT` / `HEALTHY` / `STALE` / `RESYNCING`
- 盘口不健康时关闭可交易门（`is_tradeable == False`）
- gap 后的缓冲与恢复闭环：进入 `STALE` → resync 触发信号 → 新 snapshot → 重放缓冲 delta → 恢复 `HEALTHY`
- 覆盖上述能力的 unit / integration / replay / fault 测试

### 1.3 NOT Included

- Live / REST / WS 传输实现、网络连接与重订阅动作（本阶段只产出归一化层与 resync 触发信号，不建立连接）
- Event Store、确定性 Replay 引擎（P0001.2）
- Feature / MarketState（P0001.3）
- Jev / Prediction Runtime（P0001.4）
- Accounting / Risk（P0001.5）
- Paper Execution / Order Lifecycle（P0001.6）
- Market Making（P0001.7）
- Fill Simulation（P0001.8）
- Binance 实盘下单与账户（P0001.9）
- Product API / UI / Reports（P0001.10）
- `Trade` / `Ticker` / `Bar` / `Funding` / `MarkPrice` 的载荷类型与归一化（仅保留在 `EventType` 词表中）
- 跨交易所、股票、期权、DEX、套利
- 微秒级 HFT、真实 queue position 还原
- 新增第三方依赖（含 Web Framework、数据库、消息队列、测试框架）
- 交易相关任何能力：下单、撤单、仓位、盈亏、风控

### 1.4 Success Criteria

- **SC-1 统一 MarketEvent 边界**：Binance USDⓈ-M 深度快照与 `depthUpdate` 增量报文可经归一化层无歧义转换为统一 `MarketEvent`（8 个字段齐备且语义正确）；结构非法或语义非法的报文在边界被拒绝，不进入核心。
- **SC-2 L2 盘口正确性**：对 snapshot + 连续 diff 序列，`OrderBook` 的 bid / ask 档位与交易所语义一致（新增档位、更新数量、`qty == 0` 删除档位、best bid / best ask 与 top-N depth 正确）。
- **SC-3 sequence gap → STALE**：人为跳过一段增量造成 sequence gap 后，`BookHealth` 自动进入 `STALE`，且可交易门关闭（`is_tradeable == False`），同时产生 resync 触发信号。
- **SC-4 恢复闭环**：gap 后 resync → 新 snapshot → 重放 gap 期间缓冲的 delta → 恢复 `HEALTHY` 且可交易门重新打开；最终盘口与无 gap 的参考路径盘口完全一致。
- **SC-5 乱序 / 重复 / 过期容错**：重复 sequence 与早于当前 sequence 的增量被幂等忽略，既不改动盘口也不被误判为 gap；gap 期间到达的增量被缓冲且不污染盘口。
- **SC-6 确定性**：同一份事件序列两次重放，得到完全相同的最终盘口与健康状态。

## 2. 原 P0001 总架构文本（背景，非本次实现范围）

## 目标

构建一个真正可长期运行、研究、回放、模拟和实盘的量化工程，而不是 Jev Demo。

系统吸收三类成熟设计：

```text
Freqtrade
→ Strategy / Backtest / Trade / Accounting / PnL

Hummingbot
→ Live Execution / Order Lifecycle / Market Making

lob-engine 研究所得
→ Event-domain Market Data / L2 Book / Sequence / Microstructure

Jev
→ 低延迟 Probability / Score
```

核心原则：

> **Jev 是热路径中的概率计算器，不是交易 Agent。**

它只把当前已知市场状态：

```text
X(t)
```

快速映射为：

```text
P(Event | X(t))
Score
Confidence
```

解释、总结、分析全部退出交易热路径。

---

## 背景

Freqtrade 给出了成熟的 candle backtest、Trade/Wallet/PnL 模型，并且特别强调信号时点、防未来函数和订单驱动账本。:chatgpt-content-reference{index="0"}

Hummingbot 补充了 Freqtrade 最薄弱的一层：实时订单生命周期、partial fill、cancel race、lost order、reconciliation 和 Market Making。

第三份研究反而证明一个重要事实：我们选的 lob-engine **不能作为生产级微观结构框架直接复刻**。它没有真正的 replay、OFI、microprice、trade flow，sequence gap 也只有检测没有恢复。:chatgpt-content-reference{index="1"}

因此 Market Data / L2 部分要吸收它正确的思想，但由我们按生产级标准重新设计。

# 设计

## 1. 最重要的统一对象：MarketEvent

不能让：

```text
WebSocket行情
CSV
Replay
Paper
Live
```

各走一套业务链。

进入核心以后统一成：

```text
MarketEvent

- venue
- symbol
- event_type
- exchange_ts
- receive_ts
- process_ts
- sequence
- payload
```

事件类型至少：

```text
BookSnapshot
BookDelta
Trade
Ticker
Bar
Funding
MarkPrice
```

**Live 和 Replay 从这个边界以后共用同一套 Market Core。**

---

## 2. 时间模型：不是一个 Clock

这里吸收 Hummingbot，但不照抄它的 1Hz / 0.5s 参数。

系统存在三种时间：

```text
Market Event Time
Scheduler Time
Replay Logical Time
```

统一抽象为：

```text
Clock
├─ LiveClock
└─ ReplayClock
```

实时运行：

```text
WS event ───────────────▶ Market pipeline

Scheduler ──────────────▶ maintenance / strategy timers /
                          reconciliation / risk check
```

两者不能互相阻塞。

Replay 时换成 `ReplayClock`，下游代码不需要知道现在是历史还是实时。

---

## 3. Candle Backtest 与 Event Replay 不强行合并

这一点我要直接定死。

```text
BarBacktestEngine
≠
EventReplayEngine
```

因为 OHLCV 无法告诉我们：

- 盘口队列；
- partial fill 顺序；
- cancel race；
- maker 是否真的成交；
- 一个 candle 内到底先到 high 还是 low。

Freqtrade 的 candle 撮合适合普通策略，但不能拿它验证秒级 Maker。

因此：

```text
Bar Backtest
→ 趋势 / 因子 / 普通策略研究

Event Replay
→ Maker / Microstructure / Jev 短周期研究
```

两者共享：

```text
Strategy
Risk
Accounting
Report
```

但**不共享 Fill Simulator**。

这是非常重要的边界。

## 4. Market Book 必须有可信度状态

lob-engine 最大的问题正好成为我们的设计要求。

不能只有：

```text
book initialized = true
```

必须有：

```text
BookHealth

AWAITING_SNAPSHOT
HEALTHY
STALE
RESYNCING
```

规则：

```text
Snapshot
   ↓
buffer/reconcile Delta
   ↓
HEALTHY

sequence gap
   ↓
STALE
   ↓
停止输出交易可用 Feature
   ↓
resubscribe
   ↓
snapshot
   ↓
replay buffered delta
   ↓
HEALTHY
```

**Book 不健康时禁止 Jev 预测和新建风险仓位。**

第三份报告证明 lob-engine 目前恰恰缺这一闭环。:chatgpt-content-reference{index="2"}

## 5. Market State 与 Feature

不是堆几十个技术指标。

第一阶段只构建与短周期交易直接有关的状态：

```text
Price
├─ bid / ask
├─ mid
├─ spread
├─ microprice
└─ returns

Depth
├─ L1 size
├─ top-N depth
├─ imbalance
└─ VAMP

Flow
├─ event-level OFI
├─ buy/sell aggressive volume
├─ CVD
├─ trade intensity
└─ event intensity

Volatility
└─ multi-horizon realized volatility
```

关键变化是：

### V3

```text
每秒取一次 snapshot
↓
比较 S(t-1) 与 S(t)
↓
近似 OFI
```

### 新系统

```text
每条 BookDelta
↓
old state → new state
↓
event OFI
↓
rolling aggregation
```

第三份报告已经指出两者差别是**信息域不同，而不是公式精度不同**。:chatgpt-content-reference{index="3"}

# 6. Jev Provider

Jev 必须成为普通 Provider：

```text
PredictionProvider

├─ JevProvider
├─ RuleProvider
└─ future: OtherModelProvider
```

输入不是任意 Prompt，而是版本化的：

```text
PredictionRequest

market_state
feature_schema_version
question_schema_version
horizon
as_of
```

输出：

```text
Prediction

event probabilities
scores
confidence
model
latency
created_at
expires_at
input_hash
```

关键纪律：

> **Prediction 是 immutable evidence。**

以后回测不能重新问一次 `jev-latest` 然后假装是同一个实验。

必须保存：

```text
input
model/version
question schema
raw output
normalized output
timestamp
```

# 7. Jev 不能阻塞 Market Pipeline

热路径分开：

```text
Market Feed
   │
   ├────────▶ Book / Feature continuously update
   │
   └────────▶ immutable MarketState snapshot
                    │
                    ▼
                   Jev
                    │
                    ▼
               Prediction
```

Jev 请求期间：

**行情继续更新、订单回报继续处理、Risk 继续工作。**

收到结果以后先检查：

```text
TTL
state age
book health
position revision
strategy revision
```

过期就丢掉。

不能出现：

```text
等 Jev
↓
整个交易循环停住
```

# 8. Strategy 与 Policy 分开

这是后面扩展性很关键的一刀。

```text
Strategy
```

回答：

> 市场现在是什么状态？我希望做什么？

输出：

```text
Intent
```

例如：

```text
LongBias
ReduceShort
QuoteBothSides
Hold
```

而：

```text
Policy
```

回答：

> 在当前风险、库存和交易规则下，具体应该挂什么订单？

输出：

```text
OrderProposal / QuotePlan
```

Jev 属于 Strategy 的信息源，**不是 Execution。**

# 10. Accounting：Fill 才是账本真相

这里不完全照搬 Freqtrade。

```text
Order
  ↓

  ↓
Position
  ↓
Realized PnL
  ↓
Balance

Position + Mark Price
  ↓
Unrealized PnL

Equity
```

明确区分：

```text
Balance ≠ Equity
```

```text

leverage
margin

```

# 11. Risk 是独立层

不能藏在 Strategy 里。

每个 `OrderProposal` 必须经过：

```text
RiskGate
```

最少包括：

```text
Market data health

Open-order exposure
Available balance

Drawdown limit

Liquidation-distance limit
```

任何模型——包括 Jev——都不能绕过 Risk。

# 技术路线

第一阶段我建议 **Python 3.12 + asyncio** 作为主工程。

原因不是 Python 最快，而是：

不要因为 lob-engine 写 C++ 就提前引入 C++/Rust。

# 一个必须提前承认的限制

**L2 数据不能精确还原自己的真实排队位置。**

所以 Event Replay 的 Maker fill：

```text
不是历史事实
```

而是：

```text
Fill Model Estimate
```

必须显式标记模型，例如：

```text
touch
trade-through
queue-estimate
```

绝不能把模拟成交包装成真实成交。

这是以后最容易产生虚假收益的地方之一。

# 开发阶段

总架构不要一次全部交给 Pi。

按子提案逐步验证：

```text
P0001.1  Market Event + L2 Book + BookHealth
              ↓
P0001.2  Event Store + Deterministic Replay
              ↓
P0001.3  Feature / MarketState
              ↓
P0001.4  Jev Prediction Runtime
              ↓
P0001.5  Accounting + Risk
              ↓
P0001.6  Paper Execution + Order Lifecycle
              ↓
P0001.7  Market Making
              ↓
P0001.8  Event-level Fill Simulation
              ↓
P0001.9  Binance Live
              ↓
P0001.10 Product API / UI / Reports
```

其中前三个阶段**完全不碰交易**。

先把：

```text
市场发生了什么
```

做正确。

再研究：

```text
根据这些信息应该做什么
```

最后才是：

```text
真的下单
```

# 成功标准

1. 同一份 MarketEvent 两次 Replay，MarketState、Feature、Prediction Record 和策略决策可重复。

2. 人工制造 sequence gap 后，Book 自动进入 `STALE`，停止输出可交易状态；重新 snapshot 后恢复 `HEALTHY`。

3. 同一个 Strategy 可以不修改业务代码运行于：

```text
REPLAY / PAPER / LIVE
```

4. Jev 超时、失败、返回过期结果时不会阻塞行情、订单跟踪或风险控制。

5. partial fill、late fill、cancel race、duplicate trade、lost order、程序重启均有自动化测试。

6. 任意时刻满足账本不变量：

```text
fills
→ position
→ realized PnL
→ balance
```

可以重新计算并得到相同结果。

7. Equity 明确包含未实现盈亏，与 Balance 分开。

8. Maker Replay 明确记录使用的 Fill Model，不允许把估计成交当真实成交。

9. Paper 连续运行至少 24 小时，Book、OrderTracker、Position 与交易所公共状态无不可解释漂移。

10. Live 模式只有通过独立 RiskGate 才能真正发送订单。
