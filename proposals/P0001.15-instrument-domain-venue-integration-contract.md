## 人类批准裁决（2026-10-03，本会话；对本文件具有约束力）

1. **ReferencePrice 必须补完整工程闭环**：PERPETUAL 风险路径只接受正式 **MARK** 语义（Binance `markPriceUpdate` 是当前
   正式 MARK 来源）；`MID` / `INDEX` / `LAST` 可进入 vocabulary 但**不得静默替代** MARK；无 MARK ⇒ `UNKNOWN` + fail-closed。
   **但不接受**"PAPER fixture 没有 mark ⇒ PAPER 永远不能跑完整执行链"作为最终状态（工程闭环必须完整，业务覆盖可后补）：
   - **A**：`ReferencePriceProvider` 必须可由正式 `MarketEvent.MARK_PRICE` 驱动；
   - **B**：REPLAY/PAPER 测试数据必须增加/使用**明确包含 `MARK_PRICE` event** 的 fixture（工程级 E2E）；
   - **C**：fixture 里的 MARK_PRICE 是**明确测试市场事实**，不允许把 `LAST`/`MID` 临时转换成 MARK；
   - **D**：同时保留**不含 MARK_PRICE** 的 fixture，验证 `UNKNOWN → Risk fail-closed`；
   - **E**：不得因测试 fixture 有 MARK_PRICE 就声称真实 Binance/PAPER 已获得实时 mark；真实运行仍按真实 source 状态报告。
   - 最终必须**同时**证明：known MARK → ReferencePrice known → Risk 可继续 → PAPER engineering execution chain 完整跑通；
     以及 missing MARK → UNKNOWN → fail closed。不能只验证 UNKNOWN 路径。
2. **Decision ↔ Order 不得由 `RuntimeDecisionLoop` 拥有映射**：correlation metadata（`decision_id` / `prediction_id` /
   `market_state_id|hash` / `instrument_id` / `venue_id`）必须随 `MakerDecision → OrderProposal` 进入**提交边界**，
   `client_order_id` 产生后与这些 id 一起进入 **canonical order record**（`OrderManager` / `OrderTracker`）；
   `decision_id` 随 order lifecycle 持久存在；fill / execution_event 可沿 `order_id` / `client_order_id` 回溯 decision；
   Product **不**维护额外 side mapping；`RuntimeDecisionLoop` **不**维护 `decision_id → client_order_id` 临时映射作为事实来源；
   重启后关联仍成立（不得依赖 runtime 内存）。允许对该契约做**最小 additive** 扩展。验收必须含
   `Decision → Order`、`Order → Decision`、`Fill → Order → Decision`，并验证 restart / durable read 后仍可关联
   （订单事实本身非 durable 的 mode 至少不得因 runtime mapping 丢失而变差）。
3. **Instrument semantics 只描述事实**：不进入 Risk 数学；不修改 `RiskGate` / Readiness 规则；venue 名称不得决定
   product semantics。
4. **Connector 边界**：`MarketDataConnector` = 公开行情/规则/reference-price source/health；
   `PrivateExecutionConnector` = account/position/order/fill/private stream/reconciliation/health；二者 **health 独立**。
   **不得**做一个万能 `VenueGateway` 把职责重新揉在一起。
5. **范围**：只实现 BTCUSDT / CRYPTO / PERPETUAL / PAPER + 现有 Binance adapter；EQUITY/FUTURE 只建 vocabulary/capability
   contract。禁止股票/期货/OKX/IBKR/CTP/multi-venue/OrderRouter/SOR/跨交易所套利。
6. **UI 是正式验收项**（真实浏览器）：Monitor（instrument/asset class/product type/venue/reference-price source）、
   Market（market connector + data source + MARK 状态）、Activity（instrument_id + venue_id + Decision→Order 因果链）、
   Order Detail（decision_id / client_order_id / venue_order_id / connector）、System（两个 connector health **分开**显示）、
   Assistant（Spot vs Perpetual、MARK 来源、为何 MARK UNKNOWN 导致 fail-closed、订单来自哪个 decision、经哪个 connector）。
7. **验收增补 SC-24 … SC-28**（详见下方"成功标准"增补）。

### SC-24 – SC-28（人类批准增补）

- **SC-24**：含 `MARK_PRICE` fixture → `ReferencePriceProvider` → Risk → PAPER execution **工程闭环**。
- **SC-25**：无 `MARK_PRICE` fixture → `ReferencePrice UNKNOWN` → **fail-closed**。
- **SC-26**：`decision_id` 是 **canonical order correlation metadata**，而不是 runtime side-map。
- **SC-27**：`Order → Decision` 与 `Decision → Order` 在真实 Product API/UI **可双向查询**。
- **SC-28**：market connector health 与 private execution connector health 可出现**不同**状态，不被合并成一个 `connected`。

## 目标

建立 Probex 正式的 Instrument Domain 与 Venue Integration 边界，使交易核心不再隐含依赖“Binance + BTCUSDT Perpetual”。

本阶段重点是工程架构闭环，而不是一次性实现股票、期货、多个交易所。

完成后：

- 当前 BTCUSDT 可以被明确表达为 CRYPTO / PERPETUAL；
- Market Data 与 Private Execution 具有正式 connector contract；
- PAPER 与 Binance 通过统一执行边界接入；
- Strategy / Risk / Execution 不直接依赖具体交易所；
- UI 能明确告诉用户：交易什么、在哪交易、通过哪个 connector、当前连接状态如何；
- 股票、期货、其它 Crypto venue 后续可通过增加实现扩展，而不推翻核心架构。

---

## 背景

P0001.14 已经完成真实 runtime 决策闭环：

Market
→ Prediction
→ Strategy
→ Risk
→ Readiness
→ Execution
→ Accounting
→ Product/UI

但当前系统仍存在几个架构事实：

1. 当前主线实际上是 BTCUSDT Crypto Perpetual。
2. PAPER 与 Binance execution 都已经存在，但缺少统一的正式 Venue contract。
3. Market Data 与 Private Execution 已经承担不同生命周期和失败模式，但没有被明确提升为一级架构概念。
4. 未来若支持：
   - 股票
   - 期货
   - Crypto Spot
   - Crypto Perpetual
   - 不同券商/交易所
   当前核心不能继续依赖 symbol 字符串和 Binance-specific semantics。
5. PAPER mark/reference price 的正式来源尚未建立。
6. Order → Decision 的关联仍需完整贯通。

因此本阶段不是增加更多交易能力，而是把现有单市场工程闭环整理成可扩展产品骨架。

## 架构

正式拆成两个正交维度：

```text
Instrument Domain
        │
        │ 描述“交易的是什么”
        ▼
Strategy / Risk / Execution
        │
        │ 描述“交易意图”
        ▼
Venue Integration
        │
        │ 描述“通过谁、怎么执行”
        ▼
Exchange / Broker / Paper
```

### Instrument Domain

回答：

```text
这个金融产品是什么？
有哪些业务语义？
允许什么交易能力？
如何计价、结算、做空、到期？
```

### Venue Integration

回答：

```text
通过哪个 venue / broker？
怎样获取行情？
怎样下单？
怎样接收订单、成交、账户变化？
怎样 reconciliation？
```

两者不能互相替代。

# 设计

## 1. Instrument Identity

新增正式 InstrumentSpec。

至少包含：

```text
instrument_id
symbol
asset_class
product_type

base_asset
quote_asset
settlement_asset

price_tick
quantity_step
min_quantity
min_notional

capabilities
reference_price_policy
```

当前正式实例：

```text
BTCUSDT

asset_class = CRYPTO
product_type = PERPETUAL
base_asset = BTC
quote_asset = USDT
settlement_asset = USDT
```

不能再仅靠 `"BTCUSDT"` 字符串推断全部业务含义。

---

## 2. AssetClass

正式定义：

```text
EQUITY
FUTURE
CRYPTO
```

本阶段只有：

```text
CRYPTO
```

具有生产实现。

EQUITY / FUTURE 只作为 domain vocabulary 和 capability contract 存在。

禁止本阶段实现股票或期货交易。

---

## 3. ProductType

至少定义：

```text
EQUITY_CASH
SPOT
PERPETUAL
DELIVERY_FUTURE
```

当前生产支持：

```text
PERPETUAL
```

其它类型仅用于证明 domain contract 能表达，不实现完整业务。

---

## 4. Instrument Capabilities

不同产品不能被强制抹平成同一种交易模型。

InstrumentCapabilities 至少允许描述：

```text
supports_long
supports_short
supports_margin
supports_reduce_only

has_expiry
has_funding
has_corporate_actions

supports_market_order
supports_limit_order
supports_post_only

trading_session_type
settlement_type
```

当前 Crypto Perpetual：

```text
supports_long = true
supports_short = true
supports_margin = true
supports_reduce_only = true
has_expiry = false
has_funding = true
has_corporate_actions = false
```

这些属于 instrument/product semantics。

不能由 Strategy 根据 venue 名称猜。

---

## 5. Venue Rules 与 Instrument Semantics 分离

必须明确区分：

### Instrument Semantics

例如：

```text
PERPETUAL
has_funding
supports_short
settlement_asset
expiry semantics
```

### Venue Rules

例如：

```text
tick size
quantity step
minimum notional
supported order types
rate limits
venue-specific restrictions
```

禁止继续把所有东西塞进一个 venue config dict。


## 8. PrivateExecutionConnector

执行结果必须继续映射到现有统一语义：


PaperBroker 不直接暴露给 Strategy / Product / UI。

# Reference / Mark Price

## 11. ReferencePrice Contract

解决 P0001.14 暴露的正式问题：

> PAPER Risk 需要 mark/reference price，但 AccountingCore 明确不能拿 last trade 随意代替。

建立：

```text
ReferencePriceProvider
```

输出至少：

```text
instrument_id
price_type
price
as_of
source
freshness
known
```

PriceType 至少允许表达：

```text
MARK
MID
INDEX
LAST
```

但本阶段不能偷偷决定：

```text
MARK = LAST
```

---

## 12. Current PERPETUAL Reference Price

优先审计 Binance/现有市场数据中是否已有：

- mark price
- index price
- best bid/ask midpoint

选择必须符合当前 Risk/Accounting 语义。

如果现有系统没有正式 mark price source：

允许：

```text
ReferencePrice = UNKNOWN
```

并保持 fail-closed。

不得为了让 PAPER 下单而使用 last trade 冒充 mark price。

# Execution Boundary

## 13. ExecutionEngine

ExecutionEngine 只允许依赖统一 execution connector interface。

禁止：

```text
if venue == "binance"
if mode == "paper"
```

在核心业务路径散落。

具体 venue differences 必须留在：

```text
Instrument semantics
Venue rules
Connector adapter
```

---

## 14. Normalization

Order normalization 继续由正式 normalization boundary 完成。

输入：

```text
InstrumentSpec
VenueRules
OrderIntent
```

输出：

```text
normalized price
normalized quantity
rounding evidence
reject reason
```

不能让 Strategy 自己做 Binance tick-size rounding。

---

## 15. Order Identity

正式 OrderView 增加/确认：

```text
instrument_id
venue_id
decision_id
client_order_id
venue_order_id
```

修复 P0001.14 遗留：

```text
Order ↔ MakerDecision
```

必须可以稳定关联。

最终用户必须能够：

```text
Order
→ Decision
→ Prediction
→ Market state
```

反向也能：

```text
Decision
→ Order(s)
```

不允许依赖模糊时间匹配。

## 验收结论

- **A**：`#/api/v1/instrument` 与 snapshot 一致显示 `paper:BTCUSDT` / `CRYPTO` / `PERPETUAL` / `paper(PAPER)`。
- **B / SC-24（工程闭环必须完整）**：含 `MARK_PRICE` fixture → `ReferencePriceProvider`（`source=market_event.mark_price`）
  → accounting 收正式 MARK（`60000.0`，**不是** last trade）→ Risk 允许 → 唯一 `PaperBroker` 产生 `OPEN` 订单 + ack。
- **SC-25**：无 `MARK_PRICE` fixture → `ReferencePrice UNKNOWN`（`REFERENCE_PRICE_MARK_UNAVAILABLE`）
  → `mark_price=None` → 无预算 → 决策 `NONE`、**零下单**（fail-closed，未用 last trade 冒充）。
- **SC-26**：`decision_id` 随 `MakerDecision → OrderProposal → Order` 进入 canonical order record；
  `RuntimeDecisionLoop` 与 Product **都没有** decision↔order 映射（守卫测试断言）。
- **SC-27**：`Order → Decision`（订单 correlation）与 `Decision → Order(s)`
  （`OrderTracker.orders_for_decision` → `/api/v1/decisions/orders` → UI 跳转）双向可查。
- **SC-28**：market / private connector health 完全独立（两条状态、两套事实），
  单一 `connected` 字段不存在；真实出现过两者不同的状态。
- **C**：`BinanceMarketDataConnector` / `BinancePrivateExecutionConnector` 离线验证能分别暴露 rules/facts/timestamps/
  health/reconciliation/rate-limit（复用既有实现，未重写 client）。
- **D**：`PriceType.LAST` 结构性不可用于风险路径（policy 构造期即拒绝）。
- **E**：PAPER 自然产生 decision/order；correlation 含预测 id 与决策所依据的 market state hash。
