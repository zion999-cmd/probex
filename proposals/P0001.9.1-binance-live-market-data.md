### 0.3 数据流与事件契约

```text
public WS (depth)  ─┐
                    ├─→ depthUpdate   → parse_depth_diff     → MarketEvent(BOOK_DELTA)
market WS (aggTrade)┼─→ aggTrade      → parse_agg_trade      → MarketEvent(TRADE, TradePayload)
                    └─→ markPrice     → parse_mark_price     → MarkPriceObservation（**不是** MarketEvent）
REST                ─→ depth snapshot → parse_depth_snapshot → MarketEvent(BOOK_SNAPSHOT)
                    ─→ exchangeInfo   → TradingRules
```

- depth / aggTrade 复用 P0001.1 / P0001.8 的既有载荷类型；**不修改 `market-state-v1`**。
- mark price 按提案要求作为**独立事实**：`MarkPriceObservation`（connectors 层值类型），
  本阶段不写入 `MarketEvent`、不写 Accounting、不参与 Risk（这些属 P0001.9.2/9.3）；
  绝不使用 last trade 代替 mark。
- `aggTrade` → aggressor 映射：Binance `m` = `isBuyerMaker`（买方是 maker）⇒ **aggressor = SELL**；
  `m = false` ⇒ **aggressor = BUY**。语义不得反转（有独立测试）。
- 重复 aggTrade：按 `aggregate_trade_id` 的**单调水位**去重（同 symbol），旧 id / 重复 id 被丢弃并计数，
  内存有界；该去重与 P0001.8 `SimulatedVenue` 的二级去重并存。
- malformed 报文：fail closed（丢弃该条 + `malformed_count += 1`），**不得**杀死整个 runtime（SC-10）。

### 0.4 盘口同步与重连（SC-2/3/4/9）

```text
WS depth 首帧 → 进入缓冲 → REST snapshot → MarketBook 按 U/u 规则对齐 → HEALTHY
检测到 gap   → STALE → request_resync() → 新 snapshot → 重放缓冲 → HEALTHY
WS 断线      → invalidate("transport_lost") → STALE → request_resync() → 新 snapshot → HEALTHY
```

- **新增最小机制**：`MarketBook.invalidate(reason)`（HEALTHY → STALE，已是合法转换；非 HEALTHY 时幂等），
  `FeatureEngine.invalidate(reason)` 转发。这是 SC-9「重连后 BookHealth != HEALTHY，直到重新完成
  snapshot + delta 对齐」的**必要支撑**：现有 API 无法把 HEALTHY 盘口标记为不可信，而传输层丢失
  不能伪造 gap 事件。仅新增入口，不改任何既有转换语义。
- 重连必须重新走 snapshot + 对齐，不允许「socket 连上就恢复 tradeable」。
- 重连 backoff：`ReconnectPolicy(max_attempts, base_backoff_ms, max_backoff_ms)`（必填、无默认值、无随机抖动）。

### 0.5 TradingRules（SC-8）

`parse_exchange_info(raw, symbol)` → `TradingRules`：`tick_size` / `min_price` / `max_price` /
`step_size` / `min_qty` / `max_qty` / `min_notional` / `status`，全部来自 `filters`；
**缺失即报错**，绝不使用 `pricePrecision` / `quantityPrecision` 顶替。P0001.9.2 直接消费该类型。

### 0.6 Telemetry（SC-13）

`LiveMarketDataTelemetry`：`ws_connect_count` / `ws_reconnect_count` / `ws_disconnect_count` /
`depth_gap_count` / `resync_count` / `snapshot_count` / `snapshot_latency_ms`（最后一次）/
`event_lag_ms`（最后一次 exchange→process）/ `agg_trade_count` / `duplicate_trade_count` /
`mark_update_count` / `mark_age_ms` / `malformed_message_count` / `message_count`。
时间戳全部来自事件 + live 边界时钟，核心不使用 wall-clock。

## 1.4 诊断 P0001.9.1.1（→ 已实施并验收，见 P0001.9.1.1 §1）：Futures diff depth 的连续性判定（**真实样本，已执行**）

人类指出：Futures 的 diff depth **不能**用 `next.U == prev.u + 1` 作为唯一连续性条件；官方体系里
Futures 深度事件带 `U / u / pu`，正确的连续性判据是 **`current.pu == previous.u`**（`pu` = 上一条推送的最终 update id），
而一条事件内部跨很多 id 是正常的聚合。⇒ 按人类要求**只做诊断、不改生产代码**，采集真实样本核验两种规则。

**样本（真实 Binance USDⓈ-M，经人类本机代理隧道；原始报文存于仓库外 `/tmp/probex_live/sample_*.jsonl`）**

| 规则 | `btcusdt@depth`（250ms 默认） | `btcusdt@depth@100ms` |
| --- | --- | --- |
| 事件数 / 相邻对 | 179 / 178 | 295 / 294 |
| `pu` 字段存在率 | **179/179** | **295/295** |
| **R_P：`current.pu == previous.u`** | **178/178（100%）** | **294/294（100%）** |
| R_QW：`current.U <= prev.u+1 <= current.u`（P0001.1 现行窗口规则） | **0/178（0%）** | **0/294（0%）** |
| R_QS：`current.U == prev.u + 1`（严格相邻） | 0/178 | 0/294 |
| `pu - prev.u` 取值集合 | **{0}** | **{0}** |
| `U - prev.u` min/median/max | 4 / **116** / 593 | 2 / **120** / 831 |
| 单事件覆盖 update-id 数 min/median/max | 12688 / 27299 / **101561** | 4409 / 9972 / 49531 |
| 报文字段 | `E T U a b e ps pu s st u` | 同左 |

**原始报文示例（真实，已裁剪中间数组）**

```json
{"E":1790561633099,"T":1790561633088,"U":11674982854765,"a":[["83716.30","6.318"],...],"b":[...],"e":"depthUpdate","ps":"BTCUSDT","pu":11674982854761,"s":"BTCUSDT","st":1,"u":11674982867413}
{"E":1790561633351,"T":1790561633350,"U":11674982892393,"a":[...],"b":[...],"e":"depthUpdate","ps":"BTCUSDT","pu":11674982867413,"s":"BTCUSDT","st":1,"u":11674982913256}
```

（第 2 条的 `pu` == 第 1 条的 `u` ✓ 而 `U - prev.u = 70` ⇒ 按现行规则必然误判为 GAP。）

**结论（推翻 §1.3）**

1. **Futures 数据没有丢失**：`pu == prev.u` 在 473 个相邻对中 **100% 成立**，`pu - prev.u` 恒为 0。
2. 一条 Futures diff 事件**聚合**上万个 update id（median 27299 / 9972），因此 `U` 与上一条 `u` 之间必然有大间距
   （median 116 / 120）。**`U == prev.u + 1` 这种「严格相邻」判据对 Futures 不成立**。
3. P0001.1 现行的窗口判据 `first <= last+1 <= u`（D-003）因此对 Futures **0% 通过** ⇒ 每条消息都被判 `GAP`
   ⇒ 每秒重同步 ⇒ 同步 REST 抓取阻塞读循环 ⇒ 观测到的 7–36 s event lag、HEALTHY 占比 14%、resync ≈1/s。
   **根因是连续性判据，不是 Binance 丢数据，也不是链路。**
4. §1.3 中「Binance 跳号」的判断与 A/B/C/D 四个选项**均不再成立/暂停**：不需要改流、不需要弱化完整性、
   也不需要容忍空洞；需要的只是**把 `pu` 带过边界并改判据**。

**需要的修复（待授权；本诊断未改任何生产代码）**

- 边界：`connectors/binance/market_data/depth.py` 解析 `pu`；`market/events/payloads.py::BookDeltaPayload`
  增加 `previous_update_id: int | None`（Futures 提供；现货没有 ⇒ None）。
- 判据：`market/book/order_book.py` 的连续性检查改为
  **优先 `previous_update_id == last_applied_u`**（Futures），无 `pu` 时回退到既有窗口规则（现货）。
- 这会修改 **P0001.1 的 D-003 决策与 `BookDeltaPayload` 契约** ⇒ 需人类/设计方以
  **P0001.9.1.1（或等效提案）** 落盘批准后才能实施（含 SC、迁移影响、现货/期货双路径语义）。
- 预期效果：真实环境下 gap ≈ 0、resync ≈ 0、HEALTHY 连续、event lag ≈ 链路延迟（实测 ≈200 ms）。

**本阶段状态**：P0001.9.1 保持「实现中」；`currentProposal` 保持 `P0001.9.1`；未提交。
