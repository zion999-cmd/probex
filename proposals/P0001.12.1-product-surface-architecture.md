# P0001.12.1：Product Surface Architecture

**状态**：已完成（信息架构 + gap audit）
**日期**：2026-09-29  
**依赖**：P0001.12

## 目标

建立 Probex 的统一产品 Surface 架构。

本阶段不增加交易能力，解决的是：

- 用户进入产品后先看什么；
- 一级导航是什么；
- 各页面分别回答什么问题；
- 现有 10+ 页面如何重新组织；
- Market / Execution / Risk / Runs 等能力如何形成完整工作流；
- 后续 P0001.13 以及更多产品阶段都必须服从这套 Surface，而不是继续堆页面。

Probex 定位为：

> **Automated Trading Operations Console**  
> 自动交易运行、观察、解释与评估控制台。

不是手工交易终端，也不是单纯策略研究工具。

---

## 背景

当前 UI 已经有：

```text
Overview
Market
Prediction
Strategy
Risk
Orders
Portfolio
Readiness
Evidence
Runs
```

能力实际上不少，但目前仍然是**按内部模块划页面**。:chatgpt-content-reference{index="0"}

这会导致用户必须自己在多个页面之间拼接：

```text
市场发生了什么
→ 模型怎么看
→ 策略决定什么
→ 风控为什么允许/拒绝
→ 发出了什么订单
→ 最后发生了什么
```

Surface 应该围绕人的问题组织，而不是代码目录组织。

# 1. Monitor

## 用户问题

> **现在系统怎么样？**

这是默认首页。

必须在一屏内回答：

- 系统是否运行；
- 当前模式是什么；
- 当前有没有资金风险；
- 当前仓位；
- 当前挂单；
- 当前 PnL；
- 系统现在有没有报价；
- 有没有阻塞；
- 执行是否健康；
- 最近发生了什么。

## 页面结构

```text
┌──────────────────────────────────────────────────────────────┐
│ TESTNET · BTCUSDT · RUNNING · HEALTHY · runtime-xxx          │
├──────────────────────────────────────────────────────────────┤
│ Equity │ PnL │ Position │ Exposure │ Orders │ Exec Health    │
├──────────────────────────────────────────────────────────────┤
│ Blockers / Warnings                                         │
├──────────────────────────────┬───────────────────────────────┤
│ Market / Current Quotes      │ Position / Active Orders      │
│ compact market visual        │                               │
├──────────────────────────────┴───────────────────────────────┤
│ Recent Activity                                              │
│ decision → risk → order → event → fill/cancel               │
└──────────────────────────────────────────────────────────────┘
```

### Monitor 不做

- 不显示完整 L2；
- 不显示完整 evidence；
- 不承担配置管理；
- 不堆几十个指标。

它只是：

> **30 秒理解当前系统状态。**

# 全局交互原则

## 1. Mode 必须永远明显

特别是：

```text
REPLAY
PAPER
TESTNET
LIVE
```

不能只放一个小标签。

LIVE 与 PAPER / TESTNET 应该具有明显的视觉区分。

但视觉样式由实现层决定，本提案只固定语义。

## 2. UNKNOWN 永远显式

继续坚持：

```text
UNKNOWN ≠ 0
UNKNOWN ≠ empty
UNKNOWN ≠ healthy
```

所有图表也是如此。

例如没有 latency 数据：

```text
Latency: UNKNOWN
```

不能绘制成 `0ms`。

## 3. Blocker 全局可见

任何页面都可以快速知道：

> 为什么现在系统不能做某件事。

点击 blocker 跳转到对应 System 页面。

## 4. Drill-down 而不是堆信息

统一交互：

```text
Overview
   ↓
Domain Detail
   ↓
Evidence
   ↓
Raw Facts
```

普通用户停在第一层。

专业用户可以一直钻到底。

## 5. Evidence 是底层能力，不再作为一级导航

这是一个重要改变。

当前 `Evidence` 单独一级页面不应该长期保留。

Evidence 应成为：

```text
Activity → detail
Orders → detail
Risk reject → detail
Readiness blocker → detail
```

它是产品的“证据底座”，不是用户工作流本身。

# 成功标准

1. 一级导航不超过 5 个。
2. 用户 30 秒内能从 Monitor 判断系统当前状态。
3. Market 能回答“市场发生了什么”。
4. Activity 能回答“系统为什么这么做”。
5. Performance 能回答“这次运行表现怎样”。
6. System 能回答“为什么能/不能运行”。
7. Prediction / Strategy / Evidence 不再要求用户手工拼接因果链。
8. Run 成为 Performance 的核心单位。
9. Execution Safety 有明确 UI 落点。
10. 所有现有产品能力都有明确归属，不出现“孤儿页面”。
11. 不新增第二套事实来源。
12. 不改变任何交易行为。


给专业人士评审时，我建议只问这 6 个问题
不要让对方泛泛说“UI 好不好看”，那没什么价值。
让他们评价：
1. 作为自动交易系统，你打开首页最想先看到什么？这里有没有缺？
2. Market 页的信息够不够判断当前盘口环境？
3. 从决策到订单到成交的 Activity Timeline 对实际复盘有没有价值？
4. Performance 用 Run 作为核心单位是否符合真实使用习惯？
5. Risk / Readiness / Execution 放在 System 下是否容易理解？
6. 如果每天使用这个产品，哪个操作流程最别扭或缺失？
尤其要区分两类评审者：
手工交易员 和 量化/自动交易系统操作者。

他们对 Surface 的需求会非常不一样。不要因为一个长期用股票客户端的人说“怎么没有买卖按钮”，就直接把 Probex 改成手工交易软件。
这份可以直接交给 Pi 建立 P0001.12.1-product-surface-architecture.md。
**先不要实施大规模 UI 重构。**先让 Pi 按这份设计做现有 UI → 新 Surface 的 gap audit，确认哪些只是移动/组合，哪些真的缺 Product API。然后你拿架构和 gap audit 给专业人士看，会比拿一个半成品界面给他们评价有效得多。

### 2. Gap audit（现有 UI → 新 Surface）

| Surface 需求 | 现有 Product API 是否足够 | 结论 |
| --- | --- | --- |
| Monitor：equity / PnL / position / exposure / orders / readiness / market / quotes | ✅ `/api/v1/snapshot` + `/api/v1/market/overlays` | **只需移动/组合** |
| Monitor：Execution Health（uncertain / lost / unknown 计数） | ✅ `snapshot.execution.*` | **只需组合** |
| Market：heatmap / trades / health / overlays / features / replay | ✅ P0001.12 端点齐备 | **只需组合** |
| Market：Live / Replay / Run Review | ✅ `/api/v1/runs/<id>/market` | **只需组合** |
| Activity：因果链（market→prediction→decision→readiness→order→exchange） | ✅ `snapshot` + `/api/v1/evidence` + `/api/v1/market/overlays` | **只需组合** |
| Activity：risk 环节 reason code | ✅ `snapshot.risk.rejects` | **只需组合** |
| Activity：Hit 到 **fill** 级证据（Related Fill） | ❌ `evidence.trace` 目前止于 `execution_event`，无 fill 证据 | **需新 Product API（G1）** |
| Activity：drill-down「Raw Facts / Related Fill / Raw Payload」 | ❌ 无 raw-facts 只读端点 | **需新 Product API（G2）** |
| Performance：run 列表 / 指标 / 对比 / 定义 | ✅ P0001.11 端点齐备 | **只需组合** |
| Performance：equity curve / exposure timeline | ❌ run summary 只有终值，无持久化 equity 序列 | **需新 Product API（G3）** |
| System/Health：market / private stream / clock / uptime | ✅ `snapshot.health` | **只需组合** |
| System/Health：prediction provider 状态（HEALTHY/DEGRADED/BACKING_OFF）、accounting 健康度 | ❌ read model 未暴露 | **需新 Product API（G4）** |
| System/Risk：limits / position / exposure / drawdown / daily loss / kill switch / rejects | ✅ | **只需组合** |
| System/Readiness：status / scope / reasons / blockers | ✅ | **只需组合** |
| System/Readiness：authority **kind / TTL / generation** | ❌ snapshot 只暴露 `authority_id` | **需新 Product API（G5）** |
| System/Configuration / Capabilities | ✅ P0001.11 端点齐备 | **只需组合** |
| System/Execution：rate limits / venue limits / latency / reconciliation | ❌ 后端能力尚未存在（P0001.13 负责） | **P0001.13 后端 + Surface 插槽已预留** |

**结论**：Surface 的 12 类需求可直接通过**移动/组合**现有事实满足；需要**真正新增 Product API** 的只有 5 项（G1 fill 级证据、G2 raw facts、G3 持久化 equity/exposure 序列、G4 prediction provider 与 accounting 健康、G5 authority kind/TTL/generation），
另有 1 类（Execution Safety 明细）属于 **P0001.13 的后端工作**，本阶段只保留 UI 插槽。
