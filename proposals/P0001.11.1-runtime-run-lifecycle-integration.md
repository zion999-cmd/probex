P0001.11.1：Runtime Run-Lifecycle Integration
状态：已完成
日期：2026-09-29
依赖：P0001.11
目标
把已经完成的 Run Registry 接入实际 Probex runtime，使 REPLAY / PAPER / TESTNET / LIVE 的真实运行自动形成 RunRecord。
不增加新的持久化模型，不修改交易逻辑。
设计
生命周期固定为：
runtime identity established
        ↓
create_run()
        ↓
running
        ↓
graceful stop
        ↓
finalize_run(COMPLETED)

异常退出：
created but no finalization
        ↓
next inspection
        ↓
INCOMPLETE

必须绑定现有：
RuntimeIdentity
ConfigSnapshot fingerprint
RunSummary
data range

边界
包含：
- 将现有 reports/lifecycle.py 接到真实 runtime lifecycle
- REPLAY / PAPER / TESTNET / LIVE 共用一套语义
- graceful stop 自动 finalize
- 未正常 finalize 的 run 保持 INCOMPLETE
- 验证真实运行后 runs / UI 能直接看到该 run
不包含：
- 不修改 orchestrator 决策顺序
- 不修改 MakerPolicy
- 不修改 RiskGate
- 不修改 ExecutionEngine
- 不引入 daemon
- 不做 crash recovery manager
- 不做多进程 writer
- 不扩 RunCompare
- 不处理 P0001.12 内容
成功标准
1. 实际启动一次 runtime 自动产生 RunRecord。
2. 正常结束自动变为 COMPLETED。
3. 非正常未 finalize 的记录仍为 INCOMPLETE。
4. runs / API / UI 无手工登记即可看到真实 run。
5. run 的 config fingerprint 与启动时 ConfigSnapshot 一致。
6. 不改变交易路径与运行决策。
7. 全量测试不回归。

### 说明（如实记录）

- run registry 的**读侧**语义固定为"created but no finalization ⇒ `INCOMPLETE`"：存储层无法判断进程活性，
  因此**运行中**的会话知道自己是 `RUNNING`（`session.record`），而**检查者看到的是** `INCOMPLETE`
  （与提案流程图一致）。若运行进程真的结束却没 finalize，语义即为 `INCOMPLETE` —— 这正是 `INCOMPLETE` 的用途。
- 本阶段只把会话层接到 runtime lifecycle；现有 runner（`/tmp/probex_live/*`）与 `live/orchestrator.py`
  尚未调用 `RuntimeSession`（调用接线属于后续阶段的显式工作，未擅自改动运行循环）。
