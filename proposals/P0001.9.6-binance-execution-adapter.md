### 0.2 关键不变量

1. **submit 前必须验证 authority**：TTL / scope / recovery_generation / market_generation / HWM / kill switch 任一不满足 ⇒
   本地拒单（`local_reject:<REASON>`），**零 HTTP 请求**；
2. **cancel 不要求 LIVE_READY**（降险不可被锁死），但仍要求"Probex 所有权 + 环境明确 + 凭据可用"；
3. **三分类**：只有可解析 ACK ⇒ `OrderAccepted`；只有业务拒绝（4xx + 业务码）⇒ `OrderRejected`；
   其余 ⇒ **UNKNOWN ⇒ 返回空事件**（上层按 uncertain exposure 处理）且**不重试**；
4. **clientOrderId 幂等主键**：原样作为 `newClientOrderId`；
5. **第一版只允许 LIMIT + GTX + BOTH**；`post_only=False` 本地拒绝；**不自动 round**（tick/step/min/notional 不合法即拒绝）；
6. **成交事实只来自 trade execution**（user stream 的 `TRADE` 事件）；query 结果**不**造 Fill（§11）；
7. **UNKNOWN 用 `query_order()` 收敛**（按 `origClientOrderId`，不需要 orderId）；
8. **user stream 是主要异步事实源**，桥接进既有 `OrderTracker`；与本地终态冲突的转换**跳过并计数**（冲突交给 reconciliation）；
9. **启动顺序**（§20）：private ACTIVE → recovery → collector → gate → authority → 才构造/启用写路径。

### 0.3 一处实现说明（未扩范围）

`adapter.open_orders()/recent_fills()` 复用 private 只读层（由调用方注入 `private_read`），
这样 reconciliation 仍使用**同一套**外部事实归一化（P0001.9.3），不在写路径重造读取逻辑。

### 1.6 Implementation correction（2026-09-28，人类裁决）

**缺陷**：`open_orders()` / `recent_fills()` 在未注入事实 provider 时返回**空元组** ✗。
空元组在 `ExecutionAdapter` 契约里的含义是"**交易所确认没有挂单/没有成交**"，因此这实际上是 **fail-open**：
若交易所真实存在一笔 Probex 挂单而 provider 没接上，上层会读到"external open orders = 0"，
直接破坏 P0001.6.1 的 uncertain exposure 与 P0001.9.3 的 recovery 纪律。

**修正**（UNKNOWN ≠ EMPTY）：

1. 新增 domain 错误 `ExternalFactsUnavailableError`（"external facts unavailable"）；
2. `open_orders()` / `recent_fills()`：provider 未注入 ⇒ **抛错**；provider 读取/解析失败 ⇒ **传播为 unavailable**
   （不降级为空）；provider 缺少必需方法 ⇒ unavailable；
3. **只有** provider 真实返回空元组时才返回 `()`（= 事实：无挂单/无成交）；
4. `ExternalFactsProvider` 提升为显式 Protocol（`parse_open_orders` / `parse_recent_fills`），
   产品不内置实现（provider 由 live 编排层注入 —— 属后续 live loop 范围）；
5. 新增 7 条测试覆盖：provider=None 两条、provider 抛错、provider 真空、缺方法、foreign 过滤、
   以及"不可用**绝不**被当成外部无订单"的语义断言。

### 1.7 遗留（不阻塞）

1. **`ExecutionAdapter` 仍是同步接口 + `poll()` 队列**（§18 明确不改成 async）：真实生命周期由 user stream 桥接承担。
2. `open_orders()` / `recent_fills()` 需要调用方注入 `ExternalFactsProvider`；
   **未注入即 `ExternalFactsUnavailableError`**（fail closed；绝不返回空）。
3. 目前只有 GTX/post-only LIMIT —— MARKET / stop / hedge / IOC / FOK / GTD / modify / batch 全部**未实现**（提案 NOT Included）。
4. 主网写路径**已具备能力但未验证**：主网仍受 readiness（`MAINNET_PRIVATE_NOT_VALIDATED`）与人类授权双重限制。

# 原提案文本（原样保留）

## 目标

实现第一个真实 Binance USDⓈ-M 写执行适配器：

```text
Order
→ authority validation
→ Binance submit/cancel
→ ACK / unknown outcome
→ user stream
→ ExecutionEvent
→ OrderTracker
→ Accounting
```

只支持当前 Maker V3 真正需要的：

```text
LIMIT
GTX / Post Only
one-way BOTH
reduceOnly true/false
```

本阶段验证 **Testnet 写链闭环**，不授权 Mainnet 下单。

---

## 背景

现有 `ExecutionAdapter` 已经定义：

```text
submit()
cancel()
poll()
open_orders()
recent_fills()
```

`OrderManager` 已负责：

```text
cancel-before-replace
PENDING_CANCEL
Tracker
```

`ExecutionEngine` 已负责：

```text
fresh RiskSnapshot
→ RiskGate
→ OrderManager.submit
```

P0001.9.5 又补上：

```text
ExecutionReadinessAuthority
```

所以 P0001.9.6 不重新设计 execution engine，只把真实 Binance venue 接进现有契约。

---

## 架构

```text
OrderProposal
      ↓
ExecutionEngine
      ↓
fresh RiskGate
      ↓
Authority Validator
      ↓
OrderManager
      ↓
BinanceExecutionAdapter
   │          │
   │ REST     │ User Stream
   ▼          ▼
submit/cancel ORDER_TRADE_UPDATE
   │          │
   └────┬─────┘
        ↓
  ExecutionEvent
        ↓
   OrderTracker
        ↓
    Accounting
```

# 设计

## 1. ExecutionAdapter 不拥有交易决策

Adapter 只负责：

```text
Order → Binance wire request
Binance facts → ExecutionEvent
```

禁止它判断：

```text
方向
Jev 概率
Maker edge
仓位目标
risk limits
```

这些仍属于上层。

---

## 2. Authority 必须紧邻写请求验证

真实：

```text
submit
cancel
```

之前必须验证当前：

```text
ExecutionReadinessAuthority
```

至少检查：

```text
TTL
scope
recovery_generation
market_generation
HWM generation
kill switch
```

### submit

authority 无效：

```text
不得发送 HTTP request
```

### cancel

这里与 submit 不同。

**撤单属于降险动作，不能因为 readiness 失效就锁死挂单。**

因此：

```text
cancel 不要求 LIVE_READY authority
```

但必须仍满足：

```text
目标订单属于 Probex
环境/scope 明确
凭据可用
```

这延续现有：

```text
HALT_ALL 仍允许 cancel
```

原则。

---

## 3. 第一版订单范围固定

仅支持：

```text
type = LIMIT
timeInForce = GTX
positionSide = BOTH
```

映射：

```text
Order.post_only == True
→ GTX

Order.reduce_only
→ reduceOnly=true/false
```

拒绝：

```text
MARKET
STOP
TAKE_PROFIT
IOC
FOK
Hedge Mode LONG/SHORT
priceMatch
GTD
```

不要顺手把 Binance 全部订单类型做完。

---

## 4. clientOrderId 是幂等主键

必须直接使用现有：

```text
Order.client_order_id
```

作为 Binance：

```text
newClientOrderId
```

禁止 adapter 自己再生成另一个 ID。

现有 Probex ownership：

```text
probex-...
```

继续作为恢复和 reconciliation 的 ownership boundary。

---

## 5. submit outcome 三分类

不能只分成功/失败。

定义：

```text
CONFIRMED_ACCEPTED
CONFIRMED_REJECTED
UNKNOWN
```

### CONFIRMED_ACCEPTED

只有 Binance 明确返回可解析 ACK。

生成：

```text
OrderAccepted
```

### CONFIRMED_REJECTED

只有交易所明确业务拒绝，例如：

```text
invalid quantity
post-only rejected
insufficient margin
invalid parameter
```

生成：

```text
OrderRejected
```

### UNKNOWN

例如：

```text
timeout
socket reset
response unreadable
5xx
发送后连接断开
```

**不能生成 FAILED。**

订单进入：

```text
LOST / uncertain exposure
```

然后 query/reconciliation。

这是本阶段最重要的不变量。

---

## 6. timeout 后禁止自动重试 submit

假设：

```text
POST order
→ Binance 实际已创建
→ response timeout
```

此时再次 POST：

```text
可能重复下单
```

所以：

```text
UNKNOWN submit
→ 不 retry POST
→ query by origClientOrderId
```

如果 query 得到：

```text
NEW / PARTIALLY_FILLED / FILLED / ...
```

则恢复真实状态。

如果查询仍无法确认：

```text
保持 LOST
→ uncertain exposure
→ 禁新增风险
```

---

## 7. submit reconciliation 优先使用 clientOrderId

新增只读查询能力：

```text
query_order(symbol, origClientOrderId)
```

purpose：

```text
resolve uncertain submit
resolve uncertain cancel
reconciliation
```

不要依赖 exchange orderId 才能恢复，因为 UNKNOWN submit 时可能根本没收到 orderId。

---

## 8. cancel outcome 仍然三分类

### 明确 canceled

返回/stream 已确认：

```text
CANCELED
```

### 明确已终态

例如已经：

```text
FILLED
EXPIRED
```

按事实处理，不再假装 cancel 成功。

### UNKNOWN

timeout / network error：

```text
仍然 PENDING_CANCEL / LOST
```

不能直接：

```text
CANCELED
```

随后 query/user stream 收敛。

---

## 9. User Stream 是主要异步事实源

`ORDER_TRADE_UPDATE` 已经在 private runtime 验证过。

本阶段 adapter 应桥接现有 private runtime 事件：

```text
NEW
PARTIALLY_FILLED
TRADE
FILLED
CANCELED
EXPIRED
REJECTED
```

转换为现有：

```text
ExecutionEvent
```

不要另建第二套订单状态机。

---

## 10. REST ACK 与 User Stream 必须允许重复

典型：

```text
REST ACK: NEW
↓
User stream: NEW
```

必须幂等。

同理：

```text
REST query
+
user stream
+
reconciliation
```

可能看到同一事实多次。

最终由现有：

```text
OrderTracker
FillLedger
```

去重。

Adapter 不应该假设“一个状态只来一次”。

---

## 11. Fill 事实必须来自 trade execution

成交事件必须保留：

```text
trade_id
order_id
client_order_id
price
qty
commission
commission_asset
event/exchange timestamp
cumulative qty
```

生成 canonical：

```text
ExternalFill / ExecutionEvent
```

不能从：

```text
executedQty delta
```

猜一个 synthetic Fill。

---

## 12. Post Only 契约

本阶段 Maker submit 必须：

```text
post_only=True
```

否则：

```text
adapter reject locally
```

即第一版 Binance adapter **不允许普通 GTC LIMIT**。

这样避免调用方误用 adapter 产生 taker 行为。

Binance API 当前支持 `GTX` 作为 post-only time-in-force。:chatgpt-content-reference{index="0"}

---

## 13. Reduce Only

`Order.reduce_only=True`：

```text
reduceOnly=true
positionSide=BOTH
```

但 adapter 不自行判断“它是不是真的减少仓位”。

真正的业务约束仍由：

```text
RiskGate
```

负责。

交易所如果拒绝，则作为明确 reject 事实返回。

---

## 14. Trading Rules 必须二次检查

submit 前必须使用已有：

```text
TradingRules
```

检查：

```text
tick size
step size
min qty
min notional
```

但不要在 adapter 内自动 round。

原则：

```text
不合法 → reject locally
```

不能：

```text
0.00123
→ adapter 偷偷改成 0.001
```

因为那会改变策略意图。

---

## 15. Authority 与订单 scope

submit 必须满足：

```text
authority.scope == adapter.environment
```

本阶段真实写验收只允许：

```text
TESTNET_LIVE_READY
→ Binance Testnet adapter
```

Mainnet authority 即便未来存在，也不在本阶段 acceptance 中使用。

---

## 16. REST 写边界单独隔离

建议不要直接往现有 `PrivateRestClient` 随手加大量写能力。

可以新增：

```text
BinanceExecutionRestClient
```

或：

```text
connectors/binance/execution/rest.py
```

它共享：

```text
credentials
signing
clock offset
safe error handling
```

但把：

```text
READ private
WRITE execution
```

边界显式分开。

这是安全边界，值得多一个很薄的模块。

---

## 17. 错误信息不得泄露 signed query

沿用 private REST 纪律：

```text
API key
signature
query string
```

都不能出现在：

```text
exception
logs
telemetry
repr
```

写路径尤其要保持。

---

## 18. Event bridge

真实 adapter 不能靠同步 `submit()` 返回承担完整生命周期。

建议保持现有接口不大改：

```text
submit()
cancel()
poll()
```

其中：

```text
submit/cancel
→ 只返回立即可确认事实

poll()
→ drain private-runtime-derived ExecutionEvent queue
```

不要为了 Binance 单独把整个 execution stack 改成 async。

这符合 D-021 原意：真实网络通过桥接进入既有 Tracker，而不是重写 Tracker。

---

## 19. reconnect / discontinuity

发生 private discontinuity：

```text
旧 authority invalid
Recovery invalid
```

同时 adapter：

```text
不得继续 submit
```

已有活动订单：

```text
不得假定状态
→ recovery/reconciliation
```

cancel 仍允许尝试，但结果必须遵循 UNKNOWN 语义。

---

## 20. Startup

真实 adapter 启用顺序必须：

```text
Private Runtime ACTIVE
→ Recovery RECOVERED
→ Evidence Collector
→ Readiness Gate
→ Authority issued
→ construct/enable execution write path
```

禁止：

```text
adapter 启动
→ 先下单
→ 再 recovery
```
