### 0.2 测量纪律（本阶段真实踩到并修正的两点）

1. **窗口起点必须在初始锚定之后**：`resync_count` / `snapshot_count` 要区分"启动对齐"与"窗口内连续性事件"；

   因此判定用 `snapshot_total > 0 且 anchor_established`，而不是"窗口内 snapshot > 0"（第二次运行即出现该误报）。

## 2. 原提案文本（原样保留）

目标
目标
把现有已经分别验证过的链路放到同一个真实 Testnet 运行窗口里验证：
Public Market Data
      +
Private Runtime
      +
Recovery
      +
Historical Daily PnL
      +
Clock Calibration
      +
Live Readiness

目标不是把 readiness 强行变绿，而是确认完整系统运行后真实剩余 blocker 到底是什么。
背景
目前 Readiness 剩余：
PRIVATE_LATENCY_UNKNOWN
HISTORICAL_DRAWDOWN_UNKNOWN
MARKET_NOT_READY

其中：
- PRIVATE_LATENCY_UNKNOWN：目前只是窗口内没有 private business event；
- MARKET_NOT_READY：之前 harness 没接 public market-data；
- HISTORICAL_DRAWDOWN_UNKNOWN：目前唯一明确的结构性缺口。
因此需要一次完整集成实测，避免提前假设 .2 必然是下一阶段。
架构
Binance Testnet Public
 depth / trade / mark
        ↓
 Market Runtime
        ↓
 market_ready
        │
        ├─────────────┐
        │             │
Binance Testnet   Private Runtime
Private REST      user stream
        │             │
        ├── Recovery ─┤
        ├── Income ───┤
        ├── Clock ────┤
        │             │
        └──────┬──────┘
               ↓
      LiveReadinessGate
               ↓
      READY | BLOCKED reasons

设计
1. Public market 链必须真实接入
不能再：
market_ready = 手工传 true

本次 harness 至少必须从真实 public runtime 读取：
book health
snapshot boundary
depth continuity
mark freshness
recent trade freshness

再映射成 readiness evidence。
本次只做 harness/orchestration 验证，不修改 D-043 的长期架构问题。
2. Private latency 必须取得真实业务事件样本
为了消除：
PRIVATE_LATENCY_UNKNOWN

需要在 user stream 已连接之后制造最小 Testnet 活动。
我给出明确授权边界：
仅 Binance USDⓈ-M Testnet
仅 BTCUSDT
仅测试网资金
允许仓库外 harness 执行最小订单活动

允许动作：
1. 一个远离市场价的 LIMIT GTX/Post-Only 小额订单
2. 等待 NEW 事件
3. 撤销该订单
4. 等待 CANCELED 事件

如果仅 NEW/CANCELED 已足够产生可用 private event lag 样本，不要额外制造成交。
只有如果实现证明确实需要 TRADE/ACCOUNT_UPDATE 样本才能完成 latency acceptance，才允许：
最小测试网 MARKET 开仓
→ 立即 reduceOnly MARKET 平仓
→ 最终必须 flat

约束：
notional <= 100 USDT
最终 position = 0
最终 open orders = 0
失败时优先 cleanup
所有写操作只允许出现在仓库外 harness
产品代码仍不得增加 submit/cancel endpoint

3. Clock evidence
同一运行窗口必须记录：
offset_ms
RTT
uncertainty_ms
calibration_age_ms
raw private lag
corrected private lag

并验证：
corrected = raw + offset

禁止只汇报 corrected 值。
4. Historical daily PnL
继续读取：
UTC day start → readiness cutoff
/fapi/v1/income

确认：
coverage.complete = true
daily_pnl_known = true

本次产生的 Testnet 活动如果发生在 cutoff 之后，应由本地/session accounting 路径承担，不能重新造成 historical/local 双计。
5. Recovery
活动结束、账户 flat 后重新做一次完整：
snapshot
→ reconcile
→ baseline
→ recovery

应能得到：
RECOVERED

若因 race 被 BLOCKED，可以重试，但不能跳过 RecoveryGate。
6. Readiness 最终报告
必须输出全部 evidence 和全部 blocker。
理想但不强求的预期：
PRIVATE_LATENCY_UNKNOWN   → 消失
MARKET_NOT_READY          → 消失
HISTORICAL_DRAWDOWN_UNKNOWN → 保留

如果出现新的 blocker，以真实结果为准，不要为了符合预期改 gate。
边界
包含
- 完整 Testnet public + private integration harness
- public market readiness evidence
- private business-event latency sample
- corrected clock latency
- Recovery rerun
- historical daily PnL bootstrap
- final LiveReadiness evaluation
- 最小 Testnet order activity
- current_state 版本表修正
不包含（关键）
- 不修改 MakerPolicy
- 不调用 Jev

- 不做主网订单
- 不做真实资金交易

- 不把裸 market_ready/mainnet_private_validated 的长期 typed-evidence 问题顺手重构
- 不进入 P0001.10
目录结构
尽量只允许：

/tmp/probex_live/
