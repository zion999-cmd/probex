# P0001.13：Execution Safety & Operations Surface

**状态**：已完成  
**授权**：人类当前会话明确指令（「已更新 proposals/P0001.13… , 你读取, 实施」）
**日期**：2026-09-29  
**依赖**：P0001.12.3

## 目标

把执行安全从内部机制升级成完整产品能力：

- 执行限额可感知
- 延迟可观测
- Reconciliation 可解释、可受控触发
- Execution Health 可统一判断
- Monitor / Activity / System / Performance 全部能看到
- Assistant 能解释并执行允许的 Runtime Action

不改变现有交易决策路径。

---

## 背景

当前已有：

```text
ExecutionEngine
OrderTracker
Reconciliation
ReadinessAuthority
RiskGate
Private latency
TradingRules
Assistant
Action Gateway
五 Surface
```

真实缺口包括：

- 无 rate-limit / order-rate governance
- venue rate/order limit 尚未捕获
- 无阶段化 execution latency
- 无统一 ExecutionHealth
- reconciliation 尚未产品化
- UI/Assistant 尚无完整执行安全上下文 :chatgpt-content-reference{index="0"}

## 设计

### 1. ExecutionSafetyPolicy

所有业务阈值**显式必填，无默认值**：

```text
near_limit_ratio
exhausted_ratio
order_rate_near_limit_ratio
venue_facts_max_age_ms

latency_budget_ms:
  decision_to_submit
  submit_to_ack
  cancel_to_ack
  event_receive_lag
  reconciliation_duration

latency_min_samples
latency_window_ms
reconciliation_required_after_unknown
health_rules
```

Policy 缺失：

```text
ExecutionHealth = UNKNOWN
Blocker = EXECUTION_POLICY_NOT_CONFIGURED
```

不得猜测。

---

### 2. Venue Limit Facts

统一产品事实：

```text
VenueLimitState
├── tick_size
├── step_size
├── min_qty
├── max_qty
├── min_notional
├── max_orders
├── request_weight_limit
├── order_rate_limit
├── source
├── observed_at
└── age_ms
```

现有 TradingRules 继续作为价格/数量规则事实来源。

rate/order limit 必须通过真实 Binance 响应验证后才接入；未确认：

```text
UNKNOWN
```

不能凭文档猜。当前代码确实尚未读取这些事实。:chatgpt-content-reference{index="1"}

---

### 3. RateLimitGovernor

Probex 自己拥有：

```text
request_budget
order_budget
used
remaining
reset_at
status
```

状态：

```text
HEALTHY
NEAR_LIMIT
EXHAUSTED
UNKNOWN
```

重要约束：

- 不自动 retry submit
- 不改变 UNKNOWN submit 语义
- 不创建第二执行路径
- 降险操作不能因为普通限流策略被锁死
- cancel/reconciliation 的安全语义单独处理

---

### 4. Execution Latency

正式定义：

```text
decision_to_submit
submit_to_ack
cancel_to_ack
event_receive_lag
reconciliation_duration
```

每个阶段暴露：

```text
p50
p95
max
sample_count
budget_ms
status
```

样本不足：

```text
UNKNOWN
```

不是 `0 ms`。

---

### 5. Execution Health

统一状态：

```text
HEALTHY
DEGRADED
BLOCKED
UNKNOWN
```

输入：

```text
rate_limit_state
venue_facts_state
latency_state
private_latency
uncertain_exposure
lost/unknown orders
reconciliation_state
```

`Readiness` 与 `ExecutionHealth` 保持两套语义：

```text
Readiness       = 是否有资格进入执行
ExecutionHealth = 当前执行子系统运行状况
```

不能合并。

只要任何 policy-required 来源 UNKNOWN，就不能显示 HEALTHY。

---

### 6. Reconciliation 产品化

已有 `ReconciliationReport` 继续作为 Owner。

Product 层暴露：

```text
state
last_run_at
reason
actions
converged
unknown_count
lost_count
```

Assistant / Action Manifest 中启用：

```text
runtime.request_reconciliation
```

属性：

```text
L2_RUNTIME
confirmation_required = true
```

仍通过现有：

```text
POST /api/v1/actions/<id>
```

不新增独立交易 POST API。:chatgpt-content-reference{index="2"}

## 成功标准

1. Venue trading rules 与 normalization 使用同一事实源。
2. rate/order limit 未确认时必须 UNKNOWN。
3. policy 缺失时 ExecutionHealth 不能显示 HEALTHY。
4. RateLimitGovernor 不产生 submit retry。
5. near/exhausted 状态可测试。
6. latency 五阶段定义稳定。
7. 样本不足保持 UNKNOWN。
8. ExecutionHealth 可解释其降级来源。
9. reconciliation 状态可在 UI/API/CLI 查看。
10. Assistant 能解释 execution blocker。
11. `request_reconciliation` 必须走 Action Gateway + confirmation。
12. Monitor 显示执行摘要。
13. System/Execution 显示完整事实。
14. Activity 可追踪订单到 reconciliation。
15. Performance 能看到 run 级执行安全指标。
16. Readiness 与 ExecutionHealth 不混用。
17. CAPITAL 继续 unavailable。
18. 不增加第二条交易写路径。
19. 降险操作不能被普通执行限额逻辑错误阻断。
20. 全量测试不回归。

## 实施记录（2026-09-29，已完成）

授权来源：人类当前会话明确指令（「已更新 proposals/P0001.13-… , 你读取, 实施」）。
硬要求遵守：**所有阈值来自配置**（`ExecutionSafetyPolicy` 无默认值），实现方未发明任何 limit / latency 数值。

### 落地内容

| 模块 | 内容 |
| --- | --- |
| `execution_safety/policy.py` | `ExecutionSafetyPolicy`：`near_limit_ratio` / `exhausted_ratio` / `order_rate_near_limit_ratio` / `venue_facts_max_age_ms` / `latency_budget_ms`（五阶段齐全）/ `latency_min_samples` / `latency_window_ms` / `reconciliation_required_after_unknown` / `health_rules`（每来源 severity + downgrades + required）。**全部必填、无默认值**；缺字段 / 数值非法 / 阶段或来源不全 ⇒ 构造即报错 |
| `execution_safety/venue.py` | `VenueLimitState`：价格/数量规则**复用 `TradingRules`**（与 normalization 同一事实源）；rate/order 限额来自注入的真实证据（`VenueRateLimitFacts`，含 `source` / `observed_at_ms`），未接入 ⇒ UNKNOWN，`max_orders` 交易所未给出 ⇒ UNKNOWN |
| `execution_safety/rate_limit.py` | `RateLimitGovernor`：request/order 两条 budget（limit/used/remaining/reset_at/status/source/window）；状态 `HEALTHY / NEAR_LIMIT / EXHAUSTED / UNKNOWN`；**无任何 retry 逻辑**（有测试固定）；只有 EXHAUSTED 才阻止新增暴露；**降险永不被阻断**（`allows_de_risking=True`） |
| `execution_safety/latency.py` | 五阶段固定定义 + `BoundedLatencyLog`（有界）+ `evaluate_latency`（p50/p95/max/sample_count/budget_ms/status）；样本不足 ⇒ UNKNOWN（**不是 0 ms**）；窗口由 policy 提供 |
| `execution_safety/health.py` | `evaluate_health`：四态合成，severity/downgrades/required 全部来自 policy；**任何 required 来源 UNKNOWN ⇒ 不得 HEALTHY**；返回可解释的降级来源；policy 缺失 ⇒ UNKNOWN + `EXECUTION_POLICY_NOT_CONFIGURED` |
| `execution_safety/projection.py` | 只读投影：`limits()` / `rate_limits()` / `latency()` / `reconciliation()` / `exposure()` / `health()` / `blockers()`；新增 `reconciliation_requester`（受控入口，可选注入） |
| `product/types.py` + `product/service.py` | `BlockerOwner` 新增 **EXECUTION / VENUE**；`SystemSnapshot.execution_safety` 新段；执行安全 blocker **合并进统一 `BlockerView`**（去重沿用既有契约） |
| `api/routes/execution_safety.py` + `api/server.py` | 6 个只读端点：`/api/v1/execution/{health,limits,rate-limits,latency,anomalies,reconciliation}`；未接线 ⇒ 503；policy 缺失时 rate-limits/latency ⇒ 503（不猜）；**无新增 POST** |
| `actions/manifest.py` + server | 新增 5 个 **L0 READ** 动作（`execution.health / limits / rate_limits / latency / anomalies`，由 server 幂等注册为只读 handler）；`runtime.request_reconciliation` 由 `UNAVAILABLE_NO_ENTRY_POINT` 升为 **AVAILABLE L2**（`confirmation_required=True`），handler 调既有 Owner |
| `assistant/context.py` + `assistant/service.py` | 上下文新增 `execution_health` / `rate_limit_state` / `venue_facts_state` / `latency_state` / `reconciliation_state` / `uncertain_exposure`；建议动作仍只来自 Manifest，并在出现 `RECONCILIATION_REQUIRED` blocker 时把受控 reconciliation 动作**前置**（显式规则） |
| `cli/main.py` | `probex execution {health,limits,rate-limits,latency,anomalies,reconciliation}`（`--json`、既有退出码）；`action invoke runtime.request_reconciliation [--confirm]` 复用既有 Action 命令 |
| `ui/` | System→Execution 七段（Venue Limits / Rate Limits / Latency / Reconciliation / Anomalies + 原 order 状态段）；Monitor 增加 Execution safety 摘要；Activity 增加执行 drill-down（含 normalization → submit → ack latency → reconciliation 链路）；`client/api.js` 增加 6 个端点 |
| `reports/builder.py` | `build_run_summary(..., execution_metrics=...)`：执行安全指标进入 `RunSummary.metrics`（同一 projection，不新建事实源） |

### 成功标准映射（真实证据）

| SC | 结论 |
| --- | --- |
| 1 venue rules 与 normalization 同源 | PASS：`limits.tick_size=0.1 / step_size=0.0001 / min_notional=50.0` 全部来自 `TradingRules`（测试 + 端点证据） |
| 2 rate/order limit 未确认必须 UNKNOWN | PASS：无证据时 `request_weight_limit`/`order_rate_limit`/`age_ms` 全 UNKNOWN，并产生 `VENUE_FACTS_UNAVAILABLE`(BLOCKING, owner=VENUE) |
| 3 policy 缺失不得 HEALTHY | PASS：`health.status=UNKNOWN` + reasons 含 `EXECUTION_POLICY_NOT_CONFIGURED`；rate-limits/latency 端点 503 |
| 4 governor 不产生 retry | PASS：`rate_limit.py` 无 `retry(`/`resubmit(`/`submit(`/`sleep(`（结构性测试） |
| 5 near/exhausted 可测试 | PASS：`used=850/1000 ⇒ NEAR_LIMIT`（仍允许新增暴露）、`used=990/1000 ⇒ EXHAUSTED`（阻止新增暴露，`allows_de_risking=True`） |
| 6 五阶段定义稳定 | PASS：`LATENCY_STAGES` 固定五段；policy 必须给出全部 budget（缺一即报错） |
| 7 样本不足保持 UNKNOWN | PASS：`status=UNKNOWN`、`p95.known=False`、reason 含 "not 0 ms" |
| 8 health 可解释降级来源 | PASS：`reasons=("latency_state:DEGRADED",)`、`source_status` 七来源逐项可见；超预算阶段产生 `SUBMIT_LATENCY_BUDGET_EXCEEDED`(`source_ref=execution.latency.submit_to_ack`) |
| 9 reconciliation 状态 UI/API/CLI 可见 | PASS：`/api/v1/execution/reconciliation` ⇒ `{state: CONVERGED, actions, converged, unknown_count, lost_count, required}`；snapshot 段同步 |
| 10 Assistant 能解释 execution blocker | PASS：上下文含 `execution_health=DEGRADED` 与 `rate_limit_state(known)`；建议动作含 5 个 `execution.*` 只读动作（来自 Manifest） |
| 11 `request_reconciliation` 走 Gateway + confirmation | PASS：Manifest `available=true` + `confirmation_required=true`；未确认 ⇒ **409 CONFIRMATION_REQUIRED 且既有 Owner 未被调用**；确认后 ⇒ **200 SUCCEEDED**（`{'requested': True}`），审计留痕 |
| 12 Monitor 显示执行摘要 | PASS：Monitor 新增 Execution safety 段（health / request budget / order budget / uncertain exposure / reconciliation） |
| 13 System/Execution 显示完整事实 | PASS：七段齐备（venue / rate / latency / order 状态 / unknown·lost / rejects / reconciliation + anomalies） |

| 15 Performance 可见 run 级执行指标 | PASS：`RunSummary.metrics["execution.*"]`（测试固定） |

### 仍待人类提供的输入（不阻塞本阶段，但决定投影何时能变绿）
