## 目标

把 Probex 先做成一个**真正可以本地运行、观察、复盘和理解**的量化交易产品：不依赖 Binance，用户在本地
Replay/PAPER 环境中，能完整看到一个策略从市场数据 → 决策 → Risk → Order → Fill → Position → Accounting → PnL →
UI → Run Review 的真实闭环；并补齐 UI/产品能力，使 Probex 不只是 API + 状态面板。

## 2. 产品验证层级（本阶段严格执行）

```
Replay Market Data → Market State → Feature/Indicator → Prediction（如已有） → Strategy Decision
→ RiskGate → ExecutionEngine → PaperBroker → OrderTracker → FillLedger → AccountingCore
→ Portfolio/PnL → Product Read Model → UI / Assistant / Run Review
```

之后才进入：Local → Binance Demo → Binance Testnet → Live。

## 3. 第一优先级：本地真实交易闭环

- 至少存在一个**可重复的本地 Replay/PAPER Run**：市场数据 → 策略产生真实 decision → Risk 判断 → PAPER 下单 →
  OrderTracker → 模拟成交 → FillLedger → Accounting → position/equity/PnL。
- **不得**用测试 fixture 直接拼最终结果；必须通过产品真实 runtime assembly 跑出来。
- 必须能回答"这一笔订单为什么产生"，并沿 Market → Feature → Prediction → Strategy → Decision → Risk → Order →
  Fill → Position → PnL 反查。

## 4. Strategy 能力补全

先审计：`MakerPolicy` / `RuntimeDecisionLoop` / `PredictionRuntime` / `FeatureEngine` / `RiskGate` / strategy 配置 /
trial profile。原则：**优先补接现有能力，不重新发明第二套 Strategy**。

- A. Strategy 真正运行：Replay/PAPER 中产生真实 `HOLD` / `PLACE`（等已有 decision 类型）+ decision reason +
  strategy identifier + decision timestamp + `decision_id`。
- B. 每个 decision 可解释：Strategy / Decision / Reason / Risk(ALLOW|REJECT) / Order 全链可见；
  禁止"系统自己下了单但 UI 不知道为什么"。
- C. 不得硬编码假策略结果（`if test: return PLACE` 之类）；contract 或 wiring 不足则先补 contract/wiring。

## 5. Market Workbench / K 线能力

不自己造 chart engine：先审计现有前端技术栈与依赖，在成熟开源方案（KLineCharts / Apache ECharts / 仓库现有栈）中
选最合理的一个。至少实现：K 线 OHLC / Volume / 时间轴 / 缩放 / 拖动 / 十字光标；基础指标至少 MA / EMA / VOL；
若 `FeatureEngine` 已有 VWAP / ATR，则把**已有计算结果**接入 UI（**不得**在 UI 重新计算业务指标）。

## 6. Strategy / Prediction 可视化

K 线之上必须能看到 Probex 自己的语义：Prediction（bullish/bearish）、Strategy Decision（BUY/SELL/HOLD）、
Risk（ALLOW/REJECT）、Orders（OPEN/FILLED/CANCELED），视觉形式由实现方按现有 UI 架构设计，但必须让用户把
"价格变化"与"系统为什么这样决定"放在同一时间轴上理解。

## 7. Activity / Decision Detail

Activity 不只是订单流水：点击一个 decision 至少能看到 Decision ID / Timestamp / Strategy / Instrument /
Reference price / Input facts（Prediction、Features）/ Decision（Action、Reason）/ Risk（Decision、Reason）/
Execution（Order ID、Status）/ Fill（Price、Qty）/ Accounting（Position、PnL）——形成因果链 UI。

## 8. Performance

至少补：Equity Curve（time → equity）、PnL（realized / unrealized / total）、Position（size / exposure）、
Trade statistics（若数据模型已支持 trades / win-loss / average PnL / drawdown）。不得为凑指标创造无真实来源的数据；
缺数据 ⇒ `UNKNOWN` / `NOT_AVAILABLE` 并说明原因。

## 9. Replay / Run Review

Replay 不只是播放数据：Run → 时间轴 → Market → Decision → Order → Fill → Position → Equity；用户能选择历史 Run、
查看 Run Summary 与时间轴、定位某个 Decision 与对应 Order/Fill、并在图表上看到对应时刻。已有 replay controller 就接起来，
**不重新造 Replay Engine**。

## 10. Assistant 补全

Assistant 只通过 Product Action Gateway / Product Read Model 工作；**不得**直接碰 Strategy / RiskGate /
ExecutionEngine / Binance connector / PaperBroker。至少要能解释："为什么刚才没有下单？"、"这笔订单为什么产生？"、
"当前策略是什么？"、"最近一次 decision 是什么？"、"这次 Run 表现怎么样？"、"这个位置为什么发生了交易？"。
从 Chart / Activity / Run Review 打开 Assistant 时，selected context 必须传入：
`selected_run` / `selected_timestamp` / `selected_symbol` / `selected_decision` / `selected_order` / `selected_fill`。

## 11. UI 五大 Surface 最终检查

Monitor（现在系统怎么样？）/ Market（市场发生了什么？）/ Activity（系统做了什么、为什么？）/
Performance（做得怎么样？）/ System（系统本身是否健康？）——每个 Surface 都必须由真实 Product Read Model 驱动，
**禁止 UI 自己推导交易事实**。

## 12. UI 原则

不允许"API 有字段 → UI 放个数字 → 就算完成"。每个页面都要检查：空状态 / UNKNOWN / reason / loading / error /
时间关系 / drill-down / 跨页面跳转 / selected context。

## 13. P0001.16 的处理

P0001.16 保持 **In Progress / Deferred**，不关闭；context 中明确记录"本阶段暂缓 Binance TESTNET 真实业务事件验收，
因为产品尚未进入真实交易验证阶段"。已完成的 connector/UNKNOWN/readiness/adapter/user stream/acceptance capability 全部保留，
但本阶段**不得**继续消耗主要开发时间等待真实 Binance private event。

## 14. 不包含

Binance Demo 接入 / Testnet 新的真实交易实验 / Live / Mainnet / 多交易所 / 多品种扩展 / Arbitrage / SOR /
自动资金管理 / 自动改 Risk 参数 —— 全部留到后续阶段。

## 15. 架构边界

严格保持 `Strategy → Risk → Execution → Broker/Connector`；不得出现 `UI → PaperBroker`、`UI → ExecutionEngine`、
`Assistant → Binance`、`Strategy → Binance`、`Product → Risk mutation`。同时：OrderTracker 仍是唯一 Order Owner；
AccountingCore 仍是唯一 Accounting Owner；RiskGate 仍是唯一 Risk Owner；Product 只是 projection；`UNKNOWN ≠ 0`；
不伪造事实；不新增第二套交易状态机 / 第二套 Accounting / 第二个 Execution path。

## 16. 测试要求

不只跑 unittest。至少：
- **A. 本地真实 E2E**：Replay → Strategy → Risk → PAPER Order → Fill → Accounting → Run；
- **B. UI E2E**：真实启动应用 + 浏览器验证 Monitor / Market / Activity / Performance / System / Decision detail /
  Run Review / Assistant；
- **C. 图表 E2E**：真实数据 Market data → backend read model → frontend chart（不得用纯 mock chart data 作为唯一证据）；
- **D. 因果链 E2E**：随机选至少一笔真实 PAPER trade，Decision → Order → Fill → Position → PnL 全部可反查。

## 17. 完成标准

1. 本地 Replay/PAPER 能完整跑出真实策略交易闭环；
2. 至少一笔真实 PAPER trade 可从 Decision 追到 Fill/Accounting；

12. 至少一次真实浏览器运行验证完成；

## 18. 推进方式（强制）

不再"做一个 → 报告 → 等补充 → 再做一个"。先**完整审计现状**，然后**一次性**完成本任务范围内所有必要的

# 实施记录（2026-10-04）

**状态**：实现中（本轮完成第 3 节核心闭环与 §16 A/C 的一部分；剩余 UI 细节见"仍未完成"）。

## 1. 本地真实交易闭环（§3 + §16 A/D）—— 已跑通

审计发现的 6 个真实缺口（全部修复）：

1. `execution/simulation/`（P0001.8 `SimulatedVenue`：队列近似/费率/延迟）**从未接线** ⇒ PAPER 永不自动成交；
2. trial profile **没有** `strategy.maker.*` / `risk.*` ⇒ 产品运行不产生 decision；
3. **时钟语义错位**（runtime=wall clock vs 市场/模拟器=数据时间）⇒ 撤单永不确认、成交错时；
4. **回放不节流**（1 小时数据数秒跑完）⇒ 决策环几乎没有交互机会；
5. 测试 fixture 的成交价印在**价差内部**（真实市场是主动方打 bid/ask）⇒ touch 报价永不成交；
6. smoke order helper 假设订单非终态；ack latency 只在 submit 路径采样（模拟器异步 ack）。

修复：显式 `simulation.enabled` + 既有 `SimulatedVenue` 接入**唯一** connector seam（feed 事件 sink 驱动）；
trial profile 补 `strategy.maker.*` / `risk.*` / `simulation.*` / `runtime.loop.*` / `feed.events_per_second`；
有 feed 时 runtime 时钟跟随**市场数据时间**；fixture 成交按真实微观结构打印；engine 在 poll 路径记录 accept 边界。

证据：`tests/integration/test_local_paper_loop_e2e.py`（约 5 秒确定性通过）——真实 PAPER 运行：
decision → Risk allow → 下单 → **事件级模拟成交** → OrderTracker FILLED → FillLedger/AccountingCore →
`position == 成交净额`、`fees > 0`、`equity` 反映成交 → 产品 snapshot + HTTP API + canonical correlation 因果链。
