## 1. 背景与问题定义

P0017.3 已交付单标的 event-driven 离线回测能力，包括：

* 确定性事件步进和历史数据回放；
* 策略决策、风险检查、模拟执行与会计处理；
* canonical run identity；
* manifest、summary、report 标准化产物；
* 双跑确定性与未来事件因果前缀测试；
* 与 Testnet/LIVE 写入路径的结构性隔离。

但 P0017.3 明确拒绝多标的输入，因此尚未验证多个标的同时参与交易时的完整组合行为。

P0017.2 的组合 gross-notional 硬闸已有独立验证，但这不能替代多标的回测端到端验证。

P0017.4 的核心问题是：

**当多个标的共享一个组合风险预算时，回测引擎能否在统一的事件时间线上，确定性地处理各标的行情、策略决策、订单执行、风险约束和组合会计，并且不因事件顺序、缺失行情或跨标的状态隔离问题而产生错误结果？**

## 2. 目标与非目标

### 2.1 本阶段目标

1. 支持一个数据集包含多个交易标的。
2. 为每个标的维护独立且正确隔离的市场可见状态及必要的特征状态。
3. 让所有标的共享统一的组合级风险预算。
4. 将各标的订单、成交、持仓和费用纳入一致的组合级结果。
5. 对同一时间戳的跨标的事件建立明确、可复现的处理规则。
6. 对缺失或无法估值的非空仓位采取安全的 fail-closed 处理。
7. 证明多标的回测的确定性、因果性、风险约束和会计完整性。
8. 保持单标的回测的既有语义与结果不发生非预期变化。

### 2.2 明确不在本阶段实现的能力

* BAR/OHLCV 回测与 K 线撮合；
* 滑点、funding、taker fee、market impact 等尚未实现的成本模型；
* 真实订单簿队列校准；
* 多策略组合、策略间资本分配及策略优化；
* 并行或分布式回测；
* Testnet/LIVE 实盘下单；
* 以回测收益证明未来盈利能力。

这些能力继续作为独立后续提案，不得在 P0017.4 中顺手扩展。

## 3. 核心架构原则

### 3.1 多标的市场状态隔离

每个标的必须具有明确的状态边界。

概念上：

* Symbol A → 独立的可见行情状态、特征状态和模拟执行状态；
* Symbol B → 独立的可见行情状态、特征状态和模拟执行状态；
* 所有标的 → 共享组合风险预算及统一的组合级结果。

上述组件如何实例化，必须先以现有代码中的真实接口为准。不得为了满足概念架构而复制整套引擎，也不得假定现有组件天然支持多实例或共享状态。

任何一个标的的未来事件，都不能提前污染另一个标的在当前决策时刻可见的状态。

### 3.2 组合级风险预算

组合 gross-notional 风险闸门必须在跨标的订单共同参与的执行链路中生效。

必须验证：

* 各标的已有持仓共同计入组合 gross exposure；
* 各标的待处理订单按 P0017.2 已定义的规则计入或限制暴露；
* 不能通过拆分到不同标的绕过组合限额；
* 风险拒绝不会产生实际成交、错误持仓或会计副作用；
* 非空仓位缺少必要估值时，不能因为忽略该标的而低估组合风险；
* 空仓位不存在估值缺口时，不应被错误地当作未知风险。

本阶段不得重新定义 P0017.2 的风险语义。如果发现原有契约不足以支持多标的回测，必须先报告差异并单独评估，不得静默更改。

### 3.3 统一事件时间线

所有标的事件必须进入同一个确定性的回放机制。

处理规则必须明确：

1. 事件时间的解释与时区约定；
2. 相同时间戳事件的排序规则；
3. 事件顺序与可见状态更新的关系；
4. 决策发生时能够读取哪些行情；
5. 订单提交、成交、持仓更新及风险重新检查的顺序。

如果原始数据包含可靠的事件序号或源顺序，应根据其实际语义制定规则。如果现有输入不能提供足以确定顺序的信息，必须在 Batch 0 识别并提出明确契约；不得依赖哈希遍历顺序、线程调度或其他不稳定因素。

相同时间戳的处理规则不能在实现中隐式决定。事件顺序可能影响先处理的订单是否占用剩余组合预算，因此它属于策略实验语义，而不只是性能实现细节。

### 3.4 共享组合结果与会计一致性

回测结果应同时提供：

* 组合级订单、成交、持仓及权益结果；
* 各标的的订单、成交、持仓和费用归属；
* 可以核对组合与标的明细之间关系的完整性检查。

必须先核实 AccountingCore 的实际会计模型，再确定实现方式。若现有会计核心不支持所需的多标的语义，应先设计最小兼容扩展，而不是在报告层拼接多个彼此独立、可能互相矛盾的会计结果。

所有汇总指标必须基于明确、可复现的计算规则。不得将各标的的百分比收益简单相加并冒充组合收益。

### 3.5 确定性与因果性

同一份规范化输入、配置、代码版本及必要的运行参数，应产生相同的核心执行结果。

同一数据集前缀在追加未来事件后，其既有事件范围内的决策、订单、成交及会计结果必须保持一致；如果实现语义存在例外，必须在设计中明确说明并给出可验证的边界。

确定性不能只依赖相同的汇总收益或相同的订单数量，必须比较核心内容。

## 4. 输入与配置契约

P0017.4 继续使用 P0017.3 已支持的 event-store JSONL 作为正式输入，不将新的 market-dataset 格式作为强制依赖。

Batch 0 必须确认并记录：

* 当前事件 schema 如何表达 symbol；
* 不同标的事件如何进入统一回放；
* 时间戳、事件序号及重复事件的处理语义；
* 多标的配置与现有单标的配置之间的兼容方式；
* 各标的必要市场状态和估值数据如何验证；
* 数据集身份、规范化及内容哈希的实际规则。

配置必须能够明确表达本次回测包含哪些标的，以及组合风险限额。

未知标的、配置与输入不一致、无法解释的事件顺序或必要字段缺失，必须产生明确且可诊断的失败结果，不得自动丢弃数据后继续给出貌似有效的回测结果。

具体错误分类必须复用并核对 P0017.3 的既有状态契约，不得随意增加状态或混淆输入错误与执行完整性错误。

## 5. 输出与报告

继续沿用 P0017.3 的产物体系：

* `manifest.json`
* `summary.json`
* `report.md`

在保持原有字段兼容性的前提下，新增或扩展多标的相关字段。

至少需要记录：

* 本次运行的完整标的集合；
* 各标的的数据与验证状态；
* 组合 gross exposure 的关键统计；
* 组合限额及其实际启用状态；
* 各标的订单与成交统计；
* 组合级及标的级会计指标；
* 风险拒绝的数量和原因；
* 数据、配置、代码版本及规范化运行身份；
* 尚未支持的成本模型及其他能力限制；
* 完整性检查结果。

报告不得仅因配置包含多个标的，就声称组合级风险预算已通过验证。只有实际执行并通过相应测试的能力，才能标记为已验证。

### Batch 2 — Portfolio Risk Integration

将多个标的纳入同一个组合 gross-notional 风险预算。

* 风险闸门在完整回测执行链路中得到端到端验证。

### Batch 3 — Accounting & Result Integrity

建立组合级与标的级会计结果之间的可核对关系。

验收重点：

* 成交与持仓变化一致；
* 费用归属与汇总正确；
* 组合级指标可从明确的会计规则中复现；
* 结束时不虚构成交、不强行平仓、不捏造收盘价；
* 完整性检查失败时不会输出被误标为成功的结果。

### Batch 4 — Determinism, Causality & Reporting

升级运行身份、结果完整性检查及报告。

验收重点：

* 追加未来事件，既有结果前缀保持一致；
* 同时间戳事件按既定规则确定性执行；
* 组合与标的级结果均可追溯；

## 7. 强制验收原则

最终验收报告必须逐项列出标准、证据、测试名称或代码位置及结论。

至少覆盖以下类别：

**A. 输入与事件契约**

* 多标的输入正确解析；
* 非法或不完整输入被拒绝；
* 同时间戳排序规则明确且确定；
* 标的状态隔离成立。

**B. 因果性与确定性**

* 不存在 look-ahead；
* 相同输入双跑的核心结果一致；
* 未来事件追加不改变既有结果前缀；
* 输入顺序与规范化语义一致。

**C. 组合风险**

* 多标的累计暴露受组合限额约束；
* 待处理订单不能绕过预算；
* 风险拒绝无错误副作用；
* 未知估值不会导致风险低估。

**D. 会计与执行**

* 订单、成交、持仓及费用关系一致；
* 组合与标的级汇总可以核对；
* 终态语义正确；
* 失败结果不会被报告为成功。

**E. 运行隔离与可复现性**

* 离线回测不依赖真实交易凭据或网络下单；
* Testnet/LIVE 写路径在结构上不可达；
* 运行身份和报告足以追溯输入、配置与代码版本。

**F. 兼容性与收口**

* 单标的既有测试无非预期回归；
* 所有能力声明与实际测试一致；
* B 类边界、C 类优化及未验证能力有明确记录；
* 最终 Closure Audit 完成。
