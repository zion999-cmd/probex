## 1. 任务目标

建立一个正式的离线回测执行入口，使系统能够使用固定的历史事件数据，在不连接交易所写接口、不启动真实交易路径的情况下，完整执行：

历史事件输入 → 确定性事件步进 → 策略决策 → 风险检查 → 模拟订单提交 → 模拟成交 → 会计更新 → 结果校验 → 评估报告。

第一版必须解决五个问题：

1. **确定性：** 相同代码版本、数据、配置和随机种子，应产生等价的执行轨迹和评估结果。
2. **因果性：** 每次决策只能使用当时已经可见的市场信息，不得读取未来事件。
3. **风险一致性：** 复用现有单标的 RiskGate 与 P0017.2 组合 gross-notional 硬闸，不得绕过风险约束。
4. **会计完整性：** 成交、持仓、费用、现金及评估指标必须能够相互核对；不完整或矛盾的运行不得伪装成成功。
5. **结果可追溯：** 每次运行都有明确的输入身份、配置身份、代码版本、执行状态和机器可读报告。

本任务是现有交易系统的**离线执行与评估能力建设**，不是新建策略框架，也不是建设通用金融回测平台。

## 2. 设计原则与不可突破的边界

### 2.1 复用优先

必须优先复用仓库中已有且经测试的：

* `SimulatedVenue`
* `ReplaySource`
* 现有策略决策路径及 `MakerPolicy`
* `RiskGate`
* P0017.2 组合预算第二道闸
* `AccountingCore`
* `FillLedger`
* `metrics/RunSummary` 及已有评估指标

上述组件的真实路径、接口和行为必须以只读审计确认的代码为准。本文中的名称是能力指引，不授权擅自假定接口。

允许新增一个独立的 Backtest Driver、运行上下文、manifest、结果校验器和报告生成器。

禁止复制一套独立的风险引擎、会计引擎、策略框架或模拟交易所来替代现有底座。

如果现有组件的接口无法支持确定性执行，应优先设计最小适配层；只有在确认无法通过组合或适配解决时，才提出修改现有组件的独立方案。

### 2.2 交易安全边界

Backtest Driver 必须在构造和依赖注入层面与真实交易写路径隔离。

* 不允许调用交易所下单、撤单或其他具有真实交易副作用的接口。
* 不允许因配置错误而自动降级到 Testnet 或 LIVE。
* 不允许复用会隐式启动真实交易服务的通用 assembly，除非能以结构性证据证明相关写路径不可达。
* 不允许通过环境变量、配置文件或命令参数把模拟执行切换为真实交易执行。
* 不允许在测试失败、输入损坏或会计校验失败时仍然生成状态为成功的正式报告。

禁止真实交易必须由代码结构和自动化测试共同证明，不能仅依赖“没有配置 API Key”或“运行时没有实际下单”的经验判断。

P0017.2 的 Testnet/LIVE 组合预算能力缺口不属于本任务。不得把 PAPER 或离线回测的风险保护结论外推到这些路径。

### 2.3 范围纪律

第一版不实现：

* OHLCV/bar-based 撮合。
* 基于历史逐笔成交数据的完整市场冲击模型。
* 真实订单簿队列位置的历史重建，除非现有输入已明确提供所需证据。
* 参数优化、网格搜索、策略自动选择。
* 资金费率模型，除非现有事件 fixture 已提供完整且可核对的相关数据和语义。
* 新的策略 DSL 或新的策略开发框架。
* Testnet/LIVE 的组合预算接入。
* MakerPolicy 组合额度 sizing 优化（P0017.2 的独立 C 类优化项）。

不允许为了使验收通过而降低既有风险检查、放宽输入校验或静默填补缺失数据。

## 3. 第一版执行粒度：事件驱动

### 3.1 正式决策

第一版采用 **event-driven replay**，不实现 bar-based backtest。

输入事件必须具备足够的信息来支持现有 `ReplaySource` 和 `SimulatedVenue` 的执行语义。具体必需字段由实际代码契约确定，并在实施前列明。

如果输入只有 OHLCV bar，或者其数据粒度无法支持当前执行模型所要求的行为，运行必须返回：

`UNSUPPORTED_CAPABILITY`

不得把 bar 数据转换成虚构的逐笔行情、订单簿变化或队列事件，也不得把 bar 收盘价撮合结果描述为事件级 maker 执行精度。

### 3.2 执行保真度声明

报告必须说明：

* 实际输入数据的类型和粒度。
* 实际启用的成交模型。
* 实际启用的手续费和其他成本模型。
* 是否有可用的队列、延迟和订单簿证据。
* 哪些执行行为是模型模拟，哪些无法从输入数据中验证。

即使复用了 `SimulatedVenue` 中已有的 maker 成交、队列、费用或延迟机制，也不能自动宣称回测与真实市场执行完全一致。

测试证明的是实现遵守了模型规则，不代表模型本身完整还原真实市场。

## 4. 输入契约

### 4.1 第一版输入

第一版以现有 `ReplaySource` 支持的 **event-store JSONL** 为正式回测输入。

可选的 market-dataset 输入不属于首版强制能力。只有在差距审计确认其现有契约完整、且无需引入另一套数据解释逻辑时，才允许作为兼容适配器纳入同一批次；否则明确延后。

不得仅因为仓库中存在名为 dataset 的模块，就认定其已满足回测输入要求。

### 4.2 输入完整性

在开始运行前，必须验证：

* 输入文件存在且可读取。
* 每条记录符合声明的事件 schema。
* 时间戳、symbol、事件类型及必需字段有效。
* 事件排序符合既定排序规则，或可通过确定性规则进行规范化。
* 不存在无法解释的重复事件、冲突事件或无效状态转换。
* 事件来源、时间戳语义和数据粒度能够满足回放要求。
* 输入不存在运行中被静默修改的情况。

对无法安全规范化的输入，不得猜测修复，应返回 `INVALID_INPUT` 或 `INTEGRITY_FAILURE`，具体依据失败性质决定。

### 4.3 数据集身份

每次运行必须对实际使用的输入内容计算稳定的内容 hash。

* 同一路径、相同内容，应具有相同的数据集身份。
* 相同路径但内容变化，应具有不同的数据集身份。
* 不得只使用文件名、路径、修改时间或记录数量作为数据集身份。
* 多文件输入必须定义稳定的文件清单和规范化顺序。
* 若数据集包含外部引用，必须记录实际引用的内容身份；无法固定其内容的输入不得声称完全可复现。

数据集 hash 的算法、编码方式及多文件组合规则必须在实现中固定并测试。

## 5. 确定性 Backtest Driver

### 5.1 核心职责

新增独立的 Backtest Driver，统一负责：

1. 验证输入和运行配置。
2. 构造离线专用运行上下文。
3. 初始化模拟执行、风险、会计和评估组件。
4. 按确定性顺序读取历史事件。
5. 更新可见市场状态。
6. 在指定事件边界同步执行策略决策。
7. 依次执行风险检查和模拟订单提交。
8. 驱动模拟成交、订单状态更新和会计处理。
9. 在规定边界执行会计及运行完整性校验。
10. 生成 manifest、结果文件及最终状态。

Driver 是回测执行的唯一编排入口，不应依赖 PAPER 模式中的 wall-clock 调度、后台线程轮询或真实时间节流。

### 5.2 固定执行顺序

在实际组件接口允许的前提下，采用以下逻辑顺序：

`Read Event → Advance Visible State → Decide → Risk Gate → Simulated Submit → Venue Poll/Fill Processing → Accounting → Invariant Checks`

具体事件边界必须结合现有 `ReplaySource` 和 `SimulatedVenue` 的真实语义确定。

如果某一事件类型必须先处理订单状态、成交或会计更新，才能正确推进后续决策，则必须显式规定该事件的处理顺序，并用测试验证。

不得为了符合上述示意顺序而破坏现有模拟交易所的合法状态转换。

### 5.3 事件排序

必须建立确定性的事件排序契约。

至少明确：

* 主排序时间字段及其含义。
* 同一时间戳事件的稳定排序规则。
* 相同排序键的处理方式。
* 行情更新、订单生命周期事件、成交事件与决策触发事件之间的优先级。
* 延迟事件和队列事件如何推进模拟时间。
* 结束时尚未完成的订单如何处理。

不得依赖文件系统遍历顺序、Python 容器偶然顺序、线程调度或 wall-clock 竞争来决定执行结果。

如果现有事件缺少足以确定合法先后关系的信息，必须拒绝相关输入或明确标注不支持，不得以任意排序掩盖语义缺失。

### 5.4 时间语义与因果性

必须区分并正确使用现有模型中适用的时间概念：

* **Event Time：** 事件实际对应的市场时间。
* **Availability Time：** 事件何时可被系统观察到。
* **Decision Time：** 策略何时形成决策。
* **Submission Time：** 订单何时提交给模拟执行器。
* **Execution Time：** 模拟成交何时发生。

若现有数据只提供其中部分时间字段，必须明确缺失项的处理规则，不得伪造精度。

策略决策在时间 \(t\) 只能读取在 \(t\) 时刻之前或按明确规则于该决策边界可见的信息。

未来事件不得提前写入策略可见状态。仅仅按时间戳排序并不足以证明不存在 look-ahead。

必须增加自动化因果测试，包括但不限于：

* 在未来追加一个事件，不应改变此前已完成的决策轨迹。
* 未来价格变化不得影响此前的策略输入。
* 未来成交、订单状态或会计信息不得提前暴露给策略。
* 同一时间戳事件按照已声明的边界规则处理，不得依赖输入偶然顺序。
* 延迟或队列推进不得使尚未到达的事件提前可见。

若追加未来事件依法会影响最终运行结果，这是允许的；但不得改变其到达之前已经确定的决策与执行历史。

### 5.5 随机性

凡影响运行结果的随机过程，都必须具有显式种子或明确声明为确定性的实现。

* 不得使用无法控制的隐式随机性。
* 相同 seed、输入、配置和代码版本必须产生等价结果。
* 不同 seed 不保证结果必然不同，但必须在 manifest 中准确记录实际使用的 seed。
* 若执行路径不使用随机数，应记录为未使用，而不是虚构一个有效随机参数。

### 5.6 运行结束

Driver 必须定义结束语义。

结束时应检查是否仍有未完成订单、待处理事件、未结算成交或其他影响最终结果的状态。

第一版不得静默丢弃这些状态。必须按现有模拟执行模型选择明确且可测试的处理方式：

* 按历史输入继续推进，直至规定的自然结束边界。
* 以明确规则取消或终止未完成订单，并记录其影响。
* 如果无法安全确定最终状态，则标记运行不完整。

不得在缺乏历史价格或明确估值规则时，虚构最终成交价或强行平仓。

## 6. 风险控制集成

### 6.1 复用现有风险路径

所有策略订单必须经过现有 RiskGate 及 P0017.2 组合预算硬闸。

组合预算启用时，必须保持以下行为：

* 单标的风险检查仍然有效。
* 组合 gross-notional 限额仍然有效。
* 持仓与在途订单的暴露不能重复计算。
* 不可量化的必要暴露必须 fail-closed。
* 被风险拒绝的订单不得进入模拟订单跟踪器，也不得产生成交或会计副作用。
* 组合限额未配置时，必须显式记录组合预算未启用，不能宣称其已提供保护。

回测不能因为使用固定历史数据，就跳过实时决策路径原有的风险约束。

### 6.2 风险与会计一致性

必须验证以下行为：

* 被拒绝的订单不会进入模拟成交流程。
* 被拒绝的订单不会改变持仓、现金、成交账本或费用。
* 已提交订单在成交、部分成交、撤单和结束处理中的暴露变化符合现有状态机语义。
* 部分成交的持仓暴露与剩余在途订单暴露能够正确衔接。
* 缺失必要 mark 时，不得通过跳过持仓或使用零值降低组合暴露。

P0017.2 已验收的风险行为应作为本阶段复用的既有契约，而不是重新实现一套近似版本。

## 7. 执行成本与模型能力声明

### 7.1 第一版成本模型

第一版复用现有模拟执行模型已经支持并可核实的 maker fee 机制。

**第一版不加入新的固定 bps slippage 模型。**

原因是当前任务的首要目标是建立可信的执行和评估闭环，而不是人为增加一个成本参数来制造“更真实”的回测结果。固定 bps 只是一种成本假设，并不能自动代表真实市场冲击。

### 7.2 滑点处理

第一版报告必须明确声明：

`slippage_model = UNSUPPORTED`

这表示第一版没有实现独立、可验证的滑点模型，不表示实际交易滑点为零。

如果现有模拟执行器已经存在与延迟、队列或价格变化相关的执行行为，报告应准确描述这些行为，但不得将它们直接等同于完整滑点模型。

不得把未建模的成本以零成本、零滑点的形式隐式呈现为已验证结果。

### 7.3 其他成本

* 仅当现有模型或输入数据能够支持时，才计入相应成本。
* 不得臆造 funding、borrow cost、market impact 或其他费用。
* 第一版不新增资金费率模型。
* 对于未实现的成本项，报告应标注 `UNSUPPORTED` 或 `NOT_MODELED`，而不是伪造数值。
* 已启用的成本项必须有明确的计算依据和会计归属，避免重复扣费。

如果某项成本对所声明的评估目标不可或缺，而现有数据又不支持它，则该项评估不得被描述为完整的现实收益预测。

## 8. 会计完整性与结果校验

### 8.1 复用既有会计底座

必须使用现有 `AccountingCore`、`FillLedger` 及相应状态更新路径。

不得另行维护一套与现有会计系统独立、无法核对的“回测持仓”或“回测收益”账本。

如果评估层需要派生数据，应从已确认的权威状态和成交记录中生成。

### 8.2 强制一致性检查

实际可核对的项目至少包括：

* 订单提交记录与模拟订单状态。
* 模拟成交记录与 `FillLedger`。
* 成交数量、方向和价格与持仓变化。
* 成交费用与费用记账。
* 持仓、现金和权益之间的会计关系。
* 在途订单、已成交数量与剩余数量的关系。
* 已拒绝订单与交易、会计副作用之间的隔离。
* 运行结束时的未完成订单和未结算状态。
* 评估指标使用的数据与权威会计结果的一致性。

具体恒等式、舍入容差及币种处理必须根据现有会计模型确定，并在实施计划中逐项列出。

不得在没有真实模型依据的情况下假设现金、保证金、权益和持仓估值可以直接使用某个通用公式替代。

### 8.3 失败优先于报告成功

任何强制完整性检查失败，都不得输出 `SUCCESS`。

可以生成诊断报告，但必须明确标注失败状态，并防止下游消费者将其误认为有效的成功回测。

不得通过捕获异常后继续计算、填补缺失会计数据或忽略不一致项来生成貌似完整的收益曲线。

## 9. 运行身份与可复现性

### 9.1 Run Manifest

每次运行必须生成机器可读的 manifest，至少包含：

* manifest schema 版本。
* 回测实现版本。
* Git commit。
* 工作树是否干净；若不干净，必须记录相关状态，并按照运行策略拒绝或明确标记非规范运行。
* 输入数据集的内容 hash。
* 实际使用的输入文件清单及其身份。
* 完整生效配置及其规范化 hash。
* 随机种子或无随机性的声明。
* 执行粒度。
* 成交模型版本。
* 已启用成本模型及未支持的成本项。
* 运行开始和结束状态。
* 结果文件及其内容 hash。
* 必要的运行环境与依赖版本信息。

不得仅记录配置文件路径而不记录生效配置内容。

不得把未提交的代码与已提交代码视为同一规范版本。

### 9.2 Canonical Run Identity

必须定义稳定的 `run_id` 生成规则。

`run_id` 至少应受以下因素影响：

* 代码版本。
* 数据集内容身份。
* 生效配置。
* seed。
* 影响执行语义的模型版本和 schema 版本。

只改变输出目录或日志位置，不应改变回测的逻辑身份。

改变输入内容、风险配置、策略参数、seed 或执行模型版本，应当在影响结果时反映到 run identity 中。

规范化规则必须明确处理字段顺序、浮点数序列化、默认配置展开和缺省值。不能依赖普通 JSON 文本的偶然格式生成身份。

### 9.3 双跑等价

必须提供固定 fixture 的双跑测试。

在相同代码、输入、配置、seed 和环境契约下，两次运行必须满足：

* 相同的规范化 run identity。
* 相同的决策、风险判定、订单状态和成交轨迹。
* 相同的会计终态。
* 相同的评估指标。
* 相同的规范化结果内容 hash。

允许非语义性的运行时间、临时路径或日志顺序元数据不同，但这些字段必须与规范化结果分离，不得导致核心结果 hash 改变。

不能仅以“收益数值接近”作为确定性验收标准。

## 10. 运行结果状态机

每次运行必须且只能处于以下六种最终状态之一：

| 状态                       | 含义                          |
| ------------------------ | --------------------------- |
| `SUCCESS`                | 输入、回放、风险、会计和强制完整性检查全部通过     |
| `INVALID_INPUT`          | 输入格式、字段、时间语义或配置不满足输入契约      |
| `UNSUPPORTED_CAPABILITY` | 请求的执行粒度、成本模型或其他能力超出第一版支持范围  |
| `INTEGRITY_FAILURE`      | 数据、manifest、账本、会计或结果一致性检查失败 |
| `REPLAY_FAILURE`         | 执行过程中发生无法继续的回放、状态机或组件错误     |
| `INCOMPLETE`             | 执行未能完成规定的结束与结算流程，无法证明最终结果完整 |

失败状态不能被覆盖成成功状态。

每个失败结果必须记录：

* 最终状态。
* 稳定的失败类别或 reason code。
* 可定位的失败位置或事件标识（如果存在）。
* 已完成和未完成的执行阶段。
* 是否生成诊断产物。
* 哪些结果字段可信，哪些不可用。

只有 `SUCCESS` 才能被正式评估流程作为成功回测纳入统计。

## 11. 评估报告

### 11.1 交付物

每次运行至少产生：

1. `manifest.json`：规范运行身份与执行配置。
2. `summary.json`：机器可读的运行状态、指标、完整性检查和能力声明。
3. `report.md`：面向研究和工程审查的可读报告。
4. 必要的诊断产物：错误记录、校验结果或规范化轨迹摘要。

实际文件布局可以在实施计划中固定，但不能改变上述交付契约。

### 11.2 必须覆盖的报告内容

**运行身份**

* run ID。
* 代码版本。
* 数据集身份。
* 生效配置身份。
* seed。
* 最终状态。

**策略与交易结果**

* 已完成的决策和订单统计。
* 成交数量与成交量。
* 已实现及未实现收益（仅在现有会计模型支持时）。
* 费用及其构成。
* 期末持仓与相关估值状态。

**风险**

* 风险拒绝次数与分类。
* 组合预算启用状态。
* 组合暴露与限额信息（在相关数据可用时）。
* 运行中出现的完整性问题。

**执行质量**

* 订单提交、成交、部分成交、撤单和未完成订单统计。
* 可用的延迟、队列或 maker 执行统计。
* 成本模型启用情况。
* 未建模的滑点和其他成本声明。

**数据与可信度**

* 输入事件数量。
* 实际处理的事件数量。
* 数据集 hash。
* 会计一致性检查结果。
* 确定性双跑测试或规范化结果身份。
* 不支持的能力及适用边界。

**限制声明**

报告必须清楚说明：结果是给定历史事件、策略、执行模型和成本假设下的模拟结果，不是对真实市场成交或未来收益的保证。

不得只生成一张收益曲线就宣称回测完成。

### 11.3 指标边界

复用现有 `RunSummary` 和指标实现。不得为了让报告显得完整而随意添加未经定义的指标。

任何新增指标都必须具有明确的输入、公式、边界条件和测试。

如果现有数据不足以可靠计算某项指标，则报告该项不可用及其原因，而不是填零。

## 12. 命令行入口

第一版采用独立的离线子命令：

`probex backtest --dataset <path> --config <path> --out <path>`

以上为目标接口。实施前必须核对仓库现有 CLI 的真实结构，并在保持语义不变的情况下采用与现有命令体系一致的参数名称。

命令必须：

* 明确指定输入、配置和输出位置。
* 在执行前验证输入和配置。
* 生成规定的 manifest、summary 和可读报告。
* 以退出码区分成功与失败。
* 不因输入无效而产生 `SUCCESS`。
* 不自动连接真实交易所写路径。
* 不隐式启用 Testnet 或 LIVE。
* 不覆盖其他 run 的结果，除非存在明确的覆盖规则和授权。

同一 run 的输出目录和重复执行策略必须明确，不能由偶然的文件覆盖行为决定。

命令行只负责参数解析、运行构造和结果交付；核心回测逻辑必须存在于可独立测试的 Driver 中，不能全部堆在 CLI handler 内。

## 14. 强制验收标准

以下所有标准均为强制要求。具体测试文件和测试名称由实施计划根据实际仓库确定。

### A. 输入与契约

* A01：合法 event-store JSONL 可完成回测。
* A02：无效 schema 被拒绝，状态为 `INVALID_INPUT`。
* A03：不支持的 bar-only 输入返回 `UNSUPPORTED_CAPABILITY`。
* A04：损坏、冲突或无法安全排序的输入不会被静默修复。
* A05：相同数据内容得到相同数据集身份。
* A06：数据内容改变会改变数据集身份。

### B. Driver 与确定性

* B01：回测不依赖 wall-clock 节流、后台线程或轮询等待来决定事件顺序。
* B02：事件顺序遵循冻结的排序契约。
* B03：未来事件不可提前进入策略可见状态。
* B04：相同输入、配置、seed 和代码产生等价执行轨迹。
* B05：相同时间戳的事件具有确定性处理规则。
* B06：运行结束时的订单和事件状态按既定规则处理。
* B07：失败不会被转换为成功状态。

### C. 风险与交易安全

* C01：所有候选订单经过现有单标的风险检查。
* C02：启用组合预算时，所有候选订单经过 P0017.2 组合硬闸。
* C03：组合 gross-notional 限额不能被多标的订单累计绕过。
* C04：必要持仓缺失 mark 时，跨标的候选订单 fail-closed。
* C05：被拒绝的订单不进入模拟订单跟踪器。
* C06：被拒绝的订单不产生成交或会计副作用。
* C07：Testnet/LIVE 写路径在回测构造与执行中不可达。
* C08：无 API Key 或无网络条件不是唯一的交易安全证明。

### D. 会计完整性

* D01：模拟成交与 `FillLedger` 一致。
* D02：成交数量与持仓变化一致。
* D03：费用只按声明的模型记账，不重复扣除。
* D04：部分成交、剩余数量与在途暴露一致。
* D05：订单终态与会计状态符合现有状态机契约。
* D06：缺失必要估值信息时，不伪造权益或最终收益。
* D07：会计不一致导致 `INTEGRITY_FAILURE`。
* D08：未完成的最终结算导致 `INCOMPLETE` 或其他符合冻结契约的非成功状态。

### E. Manifest 与评估

* E01：每次运行生成 manifest。
* E02：manifest 包含代码、数据、配置、seed 和模型版本身份。
* E03：相同规范输入得到相同 run identity。
* E04：影响结果的输入变化反映到 run identity。
* E05：固定 fixture 双跑得到等价的规范化结果。
* E06：机器可读 summary 与可读报告相互一致。
* E07：失败运行不会进入成功回测统计。
* E08：未实现的滑点与其他成本被显式声明。
* E09：报告明确区分模拟结果、模型假设与未验证能力。

### F. CLI 与工程验收

* F01：存在独立的 `probex backtest` 命令。
* F02：CLI 参数错误和输入错误具有明确的失败语义。
* F03：重复运行不会静默覆盖不相关的历史结果。
* F04：回测逻辑可以脱离 CLI 独立测试。
* F05：所有相关测试在干净 checkout 中通过。
* F06：验收报告包含真实测试命令、结果和失败项。
* F07：没有用测试跳过、放宽断言或关闭风险检查来换取通过。

**验收门槛：所有适用的强制标准必须 PASS。** 如果某项因环境或外部条件无法运行，应如实标记 `NOT RUN`，并说明它是否阻塞本阶段承诺能力的验收。不能把 `NOT RUN` 计作 `PASS`。
