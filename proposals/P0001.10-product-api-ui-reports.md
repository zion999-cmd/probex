P0001.10：Product API / UI / Reports
状态：已完成
日期：2026-09-29
依赖：P0001.1 ～ P0001.9.7.2
目标
把现有 Probex 内核暴露成稳定、可观察、可审计的产品接口。
本阶段解决三个问题：
1. 人能看到系统现在发生了什么。
2. 外部工具能通过稳定 API 读取系统事实。
3. Replay / Paper / Testnet Live 可以用同一种产品语义展示。
P0001.10 不新增交易智能，只包装已有 Owner 的事实。
背景
当前核心链已经完整：
Market
→ MarketState
→ Prediction
→ MakerPolicy
→ Risk
→ Execution
→ Accounting

并已有：
Replay
Paper
Simulation
Testnet Live
Readiness
Recovery
Reconciliation

现在的问题不是“缺算法”，而是这些能力仍主要存在于 Python 模块、测试和 harness 中。
缺少稳定的：
Product API
Read Model
Runtime Status
Evidence View
Human UI
Run Report

这也是后续接 Freqtrade / Hummingbot / lob-engine 前必须先固定的产品边界。
架构
Existing Domain Owners
        │
        ├─ Market
        ├─ Prediction
        ├─ Strategy
        ├─ Risk
        ├─ Execution
        ├─ Accounting
        └─ Readiness
        │
        ▼
Product Read Model
        │
        ▼
Product API
        │
        ├───────────────┐
        ▼               ▼
      Web UI          Reports

关键原则：
Product layer does not own trading truth.

Product API 只组合事实，不重新计算事实。
设计
1. Product Read Model
增加独立产品层：
product/
    model.py
    service.py

统一读取现有 Owner，生成：
SystemSnapshot

建议至少包含：
runtime
market
prediction
strategy
risk
execution
portfolio
readiness
health

例如：
SystemSnapshot
├── mode
├── symbol
├── market_state
├── latest_prediction
├── latest_maker_decision
├── risk_state
├── active_orders
├── uncertain_orders
├── position
├── balance/equity
├── pnl
├── readiness
└── timestamps

所有 UNKNOWN 必须显式保留。
禁止：
None → 0
unknown → healthy
missing → empty

2. Product API
第一版只做稳定 REST/JSON API。
建议：
GET /api/v1/status
GET /api/v1/market
GET /api/v1/prediction
GET /api/v1/strategy
GET /api/v1/risk
GET /api/v1/orders
GET /api/v1/portfolio
GET /api/v1/readiness
GET /api/v1/evidence

以及聚合：
GET /api/v1/snapshot

API schema 必须版本化。
内部 Python 类型不能直接裸序列化成产品契约。
3. Runtime Identity
所有 API 返回必须带：
mode
environment
venue
symbol
runtime_id
started_at
data_timestamp

至少区分：
REPLAY
PAPER
TESTNET
LIVE

不能让 UI 猜当前运行模式。
4. Evidence / Decision Trace
这是本项目很重要的一层。
UI 必须能回答：
为什么现在没下单？
为什么下这个价格？
为什么 Risk 拒绝？
为什么 readiness blocked？

需要把已有 reason code 串起来：
MarketState
→ Prediction
→ MakerDecision
→ RiskDecision
→ Order
→ ExecutionEvent

第一版不要求完整图数据库。
只需要稳定结构化 trace。
5. UI
UI 第一版定位为：
engineering console / research console

不是面向普通消费者的交易终端。
核心页面建议只有：
Overview
Market
Prediction
Strategy
Orders
Portfolio
Risk / Readiness
Evidence

重点是状态和因果链，不是 K 线炫技。
6. Reports
第一版只生成结构化 Run Summary。
例如：
RunSummary
├── runtime identity
├── duration
├── market health
├── prediction stats
├── decision counts
├── order counts
├── fills
├── fees
├── realized pnl
├── position
├── risk rejects
├── readiness blocks
└── anomalies

Report 必须来自事实记录。
不重新跑策略。
控制面边界
这一点要非常保守。
P0001.10 第一版：
允许
read status
read evidence
read reports

可以预留：
POST /api/v1/runtime/stop

但仅当它最终调用已有安全 stop semantics。
不允许
第一版禁止：
POST /buy
POST /sell
POST /order
POST /position
POST /set-leverage
POST /change-risk-limit

UI 不能绕过：
MakerPolicy
RiskGate
ReadinessAuthority
ExecutionEngine

尤其不能直接调用 Binance adapter。
边界
包含
- Product Read Model
- versioned Product API
- SystemSnapshot
- runtime identity
- structured decision/evidence view
- basic engineering UI
- run summary/report
- REPLAY / PAPER / TESTNET 共用产品语义
- UNKNOWN 明确传播
- API contract tests
不包含（关键）
- 不新增策略
- 不修改 MakerPolicy
- 不修改 Jev schema
- 不修改 RiskGate 逻辑
- 不修改 Accounting 语义
- 不修改 Execution state machine
- 不直接调用 Binance 下单接口
- 不做手动 Buy/Sell
- 不做 Mainnet 产品化
- 不做用户账户系统
- 不做 OAuth
- 不做多租户
- 不做复杂权限系统
- 不做移动 App
- 不做专业 TradingView 替代
- 不做参数优化器
- 不做策略回测平台重构
- 不接 Freqtrade
- 不接 Hummingbot
- 不接 lob-engine
最后三项尤其重要：
P0001.10 先固定 Probex 自己的产品契约。外部框架以后只能适配这个契约，而不是反过来污染核心。

目录结构
建议：
product/
    __init__.py

    service.py
    serialization.py

api/
    __init__.py
    server.py
    routes/
        status.py

        risk.py
        execution.py
        portfolio.py
        readiness.py
        evidence.py

ui/
    ...

reports/
    types.py
    run_summary.py

tests/
    unit/
        test_product_snapshot.py
        test_product_serialization.py
    integration/
        test_product_api.py

不要求一次把 UI 做复杂。
成功标准
1. GET /api/v1/snapshot 能完整表示一个运行实例当前状态。
2. REPLAY / PAPER / TESTNET 使用同一 snapshot schema。
3. UNKNOWN 不被转换成 0 / empty / healthy。
4. API 不重新实现任何 Market / Prediction / Risk / Accounting 逻辑。
5. 每个 Risk reject 能看到正式 reason code。
6. 每个 MakerDecision 能看到输入 prediction identity。
7. 每个 active order 能追溯到对应 decision。
8. readiness blocker 能完整显示。
9. UI 能展示：当前市场
   当前预测
   当前策略动作
   当前风险状态
   当前订单
   当前仓位/PnL
10. UI/API 无任何绕过 RiskGate 的交易写入口。
11. Product 层不得 import Binance execution REST client。
12. 全量测试不回归。

### 落地内容

| 目录 | 文件 | 职责 |
| --- | --- | --- |
| `product/` | `types.py` | `RuntimeMode` / `RuntimeIdentity` / **`Fact`（known/unknown 一等字段）** / 各段 View / `TraceEntry` / `EvidenceView` |
| | `snapshot.py` | `SystemSnapshot`（REPLAY / PAPER / TESTNET / LIVE **共用同一 schema**） |
| | `service.py` | `ProductService`：从**注入的只读 callable** 组合事实，不含任何阈值/指标/PnL/风险数学 |
| | `serialization.py` | 版本化 JSON：`Fact → {known, value, reason}`；拒绝 NaN/Inf 与未知类型（不猜测） |
| `api/` | `server.py` | stdlib-only 只读 REST/JSON；`do_POST` 一律 405（`/runtime/stop` 预留 501） |
| | `routes/*.py` | status / market / prediction / strategy / risk / **orders**（别名 `/execution`）/ portfolio / readiness / evidence |
| `ui/` | `index.html` | engineering console：每 2s 拉 `/api/v1/snapshot`，UNKNOWN 高亮显示 |
| `reports/` | `types.py` / `run_summary.py` | `RunSummary`：只汇总已记录事实（计数/求和），不重跑策略 |
| `tests/` | `unit/test_product_snapshot.py`、`unit/test_product_serialization.py`、`unit/test_run_summary.py`、`integration/test_product_api.py` | 29 条新测试 |

### 成功标准映射

| SC | 证据 |
| --- | --- |

| 2 三种模式共用 schema | `test_every_mode_shares_one_schema`（REPLAY / PAPER / TESTNET / LIVE 同一 `schema_version` 与字段集） |

### 边界遵守

- 未新增策略、未修改 MakerPolicy / Jev schema / RiskGate / Accounting / Execution 状态机；
- 未直接调用 Binance 下单接口；无 Buy/Sell、无参数/杠杆写入口；
- 未做 Mainnet 产品化、账户系统、OAuth、多租户、权限系统、移动端、参数优化器、回测平台重构；
- 未接 Freqtrade / Hummingbot / lob-engine；仅 stdlib（`http.server` / `json` / `dataclasses`），**零第三方依赖**。
