## 1. P0001.2 实现契约

### 1.1 目标

把 P0001.1 的瞬时 `MarketEvent` 变成有正式历史载体的可重放事实：append-only Event Store + 确定性 Replay。

### 1.2 Included

- `MarketEvent` 序列化 / 反序列化（codec）+ `schema_version`
- append-only、immutable、ordered、versioned 的 Event Store
- stable event ordinal（写入者分配，严格递增，不覆盖已有 ordinal）
- `EventWriter` / `EventReader` 接口，JSONL 仅作为 adapter（接口不绑定文件格式）
- `ReplaySource`
- `ReplayClock`（`now()` / `advance_to()` / `reset()`，逻辑时间按事件推进）
- `FULL` replay
- `STEP` replay（每次消费一条 canonical event）
- 确定性排序与事件完整性校验
- 文件损坏 / 非法事件检测（fail closed）
- replay → `MarketBook` 集成测试
- 同一数据重复运行一致性测试
- `tests/unit`、`tests/integration`、`tests/replay`、`tests/fault` 四层测试

### 1.3 NOT Included

- Live WebSocket、Binance REST 网络调用
- Feature / OFI / Jev / Strategy / Order / Execution / Paper / Live Trading
- 数据库、Parquet、压缩
- 多交易所统一 downloader
- 倍速播放（2x / 10x / wall-clock paced）
- UI
- 修改 P0001.1 的 Book 状态机语义
- 为 Replay 给 `MarketEvent` 增加交易业务字段
- **单独创建一套 `ReplayEvent`**：Replay 必须消费原来的 `MarketEvent`
- `LiveClock`（本阶段只创建 `ReplayClock`）
- 存储层索引、fsync 策略、文件轮转、回滚 / 修复工具
- 新增任何第三方依赖

### 1.4 排序与时间契约（实现约定，供审查）

提案原文的排序契约为「1. logical stream order、2. sequence、3. recorded ordinal（最终 tie-breaker）」。本实现落地为：

- **Replay 顺序 = store 的 `recorded ordinal`（严格递增的文件 append 顺序）**，它同时就是 logical stream order：同一文件内 ordinal 唯一，因此顺序唯一。
- **时间戳不参与排序**。`exchange_ts` / `receive_ts` 相同不影响顺序（有专门测试）。
- **`sequence` 不参与排序**：它是事件域序号，由下游 `MarketBook` 做连续性判定（P0001.1 语义不变），P0001.2 只负责原样保存与还原。
- `EventReader` 对 `ordinal` 做严格递增校验：重复或逆序一律 fail closed。
- 未引入提案未要求的额外排序字段；若后续需要跨文件合并排序，需新提案。

### 1.5 Success Criteria

- **SC-1 逐字段往返一致**：一组 `MarketEvent` 写入 Event Store 后重新读取，逐字段完全一致。
- **SC-2 append-only 且不覆盖 ordinal**：Store 只追加；对已有文件继续写入时 ordinal 从最后一个 ordinal 续接，历史记录字节不变。
- **SC-3 重复 Replay 完全一致**：相同 Store 连续 Replay 两次，消费事件顺序、`BookUpdate` outcome、`HealthTransition`、最终 `BookView` 完全一致。
- **SC-4 Replay 不绕过健康检查**：Replay 期间出现真实 sequence gap 时，行为与 P0001.1 Live-style 输入一致（`HEALTHY → STALE`，`is_tradeable = false`）。
- **SC-5 含 resync 的历史序列可完整恢复**：snapshot + buffered delta + resync 的历史序列 Replay 后，最终 `BookView` 与无故障参考路径一致。
- **SC-6 损坏输入 fail closed**：非法 JSON、缺字段、未知 `schema_version`、`MarketEvent` 校验失败、ordinal 重复/逆序、事件内容被篡改，全部抛出明确错误，不静默跳过、不部分成功。
- **SC-7 STEP 模式每次只推进一个事件**：每次 `next_event()` 消费且仅消费一条 canonical event。
- **SC-8 Replay 不依赖 `time.sleep()`**：Replay 过程中不调用 `time.sleep`；逻辑时间按事件推进到最后一个事件时间。
- **SC-9 Replay 层隔离**：`market/replay` 与 `storage/events` 不 import Feature / Jev / Strategy / Execution。
- **SC-10 阶段门**：整套测试通过后，才允许进入 P0001.3。

## 2. 原 P0001.2 提案文本（原样保留）

目标
建立市场事件的持久化与确定性重放能力。
目标不是做一个“读取历史文件的脚本”，而是建立以后：
Live Capture
→ Event Store
→ Replay
→ Research / Feature / Jev

共同依赖的基础设施。
同一份事件数据重复 Replay，必须得到完全一致的 MarketBook 最终状态和事件消费顺序。
背景
P0001.1 已经建立：
MarketEvent
→ MarketBook
→ OrderBook
→ BookHealth

但现在 MarketEvent 只是瞬时对象，没有正式历史载体。
如果此时直接进入 Feature / Jev，之后很难回答：
这个预测当时看到了什么？
能不能重新运行？
为什么两次实验结果不同？

因此必须先把“市场事实”固定下来。
架构
               Live / Imported Events
                       │
                       ▼
                 MarketEvent
                       │
              ┌────────┴────────┐
              ▼                 ▼
         MarketBook         EventWriter
                                │
                                ▼
                         Append-only Store
                                │
                                ▼
                           ReplaySource
                                │
                                ▼
                           ReplayClock
                                │
                                ▼
                           MarketEvent
                                │
                                ▼
                            MarketBook

原则：
Live 和 Replay 的区别只存在于 Event Source 和 Clock。

MarketBook 不应该知道事件来自网络还是文件。
设计
Event Store 第一版只保存规范化后的 canonical MarketEvent，不保存交易所原始 JSON 作为主数据。
但需要允许附带：
source
schema_version
capture metadata

事件记录至少包含：
event_id
venue
symbol
event_type
exchange_ts
receive_ts
process_ts
sequence
payload
schema_version

持久化必须：
append-only
immutable
ordered
versioned

禁止写入后原地修改历史事件。
Replay 顺序
确定性不能单靠 timestamp。
排序契约必须明确：
1. logical stream order
2. sequence（若该事件域有 sequence）
3. recorded ordinal

recorded ordinal 是最终 tie-breaker。
也就是说，同一文件里即使两个事件：
exchange_ts 相同
receive_ts 相同

Replay 顺序仍然唯一。
ReplayClock
本阶段创建：
ReplayClock

但不要实现复杂调度。
最小接口只需要表达：
now()
advance_to(event_time)
reset()

Replay 第一版默认：
as-fast-as-possible

逻辑时间按照事件推进，而不是 sleep()。
Replay Modes
第一版只支持两个：
FULL
STEP

FULL：跑完整数据集。
STEP：消费一条事件后暂停，由测试/调用者继续。
暂不做 2x / 10x / wall-clock paced playback。
文件格式
我建议第一版使用：
JSONL

不是因为它性能最好，而是 P0001.2 当前优先验证：
schema
ordering
determinism
corruption detection

JSONL 易审计、易构造 fault case。
Parquet 放到数据量真实性能阶段再引入，不要现在增加第三方依赖和 schema complexity。
但 Event Store 接口不能绑定 JSONL：
EventWriter
EventReader

文件格式属于 adapter。
边界
包含
- MarketEvent 序列化/反序列化
- schema version
- append-only Event Store
- stable event ordinal
- EventWriter / EventReader
- ReplaySource
- ReplayClock
- FULL replay
- STEP replay
- deterministic ordering
- 文件损坏/非法事件检测
- replay → MarketBook 集成测试
- 同一数据重复运行一致性测试
不包含（关键）
- 不实现 Live WebSocket
- 不实现 Binance REST 网络调用
- 不实现 Feature
- 不实现 OFI
- 不实现 Jev
- 不实现 Strategy
- 不实现 Order / Execution
- 不实现 Paper / Live Trading
- 不实现数据库
- 不实现 Parquet
- 不实现压缩
- 不实现多交易所统一 downloader
- 不实现倍速播放
- 不实现 UI
- 不修改 P0001.1 的 Book 状态机语义
- 不为了 Replay 给 MarketEvent 增加交易业务字段
特别禁止：
不要另外创建一套 ReplayEvent。

Replay 必须消费原来的 MarketEvent。

如果现有 CLAUDE.md 对目录有更严格约束，以项目规范为准。
成功标准
1. 一组 MarketEvent 写入 Event Store 后重新读取，逐字段完全一致。
2. Store 是 append-only；不得覆盖已有 ordinal。
3. 相同 Event Store 连续 Replay 两次：
消费事件顺序
BookUpdate outcome
HealthTransition
最终 BookView

完全一致。
4. Replay 期间出现真实 sequence gap 时，行为必须与 P0001.1 Live-style 输入一致：
HEALTHY → STALE
is_tradeable = false

不能因为是历史数据就绕开健康检查。
5. 含 snapshot + buffered delta + resync 的历史序列 Replay 后，与无故障参考路径最终 BookView 一致。
6. 对以下损坏输入必须 fail closed：
非法 JSON
缺字段
未知 schema_version
MarketEvent 校验失败
ordinal 重复/逆序

7. STEP 模式每次只能推进一个 canonical event。
8. Replay 不依赖 time.sleep()，测试运行结果不依赖机器速度。
9. Replay 层不 import Feature、Jev、Strategy、Execution。
10. 整套测试通过后，才允许进入 P0001.3 Feature / MarketState。
