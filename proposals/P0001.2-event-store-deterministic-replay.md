P0001.2：Event Store + Deterministic Replay
状态：已提议
日期：2026-09-28
依赖：P0001.1
目标
建立市场事件的持久化与确定性重放能力。
目标不是做一个“读取历史文件的脚本”，而是建立以后：
Live Capture
→ Event Store
→ Replay
→ Research / Feature / Jev

共同依赖的基础设施。
同一份事件数据重复 Replay，必须得到完全一致的 MarketBook 最终状态和事件消费顺序。
背景
P0001.1 已经建立：
MarketEvent
→ MarketBook
→ OrderBook
→ BookHealth

但现在 MarketEvent 只是瞬时对象，没有正式历史载体。
如果此时直接进入 Feature / Jev，之后很难回答：
这个预测当时看到了什么？
能不能重新运行？
为什么两次实验结果不同？

因此必须先把“市场事实”固定下来。
架构
               Live / Imported Events
                       │
                       ▼
                 MarketEvent
                       │
              ┌────────┴────────┐
              ▼                 ▼
         MarketBook         EventWriter
                                │
                                ▼
                         Append-only Store
                                │
                                ▼
                           ReplaySource
                                │
                                ▼
                           ReplayClock
                                │
                                ▼
                           MarketEvent
                                │
                                ▼
                            MarketBook

原则：
Live 和 Replay 的区别只存在于 Event Source 和 Clock。

MarketBook 不应该知道事件来自网络还是文件。
设计
Event Store 第一版只保存规范化后的 canonical MarketEvent，不保存交易所原始 JSON 作为主数据。
但需要允许附带：
source
schema_version
capture metadata

事件记录至少包含：
event_id
venue
symbol
event_type
exchange_ts
receive_ts
process_ts
sequence
payload
schema_version

持久化必须：
append-only
immutable
ordered
versioned

禁止写入后原地修改历史事件。
Replay 顺序
确定性不能单靠 timestamp。
排序契约必须明确：
1. logical stream order
2. sequence（若该事件域有 sequence）
3. recorded ordinal

recorded ordinal 是最终 tie-breaker。
也就是说，同一文件里即使两个事件：
exchange_ts 相同
receive_ts 相同

Replay 顺序仍然唯一。
ReplayClock
本阶段创建：
ReplayClock

但不要实现复杂调度。
最小接口只需要表达：
now()
advance_to(event_time)
reset()

Replay 第一版默认：
as-fast-as-possible

逻辑时间按照事件推进，而不是 sleep()。
Replay Modes
第一版只支持两个：
FULL
STEP

FULL：跑完整数据集。
STEP：消费一条事件后暂停，由测试/调用者继续。
暂不做 2x / 10x / wall-clock paced playback。
文件格式
我建议第一版使用：
JSONL

不是因为它性能最好，而是 P0001.2 当前优先验证：
schema
ordering
determinism
corruption detection

JSONL 易审计、易构造 fault case。
Parquet 放到数据量真实性能阶段再引入，不要现在增加第三方依赖和 schema complexity。
但 Event Store 接口不能绑定 JSONL：
EventWriter
EventReader

文件格式属于 adapter。
边界
包含
- MarketEvent 序列化/反序列化
- schema version
- append-only Event Store
- stable event ordinal
- EventWriter / EventReader
- ReplaySource
- ReplayClock
- FULL replay
- STEP replay
- deterministic ordering
- 文件损坏/非法事件检测
- replay → MarketBook 集成测试
- 同一数据重复运行一致性测试
不包含（关键）
- 不实现 Live WebSocket
- 不实现 Binance REST 网络调用
- 不实现 Feature
- 不实现 OFI
- 不实现 Jev
- 不实现 Strategy
- 不实现 Order / Execution
- 不实现 Paper / Live Trading
- 不实现数据库
- 不实现 Parquet
- 不实现压缩
- 不实现多交易所统一 downloader
- 不实现倍速播放
- 不实现 UI
- 不修改 P0001.1 的 Book 状态机语义
- 不为了 Replay 给 MarketEvent 增加交易业务字段
特别禁止：
不要另外创建一套 ReplayEvent。

Replay 必须消费原来的 MarketEvent。

成功标准
1. 一组 MarketEvent 写入 Event Store 后重新读取，逐字段完全一致。
2. Store 是 append-only；不得覆盖已有 ordinal。
3. 相同 Event Store 连续 Replay 两次：
消费事件顺序
BookUpdate outcome
HealthTransition
最终 BookView

完全一致。
4. Replay 期间出现真实 sequence gap 时，行为必须与 P0001.1 Live-style 输入一致：
HEALTHY → STALE
is_tradeable = false

不能因为是历史数据就绕开健康检查。
5. 含 snapshot + buffered delta + resync 的历史序列 Replay 后，与无故障参考路径最终 BookView 一致。
6. 对以下损坏输入必须 fail closed：
非法 JSON
缺字段
未知 schema_version
MarketEvent 校验失败
ordinal 重复/逆序

7. STEP 模式每次只能推进一个 canonical event。
8. Replay 不依赖 time.sleep()，测试运行结果不依赖机器速度。
9. Replay 层不 import Feature、Jev、Strategy、Execution。
10. 整套测试通过后，才允许进入 P0001.3 Feature / MarketState。
