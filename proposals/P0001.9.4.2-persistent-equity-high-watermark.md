### 0.2 关键不变量（逐条对应提案）

1. **activation 显式**：`HighWatermarkTracker.activate()` 必须收到全部满足的 `ActivationPreconditions`；
   从未 activation ⇒ `UNINITIALIZED`（readiness `HIGH_WATERMARK_NOT_INITIALIZED`）。
2. **peak 单调**：只有 `equity > peak` 才提升；普通运行路径**绝不**降低 peak（状态构造期也校验该不变量）。
3. **durable-before-publish**：提升 peak 时先 `store.save()`；save 失败 ⇒ **不发布**（内存仍为旧 peak）。
4. **restart ≠ reset**：新进程从 store 加载旧 peak 继续同一 epoch；对 ACTIVE epoch 重复 `activate()` 直接拒绝。
5. **UTC 日界不重置**：tracker 不含任何日界逻辑（只有显式 rebase 换 epoch）。
6. **外部资本流 ⇒ INVALIDATED**：`invalidate_for_capital_flow()` 持久化 `INVALIDATED` + typed `invalidation_kind`，
   之后**拒绝**任何 equity 观测，必须显式 rebase；本阶段**不**实现 cash-flow-adjusted NAV。
7. **删除状态文件 ≠ 重置**：文件缺失 ⇒ `load()` 返回 `None` ⇒ `UNINITIALIZED` ⇒ readiness BLOCKED
   （因为 activation **永不自动**，删文件不能换来一个绿色系统）；文件损坏 / schema 不匹配 ⇒ 抛错 ⇒ BLOCKED。
8. **scope**：状态携带 `scope`（TESTNET/MAINNET）与 `deployment_id`；跨 scope 复用由前置条件拒绝。

### 0.3 与历史 drawdown 的关系（提案 §1 原样坚持）

```text
drawdown = 自 trusted activation point 起、相对此后最高可信权益的回撤
```

**不是**"账户历史最高权益"；`activation_ts` / `activation_equity` 一律随状态持久化，审计可追溯。

# 原提案文本（原样保留）

## 目标

建立一个跨进程重启、跨 crash 持续存在的 **Equity High-Watermark**，使 Live Risk 能从一个明确可信的起点开始计算 drawdown。

本阶段解决：

```text
HISTORICAL_DRAWDOWN_UNKNOWN
```

但语义必须明确为：

```text
drawdown since trusted activation point
```

而不是声称知道账户启用 Probex 之前的历史最高权益。

完成后：

```text
Recovery        = RECOVERED
Daily PnL       = KNOWN
High Watermark  = KNOWN
Drawdown        = KNOWN
```

才有资格进一步评估 `LIVE_READY`。

---

## 背景

P0001.9.4.1.1 已通过真实 Testnet 全链验证：

```text
PRIVATE_LATENCY_UNKNOWN → 已消失
MARKET_NOT_READY        → 已消失

唯一结构性 blocker：
HISTORICAL_DRAWDOWN_UNKNOWN
```

历史 equity reconstruction 不适合作为主路线：

```text
历史仓位
+ 历史 mark
+ fee
+ funding
+ transfer
+ 各时刻账户状态
→ historical equity curve
```

数据要求高，而且即使重建成功，也难证明没有缺口。

本阶段改用：

```text
明确可信起点
        ↓
持续观察真实 equity
        ↓
durable max()
        ↓
Persistent High-Watermark
```

---

## 架构

```text
Accounting / Account facts
          │
          ▼
   Current Equity
          │
          ▼
HighWatermarkTracker
   │             │
   │ observe     │ durable state
   ▼             ▼
```

```text

          ↓

          ↓
BLOCKED
          ↓

```

# 设计

## 1. Drawdown 的正式时间域

从本 Proposal 起，Live drawdown 定义为：

```text
自 trusted activation point 起，
账户权益相对于此后最高可信权益的回撤
```

公式：

```text
peak_equity =
    max(all accepted equity observations since activation)

drawdown =
    max(0, peak_equity - current_equity)

drawdown_pct =
    drawdown / peak_equity
```

因此：

```text
UNKNOWN historical peak before activation
```

不再阻塞。

但必须记录：

```text
activation_ts
activation_equity
```

不能把它描述成“账户历史最高权益”。

---

## 2. Trusted Activation Point

第一次建立 high-watermark **不得自动发生**。

必须显式执行 activation，并同时满足：

```text
RecoveryStatus == RECOVERED

position == 0

open orders == 0

unresolved orders == 0

daily_pnl_known == true

current equity known

exchange/account snapshot fresh

local accounting equity
≈ authoritative exchange equity

scope explicitly known:
  TESTNET or MAINNET
```

第一版要求 **flat + zero open orders**。

理由：第一次定义风险 epoch 时不能把一个已经处于未知浮盈/浮亏状态的仓位偷偷当作风险起点。

初始：

```text
activation_equity = current_equity
peak_equity       = activation_equity
```

这是**显式业务定义**，不是历史推断。

---

## 3. Activation 不等于 Restart

必须严格区分：

```text
ACTIVATION
```

和：

```text
PROCESS RESTART / CRASH RECOVERY
```

正常 restart：

```text
load persisted HWM
→ Recovery
→ reconcile
→ current equity
→ continue existing epoch
```

**绝对不能：**

```text
restart
→ peak = current equity
```

否则每次重启都可以把 drawdown 清零。

---

## 4. Persistent State

定义独立状态，例如：

```text
EquityHighWatermarkState

schema_version
scope
deployment_id

activation_id
activation_ts
activation_equity

peak_equity
peak_ts

last_equity
last_observed_ts

capital_flow_checked_through

generation
status
```

状态：

```text
UNINITIALIZED
ACTIVE
INVALIDATED
```

不要复用：

```text
AccountingCore._historical_pnl_known
```

它描述的是历史 accounting 事实，不应该承担 durable risk epoch。

---

## 5. Durable Store

增加窄接口：

```text
HighWatermarkStore

load()
save(state)
```

优先复用现有 storage 基础设施。

不要建立：

```text
通用数据库
checkpoint framework
distributed state service
```

持久化必须满足：

```text
write temp
→ flush
→ fsync
→ atomic replace
```

写失败：

```text
不得继续认为 HWM ACTIVE
→ fail closed
```

---

## 6. Peak 必须单调

核心不变量：

```text
new_peak >= old_peak
```

只有：

```text
current_equity > persisted_peak
```

才允许提升 peak。

绝不允许普通运行路径降低 peak。

例如：

```text
peak = 5000
equity = 5100
→ peak = 5100

equity = 4900
→ peak remains 5100
```

---

## 7. 新 Peak 的 durability 顺序

这是关键 crash 边界。

错误顺序：

```text
memory peak = 5100
↓
Risk says OK
↓
later persist
```

如果期间 crash，重启可能恢复成 5000，低估 drawdown。

正确契约：

```text
observe new peak
     ↓
durably persist 5100
     ↓
publish HWM=5100
```

即：

> **新 high-watermark 在 durable write 成功之前，不得成为可供 readiness/risk 使用的已确认状态。**

---

## 8. State 丢失 / 损坏

如果系统以前已经 activation，但：

```text
文件不存在
schema invalid
内容损坏
scope mismatch
generation invalid
```

必须：

```text
BLOCKED
```

不能：

```text
重新以 current equity 初始化
```

否则删除状态文件就等于人为清除 drawdown。

---

# 9. Reset / Rebase

Reset 是风险语义变化，必须由人类显式触发。

禁止：

```text
daily reset
restart reset
drawdown breach 后自动 reset
deposit 后自动 reset
```

定义：

```text
explicit rebase
```

要求至少：

```text
human authorization
position = 0
open orders = 0
Recovery = RECOVERED
fresh account snapshot
daily PnL known
explicit reason
new activation_id
```

旧状态必须留下审计记录。

不能原地覆盖得像从来没有发生过。

---

# 10. UTC Day Boundary

**UTC 日界不重置 High-Watermark。**

即：

```text
Daily Loss:
    UTC day scoped

Drawdown:
    activation epoch scoped
```

例如：

```text
23:59 peak = 5200
00:01 equity = 5000
```

仍然：

```text
peak = 5200
drawdown = 200
```

否则每天午夜都会自动清除累计风险。

---

# 11. External Capital Flow

这是最容易把 drawdown 算错的地方。

例如：

```text
equity 5000
deposit +2000
equity 7000
```

不能因此认为：

```text
trading peak = 7000
```

反过来：

```text
withdraw 2000
```

也不能被当成：

```text
trading drawdown 2000
```

### P0001.9.4.2 第一版采取保守规则

只要 activation 后检测到：

```text
TRANSFER
```

或者未来其他明确 external capital flow：

```text
HighWatermarkState
→ INVALIDATED
```

Readiness：

```text
BLOCKED:
EXTERNAL_CAPITAL_FLOW_DETECTED
```

然后要求人类显式 rebase。

**本阶段不实现 cash-flow-adjusted NAV。**

这是有意的。

以后如果资本转移成为高频需求，可以另开子 Proposal 实现：

```text
flow-adjusted equity =
raw equity - cumulative external capital flow
```

现在不要提前复杂化。

---

# 12. Funding / Fees / Trading PnL

以下属于真实交易表现：

```text
REALIZED_PNL
COMMISSION
FUNDING_FEE
SPECIAL_FUNDING_FEE
unrealized PnL
```

它们应正常改变 equity，并影响 high-watermark / drawdown。

不要把 funding 当 external capital flow。

---

# 13. Equity Observation

HWM 只能接受：

```text
finite
fresh
source-known
```

的 equity。

Live 首次 activation 时应同时验证：

```text
local AccountingCore.equity
≈ exchange totalMarginBalance
```

偏差超出明确 tolerance：

```text
EQUITY_MISMATCH
→ BLOCKED
```

**不要悄悄选一个值。**

正常运行中的 current equity 仍由既有 Accounting/Risk 数据流提供，本阶段不重构整个账户所有权模型。

---

# 14. Sampling 语义

High-watermark 是：

```text
accepted equity observations 的最高值
```

不是声称捕获交易所连续时间上的数学极值。

因此必须记录：

```text
peak_ts
last_observed_ts
```

观察入口跟随现有 Accounting equity 更新路径：

```text
Fill
Funding
Mark update
```

不另建高频行情采样系统。

---

# 15. RiskSnapshot 接线

新增可信输入，例如：

```text
HighWatermarkEvidence
```

Live：

```text
valid persistent HWM
+
current equity
→ peak_equity
→ drawdown
→ drawdown_pct
```

然后既有：

```text
RiskGate.max_drawdown_pct
```

继续工作。

Paper / Replay：

```text
保持原有 session-derived peak 语义
```

不改变。

# 16. Readiness 接线

当前：

```text

```

## 成功标准

1. 未 activation → `HIGH_WATERMARK_NOT_INITIALIZED`。
2. activation 只有在 flat / 0 open order / RECOVERED / equity known 等条件全部满足时成功。
3. activation 后：
   ```text
   peak = activation equity
   drawdown = 0
   ```
   且明确标记为 **since activation**。
4. equity 上升 → peak 单调上升。
5. equity 回落 → peak 不下降，drawdown 正确增加。
6. 新 peak 必须 durable write 成功后才能 publish。
7. persistence 失败 → readiness BLOCKED。
8. process restart 后加载旧 peak，不用 current equity 重置。
9. crash 后旧 peak 能恢复，不低估 drawdown。
10. 状态文件缺失/损坏/版本错误 → BLOCKED，不自动重新初始化。
11. Testnet state 不能加载到 Mainnet。
12. UTC midnight 不重置 peak。
13. `TRANSFER` 发生后 → HWM INVALIDATED / readiness BLOCKED。
14. deposit/withdraw 不被错误解释成 trading peak/drawdown。
15. funding / fee / trading PnL 正常影响 equity。
16. rebase 必须显式授权，flat + 0 orders，并产生新的 activation ID。
17. Paper / Replay 现有 drawdown 语义完全不变。
18. persistent HWM 有效后：
   ```text
   RiskSnapshot.peak_equity != None
   RiskSnapshot.drawdown_pct != None
   ```
19. 配置 `max_drawdown_pct` 后 RiskGate 能真正执行 drawdown 限额，而不是 `MISSING_DRAWDOWN`。
20. Testnet 做一次：
   ```text
   activate
   → persist
   → restart process
   → recovery
   → restore HWM
   → readiness
   ```
   全链验证。
21. 产品代码仍无 Binance submit/cancel。
22. 全量测试 + detached worktree PASS。

这里我特别强调两个设计决定。

第一：

> **我们不是“恢复历史 drawdown”，而是从一个人类认可的可信时点开始正式拥有 drawdown 历史。**

第二：

> **High-Watermark 一旦建立，重启、午夜、程序 crash 都不能把它洗掉。**

否则所谓 `max_drawdown_pct` 只是一个可以靠重启规避的风控参数。

这一步做完，如果真实 Testnet readiness 的 blocker 集合变成空，我们再讨论的才应该是 **Execution Readiness → Binance ExecutionAdapter**，而不是继续补历史账。
