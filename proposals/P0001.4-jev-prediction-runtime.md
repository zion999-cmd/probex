## 1. P0001.4 实现契约

### 1.1 Included

- `PredictionProvider` protocol
- `JevProvider`（传输函数注入式 adapter）
- `PredictionRequest` / `Prediction` / `PredictionRecord` / `PredictionResult`
- question schema 版本化（`jev-market-v1`）
- `MarketState` → canonical Jev payload（含 `market_state_hash`）
- async 请求（`asyncio`）
- timeout、exponential backoff、limited inflight
- stale response rejection（迟到旧结果不得成为 current prediction）
- strict parser（probability / 分类 / NaN / Infinity / unknown field 全部 fail closed）
- TTL 与 expired 判定
- provider / model metadata 与 raw response 证据
- RECORDED 与 LIVE_REQUERY 两种 Replay 语义
- deterministic fake provider（测试基础设施）
- 本阶段不引入任何第三方依赖（`asyncio` 为标准库）

### 1.2 NOT Included

- Strategy / buy-sell-hold / 开仓阈值 / Maker / Order / Position / Accounting / Risk
- 让 Jev 看账户、仓位、盈亏、风险阈值、历史决定或「现在想买还是卖」
- 自然语言解释、模型自动修改 question schema、prompt optimization、模型训练、模型收益比较
- 因 Replay 自动调用线上 Jev
- 真实 HTTP / 网络客户端与 Jev API Key 管理（`JevProvider` 只提供传输注入点）
- Prediction 的持久化存储（本阶段只有内存 archive）
- outcome / evaluation（对过去预测的复盘）与 Experiment Runtime
- UI

### 1.3 本阶段固定的契约

| 项目 | 取值 / 定义 |
| --- | --- |
| `question_schema_version` | `jev-market-v1` |
| `feature_schema_version` | 沿用 `market-state-v1`（来自 `MarketState`） |
| 问题集合 | `future_return`（分布）、`buy_adverse_selection`、`sell_adverse_selection`、`buy_fill_probability`、`sell_fill_probability`（概率） |
| `future_return` horizons | 5s / 15s / 30s / 60s |
| `future_return` buckets | `strong_down` / `down` / `flat` / `up` / `strong_up`，互斥且求和 = 1（容差 1e-6） |
| 概率约束 | 全部落于 [0, 1]，NaN / Infinity / 负数 / >1 一律 `INVALID_RESPONSE` |
| `market_state_hash` | `sha256:` + canonical JSON（全量 `MarketState`，key 排序、紧凑分隔符、禁止非有限数值） |
| Jev payload | 只含 `identity` / `as_of` / `quality` / price / depth / flow / trade / returns / volatility + 版本 + hash + questions；字段白名单，绝不含账户 / 仓位 / 盈亏 / 风险 |
| 时间基准 | 运行时通过注入的 `Clock` 取毫秒时间戳；预测层代码不 import `time`、不使用 wall-clock |
| `expires_at` | `created_at + ttl_ms`（`ttl_ms` 由构造参数给定，不内置默认值） |
| expired 判定 | `at > expires_at` 为 expired |
| `provider_confidence` | 供应商响应中 `confidence` 字段（可缺失 → `None`） |
| `derived_confidence` | `1 - H(p_nearest)/ln(5)`，`p_nearest` 为最短 horizon（5s）的 `future_return` 分布；值域 [0, 1] |
| inflight 上限 | 默认 `max_inflight = 1`；超出 → `SKIPPED_INFLIGHT`（不排队） |
| backoff | 连续失败 `n` 次后 `next_retry_at = now + min(base * 2^(n-1), cap)`；`base_backoff_ms` 默认 1000，`max_backoff_ms` 默认 60000 |
| provider 状态 | `HEALTHY`（无连续失败）/ `BACKING_OFF`（有失败且 now < next_retry_at，请求被跳过）/ `DEGRADED`（有失败但已可重试） |
| 失败类型 | `TIMEOUT` / `TRANSPORT_ERROR` / `PROVIDER_ERROR` / `PARSE_ERROR` / `INVALID_RESPONSE`；绝不伪造 probability = 0 |
| archive 写入 | 只有 `ACCEPTED` 的记录进入 archive；`STALE_RESPONSE` 只进内存提交日志 |

### 1.4 Success Criteria

- **SC-1** 同一个 `MarketState` + 同一 question schema 生成完全相同的 canonical Jev payload 与 `market_state_hash`。
- **SC-2** Jev 请求执行期间 `FeatureEngine` 可以继续消费事件，不被阻塞。
- **SC-3** 请求 A / B 逆序返回时，旧 A 不得覆盖 B。
- **SC-4** timeout / provider error / parser error 不生成伪 Prediction。
- **SC-5** Prediction 超过 TTL 后可明确判断 expired。
- **SC-6** Jev 无法看到 Position / Balance / PnL / Risk 等未来领域对象。
- **SC-7** 非法 probability、缺分类、NaN、Infinity 等全部 fail closed。
- **SC-8** `provider_confidence` 与 `derived_confidence` 来源可区分。
- **SC-9** 每条 Prediction 可追溯到 market state hash / feature schema / question schema / provider / model / raw response。
- **SC-10** FakeProvider 使整个 Runtime 在无网络、无 Jev Key 的情况下完成确定性测试。
- **SC-11** Replay 测试不隐式访问网络。
- **SC-12** 旧 344 个测试全部继续通过。

## 2. 原 P0001.4 提案文本（原样保留）

# P0001.4：Jev Prediction Runtime
状态：已提议
日期：2026-09-28
依赖：P0001.1、P0001.2、P0001.3
目标
建立正式、可审计、可 Replay 的 Jev 预测运行时。
本阶段只解决：
给定一个确定的 MarketState，如何产生一个确定身份、有限寿命、可验证来源的 Prediction。

不交易、不做 Strategy、不做仓位决策。
最终链路：
MarketState
    ↓
PredictionRequest
    ↓
JevProvider
    ↓
PredictionRecord

Jev 调用必须与 Market Feed 完全解耦，超时、失败、迟到均不能阻塞市场状态更新。
背景
现在已经具备：
P0001.1  市场事实
P0001.2  历史可重放
P0001.3  当前市场状态

所以第一次可以准确回答：
Jev 在做某次预测时，到底看到了什么？

而这恰恰是旧 V3 最值得工程化升级的一点。
架构
FeatureEngine
     │
     ▼
immutable MarketState
     │
     ▼
PredictionScheduler
     │
     ├── eligibility gate
     │
     ▼
PredictionRequest
     │
     ▼
PredictionProvider
     │
     └── JevProvider
             │
             ▼
        ProviderResponse
             │
             ▼
       PredictionParser
             │
             ▼
       PredictionRecord

旁路：
Market events ───────────────▶ 继续运行
Order events  ───────────────▶ 未来继续运行
Risk          ───────────────▶ 未来继续运行

                 Jev request
                     │
                  async
                     │
                     ▼
                Prediction

绝不允许：
await Jev
↓
停止 Market pipeline

设计
1. PredictionRequest 必须冻结输入
Jev 不能直接拿一个不断变化的 FeatureEngine。
请求创建时：
MarketState(t)
      ↓
PredictionRequest

其中至少记录：
request_id
venue
symbol
as_of
market_state_hash
feature_schema_version
question_schema_version
horizon
created_at
expires_at
payload

payload 必须由 immutable MarketState 构造。
之后市场继续变化，也不能改变这个请求。
2. Question Schema 正式版本化
不要继续让 Prompt 成为隐性协议。
第一版：
jev-market-v1

固定预测问题，例如延续 V3 的思路：
Future return distribution
5s
15s
30s
60s

Buy-side adverse-selection risk
Sell-side adverse-selection risk

Passive buy fill probability
Passive sell fill probability

具体分类 bucket 可以继续参考 V3，但必须正式写进 schema。
任何以下变化：
bucket
horizon
question wording semantics
output meaning

都必须升级：
question_schema_version

不能偷偷改 Prompt。
3. Jev 只接收市场信息
仍坚持 V3 已经正确做出的边界：
Jev 可以看到：
price
spread
depth
microprice
VAMP
OFI
trade flow
returns
volatility
data quality

Jev 不看：
账户余额
当前仓位
可下单额度
昨日盈亏
风险阈值
此前决定
“现在想买还是卖”

这是非常重要的隔离。
否则概率模型会慢慢变成 Policy。
4. 输出不是 Action
定义：
Prediction

而不是：
Decision

例如：
future_return:
  strong_down: ...
  down: ...
  flat: ...
  up: ...
  strong_up: ...

buy_adverse_selection: ...
sell_adverse_selection: ...

buy_fill_probability: ...
sell_fill_probability: ...

confidence: ...

禁止出现：
BUY
SELL
HOLD
OPEN_LONG

这些属于下一层 Strategy / Policy。
5. Prediction Record 是证据
一次成功请求至少落下：
PredictionRecord

request_id
market_state_hash
feature_schema_version
question_schema_version

provider
model

request_created_at
response_received_at
latency_ms

raw_response
parsed_prediction

expires_at

Prediction 一旦生成，不允许修改。
如果后面判断错了：
新增 outcome/evaluation。
不能回头改 Prediction。
6. TTL 是一等字段
短周期系统最大风险之一就是：
算对了，但已经晚了。

每个 Prediction 必须有：
as_of
created_at
received_at
expires_at

之后使用预测的人必须检查：
now <= expires_at

而且最好进一步检查：
current market revision
vs
prediction market revision

本阶段只建立这些契约，不做交易 Gate。
7. Stale Result 必须可丢弃
典型场景：
t0 request A
t1 request B
t2 B returns
t3 A returns

不能让 A 覆盖 B。
Scheduler 必须知道：
latest accepted prediction

迟到旧结果：
STALE_RESPONSE

记录，但不能成为 current prediction。
8. 单飞与并发控制
同一：
venue + symbol + question_schema

第一版只允许有限并发。
默认建议：
max_inflight = 1

如果上一个 Jev 请求没回来：
不要无限堆积请求

可以选择：
skip

并记录：
SKIPPED_INFLIGHT

第一版不要做 request queue。
行情是实时流，旧请求积压没有价值。
9. Timeout / Backoff
吸收 V3 已有经验：
timeout
exponential backoff

Provider 状态：
HEALTHY
DEGRADED
BACKING_OFF

失败不能：
伪造 probability = 0

必须返回明确失败类型：
TIMEOUT
TRANSPORT_ERROR
PROVIDER_ERROR
PARSE_ERROR
INVALID_RESPONSE

10. Parser 必须严格
Jev 的优势是结构化概率，所以必须严格约束：
0 <= p <= 1

互斥分类如果契约要求和为 1，则检查容差。
检查：
missing category
duplicate category
NaN
Infinity
negative
>1
unknown field

失败就：
INVALID_RESPONSE

不能自动“猜着修”。
11. Confidence 不先重新发明
V3 目前已有：
Jev confidence
or
entropy-derived fallback

本阶段可以保留这种兼容机制，但必须区别：
provider_confidence
derived_confidence

不能最后只留下一个数字，让我们不知道来源。
12. Replay 语义
这里有一个非常重要的边界。
Replay 默认不能重新调用在线 jev-latest 来声称复现历史。
因为模型可能已经变化。
因此支持两种研究语义：
RECORDED
LIVE_REQUERY

RECORDED
Replay MarketState
→ 查找历史 PredictionRecord

这是严格复现。
LIVE_REQUERY
Replay MarketState
→ 今天重新调用 Jev

这是新实验。
两者结果绝不能混在同一个实验里。
P0001.4 第一版重点实现 Prediction Record 能支持这种区分；真正 Experiment Runtime 后面再做。
