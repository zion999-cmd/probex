### 0.1 凭据纪律（SC-1 / SC-2）

| 项目 | 规则 |
| --- | --- |
| 来源 | **只**从环境变量 `BINANCE_API_KEY` / `BINANCE_API_SECRET` 读取（`ApiCredentials.from_env()`）；缺失即 `CredentialsError`（不降级、不猜） |
| 呈现 | 凭据对象的 `repr` / `str` / `__eq__` 都不泄露 secret；secret 只在签名时参与 HMAC |

### 0.2 签名与时间（SC-3）

- `Signer.sign(params)`：参数排序 → `key=value&…` → 追加 `timestamp` 与 `recvWindow` → `HMAC-SHA256(secret, query)` hex。
- HMAC 实现用 RFC 4231 官方向量校验；签名过的 query 必须与发出的 query **逐字节一致**（测试反解校验）。
- `ServerTimeOffset`：以 `GET /fapi/v1/time` 测量 `server_time - local_time`，签名时间戳 = 本地时间 + offset（把 offset 计入，减小 `recvWindow` 压力）。
- wall-clock 只允许出现在 `auth.py` / `user_stream.py` / `runtime.py`（live 边界），与 P0001.9.1 同一纪律（由隔离测试固定）。

### 0.3 端点（外部事实，单一 Owner：`market_data/endpoints.py`）

| 用途 | 端点 |
| --- | --- |
| server time | `GET /fapi/v1/time`（公开） |
| account snapshot | `GET /fapi/v2/account`（签名） |
| position snapshot | `GET /fapi/v2/positionRisk`（签名） |
| listenKey 创建 / 续期 / 关闭 | `POST` / `PUT` / `DELETE /fapi/v1/listenKey`（仅需 API Key 头） |
| user data stream | `wss://fstream.binance.com/private/ws?listenKey=<key>` |

> 因此 URL 全部集中在 `endpoints.py` 且可整体覆盖；错误以**可观察失败**暴露，不做静默 fallback、不猜端点。

### 0.4 账户 / 持仓事实（SC-4 / SC-5）

- `AccountSnapshotObservation`（balances[]）+ `PositionObservation`（positionAmt / entryPrice / markPrice /
  unRealizedProfit / liquidationPrice / leverage / marginType / positionSide）+ exchange/receive/process 时间戳。
- **只接受 one-way 模式 + USDT-M + 单一 symbol**：`positionSide != "BOTH"` 或 `dualSidePosition=True`
  ⇒ `UnsupportedAccountModeError`（fail closed，不自动兼容，SC-5）。
- 缺失必需字段 / 非法数值 ⇒ 解析错误（fail closed），不静默补 0。

### 0.5 User Data Stream（SC-6 – SC-9）

- 事件：`ACCOUNT_UPDATE`、`ORDER_TRADE_UPDATE`、`listenKeyExpired`；其余类型记入 telemetry（不崩、不误当业务）。
- `ORDER_TRADE_UPDATE` 归一化字段：event time / transaction time / receive time / order id / client order id /
  execution type / order status / last fill qty / cumulative fill qty / last fill price / commission /
  commission asset / trade id / is_maker。
- **本阶段只产出 Observation**：不写 OrderTracker、不写 Accounting、不驱动 ExecutionEngine（SC-14 同样禁止下单接口）。
- `listenKey` 状态机：`STOPPED / STARTING / ACTIVE / RENEWING / EXPIRED / RECONNECTING / FAILED`，
  转换显式校验（非法转换抛错）；keepalive 失败 / 过期 ⇒ 重新创建（60 分钟 TTL 由 `listen_key_ttl_ms` 注入，无默认值）。
- 重连后**不假设状态连续**：`continuity_assumed=False` 直到建立新的 snapshot boundary（真正对账留给 P0001.9.3）。
- 去重 / 乱序：`ORDER_TRADE_UPDATE` 以 `cumulative_fill_qty` 为每单水位（回退即 out-of-order）+ `(client_order_id, trade_id)` 去重；
  `ACCOUNT_UPDATE` 以 `(transaction_time, event_time)` 水位。全部计数进 telemetry。

### 0.6 启动顺序（状态空窗）

```text
创建 listenKey → 建立 user stream → 拉取 account/position snapshot → 记录 snapshot boundary → 应用之后到达的事件
```

先 stream 后 snapshot（提案要求），否则存在状态空窗；`snapshot_boundary` 记录两个时间戳与 listenKey，供 P0001.9.3 对账使用。

### 0.7 Private stream latency（SC-12 / SC-13）

- 每个事件记录 `receive_lag_ms = receive_ts - event_ts`，telemetry 输出 **median / p95 / max**（有界样本）。
- `max_median_private_lag_ms` 为**必填**配置；真实 smoke 若 median 超阈值 ⇒ 本提案在完成报告中标记 **BLOCKED**
  （不进入真实下单阶段），并给出链路归属证据（tight-loop / 分层测量）。
